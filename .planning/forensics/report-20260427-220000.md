## Root Cause: The Always-On Assumption Audit That Never Happened

The v2.0 milestone (Phases 06–10) introduced the always-on architecture:
- **Phase 06:** Infrastructure foundation
- **Phase 07:** REST API security
- **Phase 08:** Scheduler real-time layer
- **Phase 09:** Operational web UI
- **Phase 10:** Servy cutover (the actual switch from batch to continuous)

That cutover was a **mechanical transformation** — it wrapped the existing Node.js process in Servy so it stays alive between cycles. But it did not audit the *implications*:

| Assumption from batch era | Reality after always-on | Bug it caused today |
|---------------------------|-------------------------|---------------------|
| Process exits, OS reclaims FDs | FDs accumulate forever | **EMFILE (#14)** |
| Pool connections are short-lived | Connections retain `USE [DB]` state across reuses | **SQL pool leak (#16)** |
| Dashboard makes occasional calls | 5s polling = 720 calls/h sustained | **Rate limit (#17)** |
| Operators don't interact much | Phase 17's "Ejecutar Ahora" button gets clicked | **API key UX (#18)** |
| Implicit defaults are safe | Changing one breaks N silent dependents | **FESA regression (#19)** |

Phase 17 didn't create any of this. It just **made the dashboard useful enough** that operators interacted with it, and **added polling** that exercised the API at sustained rates. Those two changes pulled the curtain back on the entire latent-debt pile.

Note also: each hotfix only became *visible* once the previous one was deployed. EMFILE had to be fixed before the SQL pool issue could surface (the service was crashing too often to accumulate enough pool reuse). The rate limit had to be fixed before the API key issue could be tested (every request was 429ing). The cascade is sequential because each layer's failure mode masked the next.

## Recommended Actions

### Immediate (this milestone, v2.3)
1. **Audit remaining always-on assumptions before Phase 18.** Phase 18 is "Auto-release & Manual Override" for stuck locks — it touches `OperationManager`, `setTimeout`, possibly `setInterval`. These are exactly the kind of long-running primitives where batch-era assumptions break (timer leaks, callback retention, etc.). Spend 30 min reading the planned phase doc through the "what assumes the process exits?" lens before implementing.

2. **Document `always-on` as a first-class constraint** in `.planning/PROJECT.md` or `CLAUDE.md`. Future code reviews should ask: "would this work if I never restarted?" Make it explicit so it's not re-forgotten.

### Short-term (next 1–2 weeks)
3. **Add a long-running soak test to CI/local QA.** Spin up the service, run a synthetic load (cron tick + dashboard polling) for 30+ minutes, and assert: FD count is stable, pool stats are stable, memory is stable, log size is bounded. This is the test class that would have caught EMFILE, SQL pool leak, and rate limit issues before deploy.

4. **Audit all `runQuery(query)` callers (no second arg)** as a regression preventer. PR #19 fixed 7. Future controllers being added to the codebase need to be reviewed against the "what database does this hit?" question explicitly.

### Long-term (architectural)
5. **Reject implicit defaults in shared helpers.** The `runQuery(query, database = ...)` default is the root pattern that caused both #16 and #19. Consider making `database` a **required parameter** (no default) — every caller must state intent. Tradeoff: more verbose, but eliminates the entire bug class.

6. **Move rate limit + similar config out of code and into `.env`.** The `200 → 2000` change required a code commit. If the polling cadence changes again, we're back to PR for a number bump. Externalize.

7. **Establish a "deploy day" runbook** that includes: (a) tail logs for first 15 min, (b) diagnose first cron tick before considering deploy validated, (c) keep at least one operator on standby during first hour. Today's firefight succeeded because of process discipline + immediate availability — codify it.
