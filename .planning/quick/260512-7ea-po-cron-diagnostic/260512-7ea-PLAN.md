# Quick Task 260512-7ea: PO Cron Diagnostic

## Problema

Operador reporta que el cron de cada 15 min **no está subiendo varias POs** al Portal de Proveedores (caso reportado: `PO0083449`). El script manual `src/scripts/po-upload.js` sube las mismas POs **sin errores**, lo que descarta validación Joi y rechazo de Focaltec.

Comparando código del cron (`src/controller/PortalOC_Creator.js:176-185`) vs. manual (`src/scripts/po-upload.js:203-208`):

- **Cron**: `WHERE X.Autorizada=1 AND X.Empresa=db AND (SELECT MAX(Fecha) FROM Autoriza_OC_detalle WHERE Empresa=db AND PONumber=A.PONUMBER) = CAST(GETDATE() AS DATE)`
- **Manual**: `WHERE X.Autorizada=1 AND X.Empresa=db AND A.PONUMBER IN (...)` (sin filtro de fecha)

Hipótesis: POs cuya última autorización en `Autoriza_OC_detalle.Fecha` fue **un día pasado** quedan permanentemente excluidas por el filtro `= CAST(GETDATE() AS DATE)`. Si el cron tuvo timeout, lock, o caída en su ventana original, la PO nunca se reintenta.

Operador **no tiene acceso directo a SQL Server** en prod (memoria `project_no_sql_access.md` + HANDOFF.md § 6). Cualquier diagnóstico debe ser un script Node.js ejecutable.

## Goal

Crear `src/scripts/po-cron-diagnostic.js` que, para cada PO pasada por CLI, replique exactamente las condiciones del WHERE del cron y emita un veredicto explícito que explique por qué la PO es (o no) levantada por el cron en su próxima corrida.

## Tasks

### Task 1 — Crear `src/scripts/po-cron-diagnostic.js`

**Files:** `src/scripts/po-cron-diagnostic.js` (NEW)

**Action:** Crear el script siguiendo el patrón de `src/scripts/diagnose-sage-tables.js` (safeRun + LOG_FILE module-top + console.table) y `src/scripts/po-diagnostic.js` (multi-step diagnostic por PO).

Estructura:

1. **Imports**: `runQuery`, `logGenerator`, `successResult`/`errorResult`, `config`.
2. **Module constants**: `LOG_FILE='PO_Cron_Diagnostic'`, `tenantDatabases`, `tenantIds`, `DEFAULT_DATABASE`, `skipIdentifiers`.
3. **safeRun(label, fn)**: try/catch que loguea y retorna `{__error: msg}` en vez de throw, igual que el patrón de diagnose-sage-tables.
4. **diagnoseOne(poNumber, database, tenantIndex)**: 5 checks secuenciales con safeRun:
   - 1. `POPORH1` lookup (existe?)
   - 2. `Autorizaciones_electronicas.dbo.Autoriza_OC` (autorizada?)
   - 3. `MAX(Fecha)` de `Autoriza_OC_detalle` vs. `CAST(GETDATE() AS DATE)`
   - 4. Réplica exacta del WHERE del cron (con `LEFT JOIN POPORL`, `Autoriza_OC`, subselect de `MAX(Fecha)`, y `skipCondition` de `B.[LOCATION] NOT IN`)
   - 5. `fesa.dbo.fesaOCFocaltec` rows (status, responseAPI, idFocaltec)
   - Genera `verdict.reason` según prioridad: PO inexistente > no autorizada > ya POSTED > filtro de fecha > otras causas.
5. **runDiagnostic(poNumbers, database, tenantIndex)**: itera diagnoseOne para cada PO, imprime resumen con `console.table`, retorna `successResult({verdicts}, summary, {tenant, startTime})`.
6. **main()**: parsea CLI args (PO* → poNumbers, /^\d+$/ → tenantIndex, otro → database), valida rangos, llama runDiagnostic, setea `process.exitCode = 1` en error.
7. **Exports**: `{diagnoseOne, runDiagnostic}`. Entry point: `if (require.main === module) main()`.

Convenciones:
- 4 spaces (consistente con `diagnose-sage-tables.js`).
- CommonJS, sin ESM.
- `runQuery(sql, database)` para Sage 300; `runQuery(sql, 'FESA')` para fesaOCFocaltec.
- Solo `SELECT`. Sin `INSERT`/`UPDATE`/`DELETE`.

**Verify:**
- `node -c src/scripts/po-cron-diagnostic.js` (syntax check).
- `node src/scripts/po-cron-diagnostic.js` sin args imprime usage + `exitCode=1`.
- `node src/scripts/po-cron-diagnostic.js PO0083449` corre los 5 checks contra COPDAT/tenant 0 (en prod; localmente fallará por SQL connection — esperado).
- Source-grep: `grep -E 'INSERT |UPDATE |DELETE FROM' src/scripts/po-cron-diagnostic.js` retorna 0 matches (solo lectura).

**Done:** archivo committed con mensaje `feat(quick-260512-7ea): add po-cron-diagnostic script for cron WHERE replication`.

- **No backfill** de POs huérfanas. También requiere phase aparte para no escribir filas erróneas a `fesaOCFocaltec` en producción.
