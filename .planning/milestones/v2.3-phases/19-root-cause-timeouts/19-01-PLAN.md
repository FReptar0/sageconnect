## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client (background-cycle) → portal de proveedores HTTP | Outbound trust: nuestro cliente confía en el portal pero el portal puede demorar/colgar. Timeout es la mitigación. |
| .env → config.js | Operador suministra `PORTAL_HTTP_TIMEOUT_MS` via .env; config aplica fail-fast para evitar misconfigs. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-01-01 | Denial of Service | `forResponse` always-on cycle | mitigate | Default `PORTAL_HTTP_TIMEOUT_MS=30000` aborta requests colgados; previene lock huérfano (root cause del bug 409). Range guard `>= 1000` rechaza misconfigs catastróficas (timeout 0 = sin timeout = regresión a estado pre-Phase 19). |
| T-19-01-02 | Information Disclosure | URL del axios timeout en logs | accept | URLs del portal incluyen tenant id (`urlBase(index)` con tenantIds[index]) y query params (`from=YYYY-MM`, `documentTypes=CFDI`, etc.). NO incluyen credenciales (auth via headers `PDPTenantKey`/`PDPTenantSecret`). El log entry `url=` en `[TIMEOUT]` (Plan 19-03) expone tenant id + query params. **Surface aceptado:** los tenant ids ya se loggean rutinariamente en `[START]`/`[COMPLETE]` entries de cada step. Si en el futuro requerimos PII redaction, refactor centralizado (no Phase 19). |
| T-19-01-03 | Tampering | env `PORTAL_HTTP_TIMEOUT_MS` con valor absurdo | mitigate | Range guard fail-fast: `< 1000` aborta arranque con `[CONFIG ERROR]` log. Mismo patrón que `LOCK_TIMEOUT_MS < 60000` guard. Operador no puede shippear el servicio con un timeout que reproduzca el bug. |
| T-19-01-04 | Repudiation | axios timeout sin context para forensia | accept | Plan 19-03 cubre el `[TIMEOUT]` log entry con `step + tenant + url + durationMs` — fuera de scope para 19-01. Plan 19-01 solo provee la infraestructura del timeout. |
| T-19-01-05 | Elevation of Privilege | n/a | n/a | Cliente axios singleton no introduce nuevos privilege boundaries. Auth headers siguen siendo per-tenant en cada call site (no se mueven al cliente compartido — § anti-pattern). |
