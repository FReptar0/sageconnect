<objective>
Implement the **manual override** half of Phase 18: a `POST /api/schedule/:taskId/force-release` endpoint that an operator (or the UI in Plan 18-03) can call to release a stuck `OperationManager` lock without waiting for the 14-minute auto-release. The endpoint is idempotent (always 200 — `released:false` when there's nothing to release), guarded by the standard `requireApiKey + validate + writeLimiter + asyncHandler` chain, and produces parity audit + email side-effects with the auto-release path (D-08).

Purpose: REC-04 (force-release endpoint) + REC-05 (audit history on force-release). Plus parity email (D-08 extends REC-05) so the admin sees both auto and manual releases with equivalent visibility.

Output: New POST handler in `schedule-routes.js`, two new Joi schemas in `schedule-schemas.js`, one new integration test file. The admin-email helper is COPIED INLINE from Plan 18-01's `CronScheduler.js#sendAdminAlert` (same nodemailer-direct pattern, NOT `EmailSender.sendMail`) — intentional duplication per PATTERNS.md §5 to keep blast radius tight; refactor to a shared util in a future phase if a third use case appears.

               const reason = (req.body && req.body.reason) || null;

                       'Sin lock activo para liberar'

       - **Reason handling for log/email injection:** the `reason` value is already capped at 200 chars by Joi. We embed it via simple string concat into the email HTML and into the log. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public network → API | Untrusted HTTP clients reach `POST /:taskId/force-release`. Only mitigated entry: `requireApiKey` (shared `x-api-key`). The endpoint is mounted under `/api/schedule` which is guarded at app level by the API key middleware in addition to the route-level `requireApiKey`. |

| API → SMTP (nodemailer) | Outbound to `config.mailing.server`. Auth credentials sent on outbound channel. |
| API → log filesystem | `logGenerator` writes to `paths.logs/ScheduleRoutes.log`. Reason string and tenant/operationId names embedded in log messages. |
