    ```javascript
    /**
     * REC-03 (D-05/D-07): handle the confirm button click of the force-release modal.
     * State machine documented in UI-SPEC §"Destructive confirmation summary":
     *   idle -> loading (disable buttons, swap label/icon)
     *   on 200/released:true  -> close modal, hideActiveOperationCard() (optimistic), no toast.
     *   on 200/released:false -> close modal, warning toast, hideActiveOperationCard().
     *   on 4xx/5xx/network    -> stay open, re-enable, render inline error alert.
     */
    async function submitForceRelease() {
        const confirmBtn = document.getElementById('btn-force-release-confirm');
        const cancelBtn  = document.getElementById('btn-force-release-cancel');
        const errorSlot  = document.getElementById('forceReleaseModalError');

        // Capture original (idle) HTML for restoration in finally
        const idleConfirmHtml = '<i class="fas fa-unlock-alt me-1"></i>Confirmar liberación';

        // Loading state
        confirmBtn.disabled = true;
        cancelBtn.disabled = true;
        confirmBtn.innerHTML = '<i class="fas fa-spinner fa-spin me-1"></i>Liberando...';
        errorSlot.style.display = 'none';
        errorSlot.innerHTML = '';

        try {
            const res = await apiCall('POST', '/api/schedule/background-cycle/force-release', {});

            if (res && res.success) {
                // Close the modal via the cached Bootstrap instance.
                // (The instance was lazily created by the data-bs-toggle="modal" trigger; getInstance returns it.)
                const modalEl = document.getElementById('forceReleaseModal');
                const modalInstance = bootstrap.Modal.getInstance(modalEl);
                if (modalInstance) modalInstance.hide();

                // Idempotent path warning (UI-SPEC line 122)
                if (res.data && res.data.released === false) {
                    showToast('El lock ya se había liberado', 'warning');
                }

                // Optimistic UI: hide the card immediately so the operator sees instant feedback.
                // The next 5s poll will independently confirm and idempotently re-hide if needed.
                hideActiveOperationCard();
            } else {
                throw new Error(
                    (res && (res.summary || res.message || (Array.isArray(res.errors) && res.errors[0])))
                    || 'Error desconocido'
                );
            }
        } catch (err) {
            // Inline error rendering — modal stays open, operator can retry.
            const safeMsg = (err && err.message) || 'Error desconocido';
            errorSlot.innerHTML =
                '<div class="alert alert-danger py-2 mb-0">' +
                '<i class="fas fa-times-circle me-2"></i>' +
                'Error al liberar el lock: ' + escapeHtml(safeMsg) + '. ' +
                'Intentá nuevamente o revisá los logs del servidor.' +
                '</div>';
            errorSlot.style.display = 'block';
        } finally {
            // Restore idle state. If the modal closed on success, these properties simply update an unmounted DOM — harmless.
            confirmBtn.disabled = false;
            cancelBtn.disabled = false;
            confirmBtn.innerHTML = idleConfirmHtml;
        }
    }

    /**
     * Minimal HTML-escape helper — only used inside the inline error slot (where err.message
     * may contain "<", ">", "&", etc. from a server error like 'invalid <foo>').
     * Why: we use innerHTML for the inline alert (we want to render the icon and class).
     * The server error message is the only untrusted segment within that HTML string.
     */
    function escapeHtml(s) {
        return String(s).replace(/[&<>"']/g, (c) => ({
            '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;'
        }[c]));
    }
    ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Polling response → DOM | `pollActiveOperation` writes server JSON into `activeOpSnapshot`. The `show.bs.modal` listener reads from `activeOpSnapshot` to populate the modal context line via `innerHTML`. Server is trusted (same-origin, API-key authed), but defense-in-depth requires HTML escaping. |
| Operator click → API | Confirm click triggers `apiCall('POST', '.../force-release', {})`. Body is fixed `{}` (no user input). API key is auto-injected by `apiCall` from `<meta name="x-app-key">`. |
| Server error message → DOM | `submitForceRelease` catches errors and renders `err.message` into an inline alert via `innerHTML`. Server `summary` / `errors[]` strings are trusted by source but may include legitimate `<` / `>` from invalid input echoes. Must be HTML-escaped. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-18-03-01 | Tampering / XSS | `activeOpSnapshot.stepProgress[i].step` and `.tenant` injected via `innerHTML` into modal context | mitigate | Wrap every dynamic value with `escapeHtml(...)` before string-concatenation into `innerHTML`. The server-side step name is from a fixed enum (8 values) and tenant is from `config.portal.tenants[].id`, but defense-in-depth: a future server bug or compromised polling pipeline must not be able to inject markup into the modal. Verified by the XSS-prevention spot-check in Task 3. |
| T-18-03-02 | Tampering / XSS | `activeOpSnapshot.operationId` → modal short-id display | mitigate | Although operationId is server-generated `crypto.randomUUID()` and structurally cannot contain `<` / `>` / `&`, `escapeHtml` is applied to `shortId` for consistency. Cost: zero (escapeHtml on UUID-shaped strings is a no-op). |
| T-18-03-03 | Tampering / XSS | Server error message rendered into inline error alert | mitigate | `submitForceRelease`'s catch block calls `escapeHtml(err.message)` before string-concatenation into `errorSlot.innerHTML`. Server errors that legitimately contain HTML control characters (e.g., a Joi message echoing user input) will not break out of the alert. |
| T-18-03-04 | Spoofing | Clickjacking — embedding the dashboard in an iframe to trick a user into clicking `Confirmar liberación` | accept | The dashboard is internal (RDS-only access at Capstone per CONCERNS.md / project_prod_paths). No public exposure surface. Server-level `X-Frame-Options` / CSP `frame-ancestors` is out of scope for Phase 18 (would be a separate hardening phase). |
| T-18-03-05 | Tampering / CSRF | Cross-origin POST to `/force-release` from an attacker page | mitigate | The endpoint requires `x-api-key` header. Browsers do NOT include custom headers on cross-origin form-encoded POSTs without a preflight, and preflight requires CORS allowlist (the project does not allow cross-origin by default). Functionally equivalent to CSRF-protected. |
| T-18-03-06 | Denial of Service | Operator rapidly clicking Confirmar before the response arrives | mitigate | The state machine disables BOTH the Confirmar AND the Cancelar button on entering the loading state (UI-SPEC line 273). Even `submitForceRelease` is idempotent client-side (the disabled button cannot fire a second click), and the server is idempotent (Plan 18-02). |
| T-18-03-07 | Information Disclosure | `activeOpSnapshot` logged to console / inspected in DevTools | accept | An operator with dashboard access already has API access. Same data is visible via direct API calls to `/api/operations/status`. |
| T-18-03-08 | Repudiation | Operator force-releases without intent (accidental click on `Confirmar`) | mitigate | Two safeguards: (a) Cancelar receives initial focus, so a stray Enter does NOT confirm; (b) the Bootstrap modal requires an explicit click on Confirmar (no double-click pattern, no swipe gesture). Server-side audit (Plan 18-02 `addHistory` + admin email) provides the post-hoc record. |
| T-18-03-09 | Tampering | A user with dashboard access edits the inline `<script>` block via DevTools to call `submitForceRelease()` directly | accept | A user who can edit JavaScript on the page already has API access (via the `<meta name="x-app-key">` tag). Browser-side script tampering is not a meaningful threat given the trust boundary. |

**Severity assessment:** No `high` severity threats. All `mitigate` items have explicit test or implementation mitigations within Plan 18-03 scope. Three `accept` items document pre-existing trust assumptions (internal RDS-only deployment, dashboard==API equivalence, browser-side trust).

**Note on default `innerHTML` use:** The plan uses `innerHTML` (not `textContent`) for the modal context line because we want to render `<code>` and `<em>` markup intentionally. The ONLY untrusted segments inside the constructed HTML are the dynamic values (`shortId`, `startedRel`, `labelText`, `tenant`), and ALL of those are wrapped in `escapeHtml(...)` before concatenation. The pattern is: trusted markup (template literals containing `<code>`, `<em>`, etc.) + escaped dynamic values. This is the standard sanitization-at-the-leaf approach and matches how `renderActiveOperationCard` (existing Phase 17 code) already operates.
