## Overview

Eliminar el bug donde el botón "Ejecutar Ahora" en `schedule.html` retorna permanentemente HTTP 409 "ya en ejecución" por locks huérfanos en `OperationManager`. Reportado 2026-04-24 en producción (ZCL-RDS-02, Capstone Copper). Cerrado el lock-recovery loop end-to-end con tres capas:

1. **Observability (Phase 17)** — visibilidad en tiempo real del estado de locks y heartbeats por step
2. **Recovery (Phase 18)** — auto-release por timeout + manual force-release vía API y UI
3. **Prevention (Phase 19)** — timeouts explícitos en axios al portal, child process del importador, y per-step en el ciclo

Reemplaza la "phantom continuation" tolerada en Phase 18 D-03 con semántica real de abort para HTTP work, child processes, y narrowed para per-step.

## Milestone Summary

### Key Accomplishments

1. **Lock observability stack (Phase 17)** — OperationManager.stepProgress array slot + startStep/endStep API + GET /api/operations/status enriched wire shape + "Operación en curso" Bootstrap 5.3 card with 5s polling + 1s heartbeat ticker. Operator sees in real time which step of the cycle is running, tiempo transcurrido, y último heartbeat.

2. **Auto-release timer (Phase 18 Plan 01)** — Lock auto-releases via `setTimeout(LOCK_TIMEOUT_MS)` inside `acquireLock` (default 14 min ≈ 93% of 15-min cron cadence), emits `lock:timeout` EventEmitter event with snapshot, listener writes audit history + sends admin email + warn-log con prefix `[TIMEOUT]`. Configurable via env `LOCK_TIMEOUT_MS` con fail-fast guard `<60s`.

3. **Manual force-release (Phase 18 Plans 02 + 03)** — `POST /api/schedule/:taskId/force-release` idempotent endpoint (siempre 200, `released:true|false` discriminator, snapshot-before-release ordering, audit history + admin email parity con auto-release) + Bootstrap modal con state machine (idle/loading/success/idempotent/error) + escapeHtml XSS defense + Cancelar focus override anti-accidental-Enter. Recovery loop closed: operador recupera lock stuck vía UI sin SSH/service restart.

4. **Root-cause timeouts (Phase 19, todos los 3 planes)** — `PortalClient` singleton (`axios.create` con `httpTimeoutMs` default 30s) cubriendo 18 axios call sites en 9 files + `startChildProcess` kill cascade (SIGTERM → 30s grace → `taskkill /F /T` tree-kill, default 10 min) con `hasSettled` double-settle guard + per-step `Promise.race` vía `withStepTimeout` helper envolviendo 7 forResponse step blocks (default 5 min). Defense-in-depth invariant verificado: axios (30s) < step (5m) < child (10m) < lock (14m).

5. **Unified [TIMEOUT] log routing (ROOT-04)** — Cross-cutting log format `[TIMEOUT] step=... tenant=... url=... durationMs=... err=...` rooted en per-source files: `ChildProcess.log` (background.js cascade) + `CronScheduler.log` (catch handlers + email dispatch) + `ForResponse.log` (step timeouts) + caller-specific (PortalPaymentController.js como ejemplo cross-cutting). Email dispatch SOLO para child-process timeouts (D-15 — evita inbox flood de transient axios timeouts).

6. **Security hardened, 17/17 threats closed** — STRIDE threat model across Phase 19 plans (T-19-01-{01..05} + T-19-02-{01..06} + T-19-03-{01..06}) verified by gsd-security-auditor con file:line evidence. Phase 19 boundary HELD: phantom continuation NARROWED de "all" a step-level only (axios timeout = real abort vía ECONNABORTED; child kill = real OS abort vía taskkill /F /T; per-step Promise.race = wrapped promise sigue corriendo pero axios layer corta HTTP work in flight).
