# Phase 20.3: Cross-system detection query (409 / portal existence) - Context

**Gathered:** 2026-07-28
**Status:** Ready for planning

<domain>
## Phase Boundary

A portal existence probe for purchase orders, wired into `createPurchaseOrders()` and gated on prior failure, that reconciles `fesa.dbo.fesaOCFocaltec` when the portal confirms it already holds the OC — so a lost acknowledgement stops feeding a permanent 409 → `ERROR` loop.

This phase adds a **decision point inside the upload loop**. It does not change what the cron query selects, it does not change retry timing, and it does not change the schema.

</domain>

## Implementation Decisions

All four gray areas were delegated to Claude by the user (2026-07-28): *"lo que tú me recomiendes decide por mí, solo que cumpla lo que debe de cumplir y sin agregar dificultad innecesaria o que descuadre con más cosas."* Every decision below was therefore taken against three explicit criteria: **satisfy the locked SPEC**, **minimum diff**, and **do not knock existing structures out of alignment**. Rationale is recorded for each so the planner can tell a deliberate choice from an arbitrary one.

### Probe placement in the upload loop

- **D-01: The probe runs FIRST in the loop body, before Joi validation** — an early `continue` at the top of the `for` over `ordersToSend` (`PortalOC_Creator.js:266`), ahead of the existing 4.3 validation block at L280.

  *Why:* the existence question is logically prior to payload validity. If the portal already holds the OC, no payload is being sent, so validating one is pointless work whose only side effect is harmful — the Joi failure path at L290-306 INSERTs an `ERROR` row, which would inflate `errorCount` for an OC that is already resolved. Placing the probe after Joi would manufacture exactly the noise this phase exists to stop. It is also the smaller diff: an early `continue` prepended to the loop body, versus splicing a branch between two existing blocks.

  *Bounded cost:* an OC that keeps failing Joi and does not exist in the portal absorbs one extra GET per tick. Acceptable and bounded by the `errorCount > 0` gate.

### Getting `errorCount` from the recordset to the loop

- **D-02: Build a function-scoped `Map` keyed by trimmed `EXTERNAL_ID` → `errorCount` from `recordset`, before `groupOrdersByNumber()`.** The loop reads `errorCounts.get(po.external_id.trim()) || 0`.

  *Why:* the query is one row per PO **line**; the loop iterates `ordersToSend`, which is the output of `groupOrdersByNumber()` → `parseExternPurchaseOrders()`. `errorCount` would be lost in that transformation. The alternative — threading it through those two shared utils — modifies helpers used elsewhere and is exactly the blast-radius trap CLAUDE.md §6 #2 records. A local `Map` touches nothing outside the function.

  *Always-on:* the `Map` is function-scoped and collected when `createPurchaseOrders()` returns. No module-scope retention (CLAUDE.md §3).

  *`.trim()` on both sides is load-bearing:* `ocSage` is `nchar` (space-padded) and the query emits `RTRIM(A.PONUMBER)`.

### Helper location and return contract

- **D-03: New file `src/utils/GetPurchaseOrders.js`, exporting `getPurchaseOrderByExternalId(index, externalId)`.** Mirrors `src/utils/GetProviders.js` structurally: module-scope tenant arrays from config, `urlBase(index)` builder, `PortalClient` singleton, `PDPTenantKey`/`PDPTenantSecret` headers, exact-match `.trim()` re-filter over `response.data.items`, ambiguity guard on >1 exact match.

  *Why not inside the controller:* it would be untestable in isolation and invisible to reuse. *Why not a new service under `src/services/`:* a service layer for one consumer is the "dificultad innecesaria" the user ruled out — `GetProviders.js` sets the precedent that this kind of lookup lives in `utils/`, and CLAUDE.md §7 routes shared helpers there.

- **D-04: The return value is a discriminated plain object — it must NOT copy `getProviderByExternalId`'s contract.**

  ```
  { outcome: 'found',  id, status }     // 200, exactly one exact external_id match
  { outcome: 'absent' }                 // 200, zero exact matches
  { outcome: 'unknown', reason }        // anything else — see below
  ```

  *Why the deviation is mandatory:* `getProviderByExternalId` returns `null` for "not found" (`GetProviders.js:84`) **and** `null` for "the GET threw" (`GetProviders.js:101`). RETRY-D2 forbids exactly that conflation — misreading "portal unreachable" as "OC absent" produces the duplicate POST this phase exists to prevent. Copy the file's structure, not its return contract.

  *`unknown` covers:* non-`200` / rejected request, >1 exact match (ambiguous), and a malformed `idFocaltec` (D-05). `reason` is a short machine-greppable string, not a sentence.

  *No classes, no enum module, no `Symbol`:* a plain object with a string discriminant is the minimum that cannot conflate outcomes.

- **D-05: The `^[0-9a-fA-F]{24}$` guard (RETRY-D8) lives in the HELPER, not the controller.** A portal response whose `id` fails the shape returns `{ outcome: 'unknown', reason: 'invalid-id' }`.

  *Why:* it satisfies RETRY-D8 structurally rather than by discipline — the controller never receives a malformed id, so no code path exists in which one could reach a SQL string. It also keeps the controller's job to "consume three outcomes" with no validation logic of its own.

### Log label vocabulary

- **D-06: Two labels, mirroring the established `[RETRY-DEFER]` / `[RETRY]` pair — one per-row, one per-tick summary.** The outcome travels in a `result=` **field**, not in the label, so the label set cannot grow as branches are added.

  ```
  [PORTAL-CHECK] PO <ocSage> tenant=<db> result=<found|absent|cancelled|unknown|ambiguous> id=<idFocaltec> status=<portalStatus>
  [PORTAL-CHECK-SUMMARY] tenant=<db> probed=<n> found=<n> absent=<n> skipped=<n> unknown=<n>
  ```

  *Why not a label per outcome* (`[PORTAL-CHECK-FOUND]`, `[PORTAL-CHECK-FAIL]`, …): five labels for one concern, and every new branch adds a sixth. The codebase convention is one label per *concern* carrying structured `key=value` fields — `[RETRY-DEFER] PO x tenant=y attempts=n nextEligibleAt=t` is exactly that shape.

  *Levels:* `info` for `found` / `absent` / `cancelled`; `warn` for `unknown` / `ambiguous`.

  *Anchoring warning for the planner:* the existing `[RETRY*]` labels are pinned by `^…$` regexes in the controller suites, which is why 20.2 documented them as immovable. Choose these two strings once — they become equally immovable the moment a test anchors them.

### Test layout

- **D-07: Two new suites, and one assertion added to an existing suite.**

  | File | Status | Covers |
  |---|---|---|
  | `tests/utils/GetPurchaseOrders.test.js` | NEW | RETRY-D1, D2, D8 — helper outcomes, URL/header shape, id guard |
  | `tests/controller/PortalOC_Creator.portal-check.test.js` | NEW | RETRY-D4..D7 — gating, the six-row behaviour table, fail-closed |
  | `tests/controller/PortalOC_Creator.cron-where.test.js` | EXTEND | RETRY-D3 — SQL contains `ef.errorCount`, does NOT contain `ef.lastErrorAt` · **plus the mock repair below** |

  **The alias prefix in that assertion pair is load-bearing, not stylistic.** `buildErrorStatsApply` (`RetryPolicy.js:204-206`) emits the bare substrings `errorCount` and `lastErrorAt` inside the `OUTER APPLY` itself, and `cron-where.test.js:107` already asserts `MAX(lastUpdate) AS lastErrorAt` is **present**. An unprefixed `not.toMatch(/lastErrorAt/)` would therefore fail instantly and contradict an existing assertion. Use `/ef\.errorCount/` and `not /ef\.lastErrorAt/`.

- **D-07b (pattern-mapper finding, 2026-07-28, verified): wiring the probe BREAKS an existing test unless its mock is repaired first.** `tests/controller/PortalOC_Creator.cron-where.test.js:53-54` mocks the portal client with **`post` only**:

  ```js
  const mockPortalPost = jest.fn();
  jest.mock('../../src/utils/PortalClient', () => ({ post: mockPortalPost }));
  ```

  Once the probe is wired, a fixture with `errorCount > 0` trips the gate, the helper calls `portalClient.get` — which is `undefined` — and the resulting `TypeError` is swallowed into `{ outcome: 'unknown' }`. Fail-closed then suppresses the POST, and the suite's "upload loop runs" assertion fails.

  *Required in the same commit as the wiring:* add a `mockPortalGet` to that mock and give it a default `{ data: { items: [], total: 0 } }` (i.e. *absent*) so the existing cases keep their pre-phase meaning — those fixtures were written to prove eligibility math, not portal behaviour, and must go on proving exactly that. This is a **mock repair, not a behaviour change**; if any existing assertion has to be weakened to make it pass, stop and escalate.

  *Why the wiring tests do not go in `cron-where`:* that suite anchors the **shape of the emitted SQL** with regexes. The probe is **behavioural**. Keeping them apart means a behaviour change cannot break a SQL-shape anchor and vice versa — the same separation 20.2 used when it put the schema guard in its own `tests/schema-guard.test.js`. The one genuinely SQL-shaped assertion (D3) does belong in `cron-where`, so it goes there.

- **D-08: Mirror `tests/utils/GetProviders.test.js`, NOT `tests/GetProviderByExternalId.test.js`.**

  *Why this warning exists:* despite its name and its `*.test.js` extension, `tests/GetProviderByExternalId.test.js` is **not a Jest suite** — it is a manual CLI script (`node tests/GetProviderByExternalId.test.js <EXTERNAL_ID>`) that hits the live portal and calls `process.exit`. Copying it as a template would produce a live-portal script instead of a unit test.

  *Correction (2026-07-28, pattern-mapper finding, verified):* an earlier draft of this decision cited only `jest.config.js:5` (`testMatch: ['<rootDir>/tests/**/*.test.js']`) and implied Jest would execute the script. It does not — `jest.config.js:6-10` lists it in `testPathIgnorePatterns` alongside `EnhancedPaymentSync.test.js` and `ResolveUuidByFolio.test.js`. The decision stands (mirror `tests/utils/GetProviders.test.js`), but the runtime hazard it implied is not real. If a NEW live-portal script is ever added under `tests/`, it must be added to that ignore list — that is the actual standing rule.

- **D-09: Mock `src/utils/PortalClient`, not `axios`.** The established line is `jest.mock('../../src/utils/PortalClient', () => ({ get: mockGet }))` (`tests/utils/GetProviders.test.js:34`). Mock `src/config` too (Pattern S-9) so a missing env var cannot `process.exit(1)` the suite, and `src/utils/LogGenerator` so no log files are written.

- **D-10: `mockReset()` every shared mock in `beforeEach`, never `clearAllMocks()` alone.** Carried forward from 20.1-02: `jest.clearAllMocks()` does **not** drain queued `mockResolvedValueOnce` implementations, and both `cron-where` suites leaked stubs across cases until this was fixed. The new suites queue per-case portal responses, so they are exposed to exactly that bug.

### Established Patterns
- **Return a value, never throw, on an always-on path.** `computeRetryEligibility` is documented as never throwing because "an exception here aborts a cron tick mid-batch on an always-on service" (`RetryPolicy.js:53-59`). The probe inherits that posture — hence `{ outcome: 'unknown' }` rather than a rejected promise.
- **One label per concern with `key=value` fields**, per-row plus a per-tick summary (`[RETRY-DEFER]` + `[RETRY]`).
- **Log labels become immovable once a test anchors them** with `^…$` — 20.2 recorded this as the reason the `[RETRY*]` strings could not be corrected even when their timezone semantics were found to be misleading.
- **Every failed OC attempt INSERTs a new row**; nothing updates in place. That is why `buildErrorStatsApply` uses `COUNT(*)`, and why reconciliation is an INSERT (RETRY-D6).

<specifics>
## Specific Ideas

- The lost-ack failure this phase automates has a worked manual precedent: PO0084361 (COPDAT, tenant `t7e92ajx4dm77k`, 2026-06-30). Its runbook step 2 — *seed one `POSTED` row, leave the old `ERROR` rows alone ("harmless")* — is precisely the reconciliation shape RETRY-D6 locks in. The phase is that runbook's detect-and-seed half, automated.
- `OPEN` in the control table means **the OC already exists in the portal** — confirmed 2026-07-27 and proven by `src/controller/PortalOC_StatusUpdater.js:117-124`, which only writes rows where `idFocaltec IS NOT NULL`. This corroborates the phase's premise: rows carrying portal-vocabulary statuses are, by construction, OCs that reached the portal.

<deferred>
## Deferred Ideas

- **CR-02 — OC dedupe misses `CANCELLED` and `OPEN`** (todo `2026-07-27-oc-dedupe-misses-cancelled-and-open-statuses.md`). Explicitly considered during this discussion and **kept out** (user decision, 2026-07-28).

  *Reasoning:* 20.3 adds a decision point **inside** the loop, does not change what the query selects, and is fully verifiable with mocks; its failure mode is noisy (a visible 409). CR-02 changes **candidate selection** against a production table with no staging, and its failure mode is silent (an OC that never uploads) — this codebase's documented enemy (CLAUDE.md §3). Folding them would force one review pass to hold two different risk models on the same lines.

  *Known interaction the planner should not try to fix here:* a Sage-cancelled PO loses its `POSTED` row (`PortalOC_Canceller.js:100` UPDATEs it to `CANCELLED`), so it reaches the cron with `errorCount = 0`, skips the probe, and absorbs one 409. The next tick sees `errorCount = 1`, probes, finds `CANCELLED`, and stops POSTing. **20.3 therefore mitigates CR-02 without closing it** — the dedupe keeps selecting that OC every tick, producing a perpetual but harmless GET. Closing it is CR-02's job.

  *Recommended predicate when it does get a phase:* `AND status <> 'ERROR'` in both RETRY-C7 sites, with the silent-failure trade-off the todo documents weighed explicitly at that time.

- **D-ITEM-03 / CR-04** — projecting `ef.lastErrorAt` and restoring a working PO retry interval. Blocked on an `ALTER TABLE` giving `fesaOCFocaltec` a time-carrying timestamp; must land together with CR-04. The interval remains inert after this phase, which is why the probe is gated on `errorCount` rather than on deferral.
