## Critical Issues

### CR-01: un `200` con cuerpo malformado se reporta como `absent` y habilita el POST duplicado

> **RESUELTO** — fuente `adef1bf`, cobertura `07dcb9d`.
> `src/utils/GetPurchaseOrders.js` ahora devuelve `{ outcome: 'unknown', reason: 'malformed-response' }`
> —la quinta constante del contrato— cuando el cuerpo del 200 no trae un arreglo `items`. El
> controlador no se tocó: su rama por defecto (`PortalOC_Creator.js:351-355`) ya trataba cualquier
> `reason` no reconocido como terminal, lo que se comprobó en ejecución.
> Control negativo: los cuatro cuerpos de la transcripción devolvían `absent` contra el fuente
> anterior, y el caso de cableado con `{ data: {} }` **sí emitía el POST duplicado** (verificado
> restaurando el fuente pre-fix). Cobertura nueva: cuatro cuerpos malformados + el control positivo
> de que `{items: [], total: 0}` sigue siendo `absent`, más el caso de cableado que exige cero POST
> y cero filas.

**File:** `src/utils/GetPurchaseOrders.js:95`
**Issue:**

```js
const items = response.data.items || [];
```

El predicado que la fase declara —«sólo un 200 con cero coincidencias exactas significa que la OC no
está»— no es el que el código implementa. El implementado es «un 200 cuyo `items` no resuelva a un
arreglo con una coincidencia exacta». Ambos difieren exactamente en el caso del cuerpo malformado, y
ahí el `|| []` convierte «no sé» en «no existe».

Ejecutado contra el módulo real (dobles inyectados en `require.cache`, sin tocar el fuente):

```
  200 body = {} (no items key)                       -> {"outcome":"absent"}
  200 body = {items:null, total:7}                   -> {"outcome":"absent"}
  200 body = HTML string (proxy/login)               -> {"outcome":"absent"}
  200 body = {code,description} envelope             -> {"outcome":"absent"}
  200 body = {items:[], total:0} (true absent)       -> {"outcome":"absent"}
```

Las cuatro primeras filas son indistinguibles de la quinta para el controlador. Y el segundo caso es
el peor de todos: el portal está diciendo `total: 7` — afirmando que SÍ tiene coincidencias — y el
helper responde `absent`.

Los disparadores son reales, no hipotéticos:

1. **Redirección a una página de login / WAF / proxy.** `PortalClient` es un `axios.create()` sin
   `maxRedirects: 0` (`src/utils/PortalClient.js:16-19`), así que axios sigue el 302 y entrega un
   `200` con `data` = string HTML. `'<html>…'.items` → `undefined` → `[]` → `absent`.
2. **Sobre de error con status 200.** El propio codebase ya asume que el portal devuelve cuerpos
   `{code, description}` (`PortalOC_Creator.js:510`). Servido con 200 en vez de 4xx → `absent`.
3. **`items: null` en una respuesta vacía o degradada** — variante común en APIs Java/Kotlin.

Consecuencia en el controlador (`PortalOC_Creator.js:324`): `probe.outcome === 'absent'` ⇒ no entra
al bloque, cae a Joi y hace POST. Si el portal ya tenía la OC → 409 → fila ERROR → `errorCount++` →
mismo ciclo el siguiente tick. Es decir, exactamente el deadlock que la fase 20.3 existe para
cortar, ahora con un GET extra por tick y con una línea de bitácora `result=absent` que le dice al
operador que todo funcionó. Fallo silencioso, el modo de falla que CLAUDE.md §3 y HANDOFF §7
señalan como el más caro de este codebase.

Ninguna prueba cubre este caso: `tests/utils/GetPurchaseOrders.test.js` sólo construye cuerpos vía
`ok(items)` (L55-57), que siempre produce un `items` array bien formado.

**Fix:**

```js
// GetPurchaseOrders.js, sustituye la L95
// RETRY-D2: un 200 cuyo cuerpo no trae un arreglo `items` NO prueba ausencia — no prueba nada.
// Colapsarlo a [] lo convierte en 'absent', el único desenlace que autoriza el POST.
const body = response && response.data;
if (!body || !Array.isArray(body.items)) {
    console.warn(`[WARN] Malformed portal body for externalId: ${externalIdClean}`);
    logGenerator(logFileName, 'warn', `Malformed portal body for externalId: ${externalIdClean}`);
    return { outcome: 'unknown', reason: 'malformed-response' };
}
const items = body.items;
```

El controlador ya trata cualquier `reason` desconocido correctamente (`PortalOC_Creator.js:351-355`:
`result = 'unknown'`, `localStatus` sigue `null`, no escribe fila, `continue`), así que no requiere
cambio. Añadir a `tests/utils/GetPurchaseOrders.test.js` los cuatro cuerpos de arriba con
`expect(result).toEqual({ outcome: 'unknown', reason: 'malformed-response' })`, y un caso de
controlador que afirme `expect(mockPortalPost).not.toHaveBeenCalled()` para `{ data: {} }`.

## Warnings

### WR-01: el `catch` del helper puede lanzar, rompiendo el contrato «nunca lanza»

> **RESUELTO** — fuente `5b475c3`, cobertura `401dfc8`.
> El valor se normaliza una sola vez con `String(...)` y se declara fuera del `try`, de modo que el
> `catch` ya no lo recalcula. **Desviación deliberada respecto del arreglo sugerido:** la
> *asignación* se dejó DENTRO del `try` en vez de calcularla fuera — `String()` sobre un objeto con
> un `toString` hostil también lanza, y sacarla habría movido esa excepción fuera de la protección
> (el mismo fallo, un renglón más arriba). Así se conserva además la doctrina S-3 de «el cuerpo
> entero dentro del try» que documenta el propio archivo.
> Control negativo: los dos casos nuevos fallaban con `TypeError: (externalId || "").trim is not a
> function` lanzado **desde el catch** (`GetPurchaseOrders.js:151`), es decir con la excepción
> escapando del helper, exactamente como describe el hallazgo.

**File:** `src/utils/GetPurchaseOrders.js:134` (y `:74`)
**Issue:** El JSDoc (L38) declara «Nunca lanza, nunca devuelve un valor nulo», y el comentario del
catch (L135-136) razona explícitamente sobre no hacer estallar el propio catch. Pero la primera
línea del catch repite la operación que puede haber causado la excepción:

```js
} catch (error) {
    const externalIdClean = (externalId || '').trim();   // <- vuelve a lanzar
```

Con un `externalId` que no sea string, `(valor || '').trim` es `undefined`; el `try` lanza, el
`catch` lanza lo mismo, y la excepción escapa del helper. Verificado:

```
  non-string externalId (number 12345)  ->  THREW: TypeError: (externalId || "").trim is not a function
```

Hoy no es alcanzable desde el único call site (el controlador pasa `ocKey`, ya `String(...)`), pero
el helper es una utilería exportada y su contrato es lo que el próximo consumidor va a creer. En un
servicio que no termina entre ticks, una excepción que escapa aborta el tick a media tanda
(CLAUDE.md §3).

**Fix:** normalizar con `String()` en ambos sitios y calcular el valor una sola vez, fuera del try:

```js
async function getPurchaseOrderByExternalId(index, externalId) {
    const logFileName = 'GetPurchaseOrders';
    const externalIdClean = String(externalId == null ? '' : externalId).trim();
    try {
        if (!externalIdClean) { /* … igual … */ }
        // …
    } catch (error) {
        // ya no recalcula externalIdClean
    }
}
```

### WR-02: el `catch` de la sonda reporta `reason=write-failed` siempre, y en el camino `absent` suprime un POST legítimo

> **RESUELTO** — fuente `1a5df04`, cobertura `c8d9bad`.
> Se adoptó la variable de etapa que propone el arreglo: `reason` pasa a ser
> `probe-failed` | `write-failed` | `log-failed` | `log-absent-failed`, y el `catch` deshace el
> `probeAbsent++` cuando la excepción cayó en el tramo `absent`, de modo que
> `probed === found + absent + skipped + unknown` se sostiene también ahí. El conjunto de etiquetas
> no creció (la Guarda 9 sigue verde).
> **Lo que NO cambió, a propósito:** el `continue` del `catch` se conserva, así que una excepción en
> el tramo `absent` sigue difiriendo el POST al siguiente tick. Sacar la bitácora del `try` la
> dejaría desprotegida —el camino `absent` no hace `continue`, así que una excepción ahí escaparía y
> abortaría el tick a media tanda (CLAUDE.md §3)—, y dejar caer al POST sin haber podido escribir la
> bitácora contradice el fail-closed de RETRY-D5. La supresión del POST queda como coste aceptado y
> acotado a un tick.
> Control negativo: contra el controlador anterior el resumen imprimía `probed=1` contra una suma de
> 2 (`absent=1` y `unknown=1` a la vez). El control positivo —cuando el que falla es el INSERT, el
> `reason` sigue siendo `write-failed`— pasa antes y después.

**File:** `src/controller/PortalOC_Creator.js:411-422`
**Issue:** El `try` abarca la sonda, la escritura de reconciliación **y** las cuatro llamadas de
bitácora, incluido el tramo `absent` de L407-410. El catch asume una sola causa:

```js
const failMsg = `[PORTAL-CHECK] PO ${po.external_id} … result=unknown … reason=write-failed`;
```

Dos consecuencias concretas:

1. **Diagnóstico falso.** Cualquier excepción que no sea el INSERT —un `getPurchaseOrderByExternalId`
   no-función por un require circular, un throw de `logGenerator`, o el TypeError de WR-01— se
   registra como «falló la escritura». En prod no hay SSMS ni depurador (HANDOFF §6): la bitácora es
   el único canal, y aquí miente sobre la etapa que falló.
2. **POST legítimo suprimido y contadores rotos.** Si la excepción ocurre en L409-410 (tramo
   `absent`), ya se hizo `probeAbsent++`; el catch hace `probeUnknown++` y `continue`. Resultado: una
   OC que el portal confirmó ausente **no** se crea ese tick, y el resumen imprime
   `probed=1 absent=1 unknown=1`, violando la invariante `probed === found+absent+skipped+unknown`
   que el comentario de L537-539 declara que «debe cumplirse siempre».

`logGenerator` sí puede lanzar: la ruta de respaldo de `LogGenerator.js:53-56` hace `fs.mkdirSync`
fuera de cualquier try. Y `console.log` sobre un stdout capturado por Servy puede dar EPIPE durante
la rotación de `servy-stdout.log`.

**Fix:** llevar una variable de etapa y acotar lo que el catch afirma:

```js
let stage = 'probe';
try {
    probed++;
    const probe = await getPurchaseOrderByExternalId(index, ocKey);
    if (!probe || probe.outcome !== 'absent') {
        // …
        if (localStatus) { stage = 'write'; await runQuery(sqlCheck, 'FESA'); }
        stage = 'log';
        // …
        continue;
    }
    probeAbsent++;
    stage = 'log-absent';
    // … logs del camino absent …
} catch (probeErr) {
    if (stage === 'log-absent') { probeAbsent--; }   // mantiene la invariante
    probeUnknown++;
    const reason = stage === 'write' ? 'write-failed' : `${stage}-failed`;
    // …
    continue;
}
```

Alternativa más limpia: sacar las llamadas de bitácora del `try` (son el tramo que no debe poder
cancelar una decisión ya tomada).

**Issue:** La compuerta entera depende de que la clave del Map y la lectura coincidan:

### WR-05: la sonda añade trabajo HTTP serial sin tope dentro del presupuesto de 5 min del paso

**File:** `src/controller/PortalOC_Creator.js:297-317`
**Issue:** El GET se emite dentro del bucle, secuencialmente, para **cada** OC con `errorCount > 0`
que sobreviva al post-filtro. No hay tope por tick. El paso está acotado por
`withStepTimeout(createPurchaseOrders(i), config.schedule.stepTimeoutMs, …)`
(`src/background.js:237`), y al vencer:

- `background.js:246` hace `throw stepErr`, que sube al try/catch por tenant y **salta los pasos
  restantes de ese tenant** en ese tick (`processOrderChanges`, `closePurchaseOrders`, …).
- La promesa original **no se cancela** (continuación fantasma, D-10 documentado en `background.js:88-90`):
  sigue iterando OCs, emitiendo GETs/POSTs e insertando filas mientras el resto del tick avanza, y
  potencialmente hasta dentro del siguiente tick.

Con el portal degradado (responde, pero al límite de los 30 s de axios) bastan ~10 OCs sondeadas
para consumir los 300 s completos. Con el portal sano el costo es pequeño, pero es aditivo sobre el
presupuesto de POST que ya existía, y el conjunto de OCs sondeables sólo crece mientras CR-02 y las
ramas de WR-04 sigan abiertas. La `Guarda 6` de `portal-check.test.js:248-254` razona sobre este
riesgo pero sólo fija que exista **un** call site — no acota cuántas veces se ejecuta.

**Fix:** un tope por tick, con el resto anotado para el siguiente:

```js
const MAX_PROBES_PER_TICK = 50;   // ~50 × 30 s worst case aún cabe si baja el timeout; ajustar con dato de prod
// …
if (priorErrors > 0 && probed < MAX_PROBES_PER_TICK) {
    // … bloque de la sonda …
} else if (priorErrors > 0) {
    probeDeferred++;
    continue;   // fail-closed: sin sondear no se postea
}
```

y añadir `deferred=` a la línea `[PORTAL-CHECK-SUMMARY]` para que el operador vea el rezago.

### IN-03: colisión de clave vacía en `errorCounts`

**File:** `src/controller/PortalOC_Creator.js:282`, `:306-307`
**Issue:** Cualquier fila con `EXTERNAL_ID` nulo o vacío se colapsa en la clave `''`, y una OC cuyo
`external_id` sea vacío leería ese conteo. Si además `priorErrors > 0`, la sonda se llama con `''`,
devuelve `{outcome:'unknown', reason:'empty-external-id'}` y la OC se salta **sin escribir fila
ERROR** — donde antes de la fase el camino de Joi sí dejaba rastro. Poco probable (`A.PONUMBER` no
es nulo en la práctica), pero el modo de falla es «desaparece en silencio».
**Fix:** saltar las filas sin clave al construir el Map:

```js
recordset.forEach((row) => {
    const key = String(row.EXTERNAL_ID || '').trim();
    if (!key) return;
    errorCounts.set(key, row.errorCount || 0);
});
```

### IN-04: el INSERT de reconciliación usa `po.external_id` en vez del `ocKey` ya normalizado

**File:** `src/controller/PortalOC_Creator.js:368`
**Issue:** La sonda y el Map usan `ocKey` (recortado en L306); el INSERT y las bitácoras interpolan

**Fix:** usar `ocKey` en el INSERT nuevo y en el mensaje `[OK] … reconciliada …`.
