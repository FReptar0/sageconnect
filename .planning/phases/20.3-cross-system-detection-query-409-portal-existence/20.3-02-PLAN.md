<objective>
Project `ef.errorCount AS errorCount` in the `PortalOC_Creator.js` SELECT list, and pin both halves of
RETRY-D3 with an alias-prefixed assertion pair in the existing `cron-where` suite.

Purpose: `PortalOC_Creator.js` joins the error-stats `OUTER APPLY` at L183 but its SELECT list (L52-156)
**never references `ef`** — `grep -n "ef\." src/controller/PortalOC_Creator.js` returns zero matches
today. So `row.errorCount` is `undefined` on every live row and the `[RETRY-DEFER]` line can only ever
print `attempts=0`. More importantly for this phase: without the projection, plan 20.3-03's
`errorCount > 0` gate would be permanently false and the portal probe would never fire. This is the
enabling change, and it is deliberately shipped on its own so a SQL-shape edit and a behaviour edit
never share a review pass.

Output: one new SELECT line, one comment, and three assertions. No behaviour change of any kind.

Decisions implemented (SPEC / CONTEXT traceability) — **RETRY-D3**: project `errorCount` and *only*
`errorCount`. **`ef.lastErrorAt` stays unprojected** — it is `MAX(lastUpdate)` over a column typed
`date`, so projecting it today would anchor every OC's last failure at 00:00 and produce a retry
deferral that is live roughly four hours a day. That is D-ITEM-03, deferred by Phase 20.2 and tied to
CR-04's `ALTER TABLE`; this phase does not reopen it. `errorCount` is `COUNT(*)`, entirely unaffected
by the date-granularity problem, and since 20.1 D-04 it feeds no timing math at all — it survives only
as the `attempts=` log field and, from plan 03 onward, as the probe gate. **CONTEXT D-07**: the
assertion pair belongs in `cron-where` because it is the one genuinely SQL-shaped assertion this phase
adds; every behavioural assertion goes in a separate suite so a behaviour change cannot break a
SQL-shape anchor and vice versa.
</objective>
