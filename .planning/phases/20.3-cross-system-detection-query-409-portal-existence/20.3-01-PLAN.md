<objective>
Create the portal existence probe: `src/utils/GetPurchaseOrders.js` exporting
`getPurchaseOrderByExternalId(index, externalId)`, plus its Jest suite. This is the **first portal GET
for purchase orders anywhere in `src/`** — every one of the twelve existing `purchase-orders` call
sites is a POST or PUT.

Purpose: `PortalOC_Creator.js` decides what to create from the local control table alone. When the
portal accepted an OC but the acknowledgement was lost, the local table stays all-`ERROR`, the cron
re-POSTs, the portal answers 409, another `ERROR` row is written, and the loop is self-sustaining
(3,313 accumulated `ERROR` rows in production, measured 2026-07-27). This helper is the missing second
opinion. Nothing consumes it yet — plan 20.3-03 wires it in.

Output: a pure request/parse helper with a three-outcome discriminated return contract, a 24-hex shape
guard on the portal-returned id, and 13 Jest cases pinning every branch plus the structural
constraints a runtime mock cannot prove.

Decisions implemented (CONTEXT traceability) — **D-03**: new file under `src/utils/`, mirroring
`GetProviders.js` structurally (module-scope tenant arrays, `urlBase(index)` builder, `PortalClient`
singleton, `PDPTenantKey`/`PDPTenantSecret` headers, exact-match `.trim()` re-filter, ambiguity guard).
**D-04**: the return contract deliberately deviates — `getProviderByExternalId` returns `null` at four
distinct sites (`GetProviders.js:65`, `:87`, `:93`, `:101`), conflating "absent" with "the request
threw"; RETRY-D2 forbids exactly that conflation, because misreading "portal unreachable" as "OC
absent" produces the duplicate POST this phase exists to prevent. **D-05**: the `^[0-9a-fA-F]{24}$`
guard lives here, not in the controller, so a malformed id structurally cannot reach a SQL string.
**D-08/D-09/D-10**: mirror `tests/utils/GetProviders.test.js`, mock `src/utils/PortalClient` (not
`axios`), `mockReset()` every shared mock in `beforeEach`.

// src/utils/GetPurchaseOrders.js
getPurchaseOrderByExternalId(index: number, externalId: string): Promise<ProbeResult>

// ProbeResult — a plain object with a string discriminant. No classes, no enum module, no Symbol.
{ outcome: 'found',   id: <24-hex string>, status: <trimmed portal status string> }
{ outcome: 'absent'   }                                  // no other keys
{ outcome: 'unknown', reason: <one of four constants> }

// The four `reason` constants — short, greppable, no sentences, no interpolation of portal data:
'empty-external-id'   // externalId was null/undefined/blank; NO HTTP request was issued
'ambiguous'           // 200, more than one exact external_id match
'invalid-id'          // 200, exactly one exact match, but its id failed ^[0-9a-fA-F]{24}$
'request-failed'      // the GET rejected: 4xx, 5xx, timeout, network error — ANY non-200

// Request shape (swagger-confirmed: pageSize and offset are REQUIRED query params)
GET ${config.portal.url}/api/1.0/extern/tenants/${tenantIds[index]}/purchase-orders
    ?external_ids=<encodeURIComponent(externalIdClean)>&pageSize=1&offset=0
Headers: { 'PDPTenantKey': apiKeys[index], 'PDPTenantSecret': apiSecrets[index] }
Options object carries HEADERS ONLY — no `timeout` key (PortalClient's 30s governs, CLAUDE.md §9).

// The four-value portal status enum (confirmed at three swagger schema sites):
OPEN | CANCELLED | GENERATED | CLOSED
The helper does NOT interpret status — it returns it trimmed and unmodified. Branch logic is the
controller's job (plan 20.3-03), because RETRY-D7 requires an unrecognised value to be handled
explicitly rather than normalised away.

// The id shape guard (RETRY-D8) — module-scope const, regex literal with NO `g` flag:
/^[0-9a-fA-F]{24}$/

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-20.3-01 | Tampering | `getPurchaseOrderByExternalId` return value → (plan 03) interpolated `INSERT INTO fesa.dbo.fesaOCFocaltec` | mitigate | `runQuery` (`src/utils/SQLServerConnection.js:51`) does `USE [${database}]; ${query}` with no `request.input()` anywhere, and changing that shared signature is the CLAUDE.md §6 #2 trap (PR #16 broke 7 callers). The defence therefore moves to the value: the trimmed portal `id` must match `^[0-9a-fA-F]{24}$` before it can be returned as `found`. A failing value becomes `{outcome:'unknown', reason:'invalid-id'}`, which plan 03 treats as fail-closed. Because the guard lives in the helper (CONTEXT D-05), **no controller code path exists in which a malformed id could reach a SQL string** — it is structural, not disciplinary. Pinned by six negative Jest cases (`"'; DROP TABLE--"`, `''`, `null`, 23-hex, 25-hex, 24-non-hex). |
| T-20.3-02 | Tampering | the same guard — what it does NOT cover | accept | The 24-hex regex is a **shape** guard, not an **authenticity** guard. A compromised or malfunctioning portal could return a syntactically perfect 24-hex id belonging to a different purchase order, and plan 03 would record it as this OC's `idFocaltec`. Residual risk accepted for three reasons: (1) the same portal already supplies `resp.data.id` to the existing POST-success INSERT at `PortalOC_Creator.js:330` with **no** validation at all, so this phase is a strict improvement over the status quo; (2) authenticity rests on TLS plus the `PDPTenantKey`/`PDPTenantSecret` pair, and on the client-side exact `external_id` re-filter, which requires the portal to have claimed the item *is* that OC; (3) the wrong-id blast radius is a mislinked control-table row for one OC, detectable because plan 03 tags every probe-written row with `responseAPI = 'PORTAL-CHECK'`. Severity: low. |
| T-20.3-03 | Spoofing / Information disclosure | credential placement on the outbound GET | mitigate | `PDPTenantKey` / `PDPTenantSecret` travel in headers only, never in the query string (query strings land in proxy and portal access logs).
