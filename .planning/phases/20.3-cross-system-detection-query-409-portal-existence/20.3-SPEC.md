# Phase 20.3: Cross-system detection query (409 / portal existence) — Specification

**Created:** 2026-07-28
**Ambiguity score:** 0.14 (gate: ≤ 0.20)
**Requirements:** 8 locked
**Milestone:** v2.4 — Retry policies · **Branch:** `feat/reintentos`

## Goal

Before the cron POSTs a purchase order that has already failed at least once, ask the Focaltec portal whether it already holds that OC by `external_id`; when it does, record the portal's `idFocaltec` in `fesa.dbo.fesaOCFocaltec` and skip the POST — so an OC whose creation succeeded at the portal but whose acknowledgement was lost stops being re-POSTed into a permanent 409 → `ERROR` loop.

## Background

**The deadlock.** `src/controller/PortalOC_Creator.js` decides what to create from the **local control table alone**. Its `NOT EXISTS` dedupe (L188-193, tightened to `status IN ('CLOSED','POSTED')` by RETRY-C7 in Phase 20.1) excludes an OC only when a `CLOSED` or `POSTED` row exists. An OC whose rows are all `ERROR` — or that has no row at all — is therefore re-selected on every tick inside the rolling 30-day scope. If the portal actually accepted that OC and only the ack was lost, the POST at L312 returns **409**, the `catch` at L347 INSERTs another `ERROR` row (L362-374), and the next tick repeats it. Nothing in the loop can ever break out, because nothing ever asks the portal.

Production shape of the problem, measured 2026-07-27 on `ZCL-SQL-01`: `fesaOCFocaltec` holds 9,032 rows — `CLOSED 4498` · **`ERROR 3313`** · `POSTED 1198` · `CANCELLED 18` · `OPEN 5`. Every failed attempt INSERTs a new row, so the 3,313 `ERROR` rows are the accumulated retry history, not 3,313 distinct OCs. The worked recovery for one such OC (PO0084361, COPDAT, 2026-06-30) is the lost-ack runbook: recover `idFocaltec` from the portal, seed a `POSTED` row, reopen, fix the total. This phase automates the detect-and-seed half of that runbook.

**Nothing to reuse.** The 2026-07-22 read-only review of `master` and of Fernanda's Dec-2025 branches confirmed there is **no portal GET for purchase orders anywhere in the codebase** — every existing OC call is a POST, PUT or status update. This phase adds the first one.

**The endpoint is confirmed, with no external dependency.** `.planning/codebase/swagger-spec-raw.json` documents two viable shapes:

| Shape | Existence signal | Notes |
|---|---|---|
| `GET .../purchase-orders?external_ids=<oc>&pageSize=1&offset=0` | `200` + `items`/`total` | `external_ids` is an **array** (batchable); `pageSize` and `offset` are **required** |
| `GET .../purchase-orders/<oc>?id_type=EXTERNAL` | `200` vs `404` | The shape the lost-ack runbook executed successfully against production |

Both take `PDPTenantKey` / `PDPTenantSecret` headers. The response item carries `id`, `external_id`, `status`, `number`, `total`, and **`status` is a four-value enum — `OPEN | CANCELLED | GENERATED | CLOSED`** — not the two values recorded in `20.1-RELEASE-STATUS.md` § BLOQUEOS 1, which this SPEC corrects.

**The PO retry interval is currently inert, and it changes this phase's cost model.** `PortalOC_Creator.js` joins the error-stats fragment at L183 (`OUTER APPLY … AS ef`) but its SELECT list (L52-156) **never projects `ef.errorCount` or `ef.lastErrorAt`** — the comment at L211 asserts a projection that does not exist. So `row.lastErrorAt` is `undefined` on every live row, `computeRetryEligibility` reads that as "never failed → eligible immediately" (a deliberate fail-open, `RetryPolicy.js:83`), and **every candidate OC is re-POSTed on every 15-minute tick** rather than every 240 minutes. This is D-ITEM-03, deferred during Phase 20.2 and tied to CR-04.

That deferral is only half-binding here. It rests on `lastErrorAt` being `MAX(lastUpdate)` where `lastUpdate` is typed `date`: projecting it today would anchor every OC's last failure at 00:00 and produce a deferral live only four hours a day. **`errorCount` is `COUNT(*)` and is entirely unaffected by that date-granularity problem**, and since Phase 20.1 D-04 it feeds no timing math at all — it survives only as the `attempts=` log field. This phase therefore projects `errorCount` **alone**, leaving `lastErrorAt` and CR-04 deferred exactly as 20.2 left them.

**Prior art for the client call.** `src/utils/GetProviders.js:58` `getProviderByExternalId()` is the established GET-by-external-id pattern: `PortalClient` singleton, headers from the tenant arrays, exact-match re-filter over the returned `items` rather than trusting the API filter, an ambiguity guard on >1 match, and `null` on miss. `ocSage` is `nchar` (space-padded) while the creator query emits `RTRIM(A.PONUMBER)`, so the same `.trim()`-both-sides discipline is load-bearing here.

## Requirements

1. **RETRY-D1 — Portal existence probe**: A reusable helper resolves whether the portal holds an OC for a given tenant and `external_id`.
   - Current: No portal GET for purchase orders exists anywhere in `src/`. The only OC-existence knowledge in the process comes from `fesa.dbo.fesaOCFocaltec`.
   - Target: A helper accepting a tenant index and an `ocSage` value issues `GET /api/1.0/extern/tenants/{tenantId}/purchase-orders?external_ids=<oc>&pageSize=1&offset=0` through the `PortalClient` singleton with `PDPTenantKey` / `PDPTenantSecret` headers, and returns a discriminated result covering *found* (carrying `id` and `status`), *not found*, and *undetermined*.
   - Acceptance: A Jest suite mocking `PortalClient.get` proves the helper returns **found** for a `200` whose `items` contain an exact `external_id` match, **not found** for a `200` with `items: []`, and **undetermined** for a rejected request — and that the request URL contains `external_ids=`, `pageSize=` and `offset=` and the two auth headers.

2. **RETRY-D2 — The list endpoint is the contract, per-OC**: Existence is read from a `200` response body, never from an HTTP error code, and one OC is probed per request.
   - Current: No probe exists, so no contract exists.
   - Target: The probe uses the list endpoint (`?external_ids=`) with a single id per call. A non-`200` outcome — 4xx, 5xx, timeout, network failure — is **never** interpretable as "the OC does not exist"; only a `200` carrying zero exact matches means that. The batched (`external_ids` array) and `id_type=EXTERNAL` shapes are rejected: the former puts a ~300-id URL near the 8 KB limit and makes one failure lose a whole tick, the latter buries the not-found-vs-unreachable distinction inside a `catch`.
   - Acceptance: A Jest case where `PortalClient.get` rejects with a 404-shaped error asserts the result is **undetermined**, not *not found*; grep confirms no call site passes more than one `external_ids` value, and that `id_type=` appears in no file on the purchase-order path (`src/utils/GetPurchaseOrders.js`, `src/controller/PortalOC_*.js`).
   - **Amended 2026-07-28** (pattern-mapper finding, verified): the original acceptance read "`id_type=EXTERNAL` appears nowhere in `src/`". That is unsatisfiable and always was — `src/scripts/payment-status-check.js:10` and `:78` already use `?id_type=EXTERNAL` against the **payments** endpoint, which this phase does not touch. The check is scoped to the purchase-order path instead. The requirement itself is unchanged; only its grep was over-broad.

3. **RETRY-D3 — `errorCount` projection (and only `errorCount`)**: The creator query surfaces the error count the `OUTER APPLY` already computes.
   - Current: `PortalOC_Creator.js` joins `OUTER APPLY … AS ef` (L183) but its SELECT list never references `ef`; `row.errorCount` is `undefined` on every live row and `[RETRY-DEFER]` can only ever print `attempts=0`.
   - Target: The SELECT list projects `ef.errorCount AS errorCount`. `ef.lastErrorAt` stays **unprojected** — it remains blocked on CR-04's `ALTER TABLE` exactly as Phase 20.2 D-ITEM-03 decided, and this phase does not reopen it.
   - Acceptance: The emitted SQL contains `ef.errorCount` and does **not** contain `ef.lastErrorAt`; a Jest assertion pins both halves. No retry-timing behaviour changes, proven by the existing `PortalOC_Creator.cron-where` suite passing unchanged.

4. **RETRY-D4 — The probe is gated on prior failure**: Only OCs that have already failed are probed.
   - Current: Every candidate row would be probed if the check were unconditional, on every 15-minute tick, because the inert interval defers nothing.
   - Target: The probe runs only when `errorCount > 0`. An OC with no prior `ERROR` row is POSTed exactly as today, with no portal GET issued. This is what makes RETRY-D5's fail-closed posture free: a first-time OC can never be delayed by it.
   - Acceptance: A Jest case with `errorCount: 0` asserts `PortalClient.get` was **not** called and the POST path ran; a case with `errorCount: 3` asserts the probe was called exactly once before any POST.

5. **RETRY-D5 — Fail-closed on an undetermined probe**: A probe that cannot answer blocks creation for that tick, without polluting the control table.
   - Current: Not applicable — no probe exists; every candidate proceeds straight to POST.
   - Target: An *undetermined* result skips the POST for that OC in that tick, writes **no** row to `fesa.dbo.fesaOCFocaltec` (neither `ERROR` nor `POSTED`), emits one log line, and lets the next tick re-evaluate. Writing an `ERROR` row is specifically forbidden: it would inflate `errorCount` for a portal-side fault and corrupt the operator's failure history.
   - Acceptance: A Jest case where the probe rejects asserts `portalClient.post` was not called **and** `runQuery` was not called with any `INSERT INTO fesa.dbo.fesaOCFocaltec`.

6. **RETRY-D6 — Reconciliation writes one new row, never an update**: A confirmed portal OC is recorded by insertion.
   - Current: An OC that exists at the portal but is all-`ERROR` locally stays all-`ERROR` forever; only the manual runbook can seed a `POSTED` row.
   - Target: A *found* result INSERTs one new row into `fesa.dbo.fesaOCFocaltec` carrying the portal's `idFocaltec`, following the exact column list and `GETDATE()` pattern of the three existing writes at L293/L332/L363. Pre-existing `ERROR` rows are left untouched — the same posture the runbook records (*"Old ERROR rows stay; harmless"*) — so the retry history survives and no `UPDATE` touches the 3,313 historical `ERROR` rows in a production table that has no staging and no rollback. One inserted row is sufficient and permanent: the RETRY-C7 dedupe already reads `status IN ('CLOSED','POSTED')`.
   - Acceptance: A Jest case asserts the emitted SQL is an `INSERT INTO fesa.dbo.fesaOCFocaltec` containing the portal `id`, and that no `UPDATE fesa.dbo.fesaOCFocaltec` is emitted anywhere in the new code path.

7. **RETRY-D7 — All four portal statuses are handled explicitly**: No branch treats an unrecognised status as "does not exist".
   - Current: Not applicable — nothing in `src/` reads a portal OC status on the creation path.
   - Target: The *found* branch resolves as follows, with no fallthrough:

     | Portal `status` | POST | Row written |
     |---|---|---|
     | `OPEN`, `GENERATED` | skipped | `INSERT … 'POSTED'` + `idFocaltec` |
     | `CLOSED` | skipped | `INSERT … 'CLOSED'` + `idFocaltec` |
     | `CANCELLED` | skipped | **none** — logged; closed properly by CR-02, which is out of scope here |
     | unrecognised value | skipped | **none** — logged at `warn` |
     | >1 exact match | skipped | **none** — logged at `warn` (the `getProviderByExternalId` ambiguity guard) |

   - Acceptance: A Jest case per row of that table asserts the POST/write outcome. A case with a status string absent from the enum asserts the POST was **not** issued — an unknown status must never fall through to creation.

8. **RETRY-D8 — The portal `idFocaltec` is shape-guarded before it reaches SQL**: Externally-sourced data cannot enter an interpolated INSERT unvalidated.
   - Current: All three existing INSERTs interpolate directly (`'${po.external_id}'`), but every interpolated value is either a controlled tenant value or Sage-sourced. `runQuery(query, database)` (`src/utils/SQLServerConnection.js:51`) accepts **no parameters**, so parameterisation would require changing a shared util used across the codebase — the exact signature change CLAUDE.md §6 pitfall #2 records (PR #16 broke 7 callers).
   - Target: The `idFocaltec` returned by the portal is rejected unless it matches `^[0-9a-fA-F]{24}$` (the 24-hex id the lost-ack runbook documents). A value failing the guard is treated as *undetermined* per RETRY-D5 — POST skipped, nothing written, logged. `runQuery`'s signature is **not** changed.
   - Acceptance: Jest cases feeding `"'; DROP TABLE--"`, `""`, `null`, a 23-char and a 25-char hex string each assert no SQL is emitted and the OC is skipped; a valid 24-hex id asserts the INSERT proceeds.

## Boundaries

**In scope:**
- A portal existence-probe helper for purchase orders (the first OC GET in the codebase), built on the `PortalClient` singleton.
- `ef.errorCount` projected in the `PortalOC_Creator.js` SELECT list.
- The probe wired into `createPurchaseOrders()`, gated on `errorCount > 0`, ahead of the existing POST.
- Reconciliation INSERT (`POSTED` / `CLOSED` + `idFocaltec`) for confirmed portal OCs.
- Explicit handling of all four portal status values, the unknown-status case, and the ambiguous-match case.
- Fail-closed handling of an undetermined probe, writing nothing.
- A 24-hex shape guard on the portal-returned `idFocaltec`.
- Jest coverage for every branch above.

**Out of scope:**
- **`ef.lastErrorAt` projection and the PO retry interval (D-ITEM-03 / CR-04)** — `lastUpdate` is typed `date`, so projecting it produces a deferral live only 4 h/day; it needs the `ALTER TABLE` and must land together with CR-04, per the Phase 20.2 decision. The interval stays inert after this phase.
- **CR-02 (`CANCELLED` added to the `NOT EXISTS` dedupe IN-list)** — a separate one-line SQL change; this phase only stops those 18 rows from being POSTed, it does not stop them from being re-selected.
- **Q3 (consolidated per-batch failure email)** — separate deliverable of the same August release; this phase emits log lines only, no email.
- **CR-03 (payment error recording)** — payments have no `ERROR` rows and no column to hold an error; unrelated to OC existence.
- **Any portal GET for payments** — the deadlock being fixed is OC-specific.
- **Schema changes of any kind** — no `ALTER TABLE`, no new column, no new status value in the control table's vocabulary.
- **Changing `runQuery`'s signature to accept parameters** — shared-util blast radius (CLAUDE.md §6 #2); RETRY-D8 solves the injection concern at the value instead.
- **`po-cron-diagnostic.js` reporting portal state** — it is a read-only diagnostic; giving it a portal call is a separate concern. Note it already carries a known drift logged in `.planning/phases/20.1-retry-policy-correction/deferred-items.md`.
- **The RYASA exclusion, the rolling 30-day scope, and the RETRY-C7 dedupe** — all unchanged; this phase adds a decision point inside the loop, it does not touch what the query selects.
- **Retroactive reconciliation of the existing backlog** — the probe heals an OC the next time the cron reaches it; no one-shot sweep over the 3,313 historical `ERROR` rows is built here.

## Constraints

- **Always-on (CLAUDE.md §3):** no module-scope cache, timer, listener or accumulating structure whose lifetime is not bounded. The probe must be a per-call operation retaining nothing between ticks.
- **Defense-in-depth invariant (CLAUDE.md §9):** `axios (30s) < step (5m) < child (10m) < lock (14m)` must hold unchanged. The probe reuses the `PortalClient` singleton so its 30 s timeout applies automatically; it must not set its own timeout, and must not introduce internal retry loops — a retry inside the probe would multiply the per-OC HTTP budget against the 5-minute step ceiling.
- **HTTP budget:** the probe adds at most one GET per already-failed candidate per tick, sequential within the existing per-OC loop. The `errorCount > 0` gate is what bounds this; without it the probe would run over the entire candidate set every 15 minutes.
- **No new SQL interpolation of untrusted data (CLAUDE.md §6 #1):** satisfied via RETRY-D8's shape guard, not via a `runQuery` signature change.
- **`nchar` padding:** `ocSage` is space-padded `nchar` and the creator query emits `RTRIM(A.PONUMBER)`; exact-match comparison must `.trim()` both sides, as `getProviderByExternalId` does.
- **No local Sage DB and no staging (HANDOFF §6):** verification is structural (grep/SQL-shape assertions) plus Jest with mocked `PortalClient` and `runQuery`. Live confirmation is deferred to post-deploy on `ZCL-RDS-02`.
- **Test baseline:** `npm test` must end at the CLAUDE.md §6 baseline — 6 failed suites / 7 failed tests of ~485 (`PaymentReconciliation`, `TransformTime`, `no-process-exit`, `enforcement-wiring`, plus the `config` / `operation-manager` worker crashes). Any new failure is a regression.
- **Inherited by the operator script:** `retry-month-pos.js --apply` calls `createPurchaseOrders()`, so it acquires this behaviour automatically. Its dry-run preview mirrors the cron WHERE and is unaffected, because the probe lives in the JS loop, not the query.
- **Release coupling:** ships in the single "todo-junto" August deploy (item #5 of `20.1-RELEASE-STATUS.md`), targeted after the first week of August 2026. Deploy gates: lead OK + notify Memo + outside the month-close window.

## Acceptance Criteria

- [ ] A portal existence probe for purchase orders exists in `src/` and issues `GET .../purchase-orders?external_ids=…&pageSize=…&offset=…` with `PDPTenantKey` and `PDPTenantSecret` headers via the `PortalClient` singleton.
- [ ] The probe returns three distinguishable outcomes — found / not found / undetermined — and a non-`200` outcome never yields *not found*.
- [ ] `PortalOC_Creator.js` projects `ef.errorCount` and does **not** project `ef.lastErrorAt`.
- [ ] An OC with `errorCount === 0` is POSTed with no portal GET issued.
- [ ] An OC with `errorCount > 0` is probed exactly once before the POST decision.
- [ ] A *found* result with status `OPEN` or `GENERATED` skips the POST and INSERTs one `POSTED` row carrying the portal `idFocaltec`.
- [ ] A *found* result with status `CLOSED` skips the POST and INSERTs one `CLOSED` row carrying the portal `idFocaltec`.
- [ ] A *found* result with status `CANCELLED`, an unrecognised status, or >1 exact match skips the POST and writes no row.
- [ ] A *not found* result POSTs exactly as the pre-phase code did.
- [ ] An *undetermined* result skips the POST and emits no `INSERT INTO fesa.dbo.fesaOCFocaltec`.
- [ ] An `idFocaltec` not matching `^[0-9a-fA-F]{24}$` never reaches a SQL string; the OC is skipped instead.
- [ ] No `UPDATE fesa.dbo.fesaOCFocaltec` statement is emitted by any new code path.
- [ ] `runQuery`'s signature in `src/utils/SQLServerConnection.js` is unchanged.
- [ ] No `setInterval`, `setTimeout`, module-scope `Map`/`Set`, or EventEmitter listener is added.
- [ ] The probe sets no axios timeout of its own and contains no internal retry loop.
- [ ] `npm test` reports the CLAUDE.md §6 baseline with no NEW failing suites or tests.
