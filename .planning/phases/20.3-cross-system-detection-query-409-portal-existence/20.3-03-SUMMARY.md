**El cron dejó de reenviar a ciegas: cuando una OC ya falló al menos una vez le pregunta al portal antes de volver a hacer POST, y si el portal contesta que ya la tiene, siembra la fila de reconciliación con el idFocaltec real en vez de fabricar otro ERROR — el bucle 409 que se sostenía solo queda cortado, con fail-closed estructural en el que llegar al POST exige acertar `absent` y no fallar una lista.**

**Línea por fila probada** (`PortalOC_Creator.js:395`), plantilla literal:

```
[PORTAL-CHECK] PO ${po.external_id} tenant=${databases[index]} result=${result} id=${idField} status=${statusField} reason=${reason}
```

Ejemplo materializado: `[PORTAL-CHECK] PO PO0084361 tenant=COPDAT result=found id=6650c1f2a4b8e91d3c7f0a12 status=OPEN reason=n/a`

| Campo | Regla exacta enviada |
|---|---|
| `PO ` | posicional pelado, `po.external_id` (nunca `po=<id>`) — mismo estilo que `[RETRY-DEFER] PO …` |
| `tenant=` | `databases[index]` |
| `result=` | uno de cinco: `found` \| `absent` \| `cancelled` \| `unknown` \| `ambiguous` |
| `id=` | `probe.id` siempre que `probe.outcome === 'found'` (con cualquier status), si no el literal `n/a` |
| `status=` | el status saneado siempre que `probe.outcome === 'found'`, si no el literal `n/a` |
| `reason=` | `probe.reason` cuando el outcome es `unknown`; el literal `unrecognised-status` para found con status fuera del enum; el literal `unrecognised-outcome` para un objeto malformado sin `reason`; el literal `write-failed` cuando el INSERT lanzó; si no el literal `n/a` |

Saneador del status, expresión en línea (no constante de módulo), `PortalOC_Creator.js:393`:

```js
String(probe.status == null ? '' : probe.status).replace(/[^A-Za-z0-9_-]/g, '').slice(0, 32) || 'n/a'
```

**Línea de resumen por tick** (`PortalOC_Creator.js:428`):

```
[PORTAL-CHECK-SUMMARY] tenant=${databases[index]} probed=${probed} found=${probeFound} absent=${probeAbsent} skipped=${probeSkipped} unknown=${probeUnknown}
```

Ejemplo materializado: `[PORTAL-CHECK-SUMMARY] tenant=COPDAT probed=7 found=3 absent=2 skipped=1 unknown=1`

Recomendación de anclaje para el plan 20.3-04, siguiendo cómo el repo ya lo divide (PATTERNS Q5): **anclar con `$` solo `[PORTAL-CHECK-SUMMARY]`**, cuyo juego de campos es fijo y completo, igual que `[RETRY]` y `[RETRY-CLOCK]`; dejar `[PORTAL-CHECK]` con la cola abierta después de `result=<valor>`, igual que `[RETRY-DEFER]`. Nótese que `^\[PORTAL-CHECK\]` no colisiona con la de resumen gracias al `\]`.

Niveles: `info` para `found` / `absent` / `cancelled`; `warn` para `unknown` / `ambiguous`. Minúsculas (niveles de winston). Cada línea empareja `console.log`/`console.warn` con `logGenerator(logFileName, level, msg)` (S-2).

## Semántica exacta de los contadores (para la aserción de resumen del plan 04)

```
probed === found + absent + skipped + unknown
```

| Resultado de la sonda | `result=` | contador que sube | POST | fila escrita |
|---|---|---|---|---|
| found + `OPEN` | `found` | `probeFound` | omitido | INSERT `'POSTED'` + id |
| found + `GENERATED` | `found` | `probeFound` | omitido | INSERT `'POSTED'` + id |
| found + `CLOSED` | `found` | `probeFound` | omitido | INSERT `'CLOSED'` + id |
| found + `CANCELLED` | `cancelled` | `probeSkipped` | omitido | ninguna |
| found + cualquier otro status | `unknown` | `probeUnknown` | omitido | ninguna |
| unknown + reason `ambiguous` | `ambiguous` | `probeUnknown` | omitido | ninguna |
| unknown + cualquier otro reason | `unknown` | `probeUnknown` | omitido | ninguna |
| probe `undefined` / `null` / outcome no reconocido | `unknown` | `probeUnknown` | omitido | ninguna |
| el INSERT de reconciliación lanzó | `unknown` | `probeUnknown` | omitido | ninguna (fail-closed) |
| **absent** | `absent` | `probeAbsent` | **PROCEDE** | como hoy (POSTED o ERROR) |
| compuerta cerrada (`errorCount === 0`) | — | **ninguno** | PROCEDE | como hoy |

Dos detalles que importan para escribir la aserción:

1. **La compuerta cerrada no incrementa `probed` ni emite línea alguna.** Una OC que nunca falló no produce ninguna salida de sonda: ni `[PORTAL-CHECK]`, ni contador, ni GET.
2. **Los incrementos van DESPUÉS de la escritura de reconciliación.** Si `runQuery` lanza, el `catch` cuenta `probeUnknown` y ninguna otra rama había contado todavía, así que la invariante también se sostiene en el camino de fallo. (El único modo teórico de romperla sería que `logGenerator` o `console.*` lanzaran *después* de un incremento; hoy ese mismo evento mataría el tick de plano en los tres sitios preexistentes, que llaman a `logGenerator` sin protección alguna. Dentro del bloque nuevo es estrictamente más seguro que el statu quo.)

## ¿Se omite `[PORTAL-CHECK-SUMMARY]` con `probed === 0`?

**Sí.** Es el punto que CONTEXT dejaba a discreción y se resolvió por omitirlo: el tick sin ninguna OC ya fallida es el abrumadoramente común, y una línea de ceros por tick cada 15 minutos vuelve ilegible la bitácora que el operador necesita leer. Es el mismo instinto de `[EOM-SKIP]` ("no digas nada cuando no pasó nada"); `[RETRY]` hace lo contrario y ambas posturas eran defendibles, así que quedó elegida y ahora está documentada.

**1. [Regla 2 - Funcionalidad crítica faltante] Línea de detalle del error en el `catch` de la sonda**

- **Found during:** Task 1, al escribir el bloque `catch (probeErr)`.
- **Issue:** El plan especifica que el `catch` registre a nivel `warn` con `result=unknown` y `reason=write-failed`. Pero el juego de campos de `[PORTAL-CHECK]` es fijo y no tiene hueco para el mensaje del error, así que un operador que viera `reason=write-failed` en la bitácora se quedaría con cero información diagnóstica sobre por qué falló la escritura — y las bitácoras de winston son el rastro de auditoría que sobrevive al reinicio (CLAUDE.md §5). Usa el prefijo `[ERROR]` que este archivo ya emplea, así que **no** añade una etiqueta nueva y la Guarda 9 sigue verde.
