# Phase 20.3: Cross-system detection query (409 / portal existence) Verification Report

**Phase Goal:** Stop the cron from re-POSTing a purchase order the portal already has. Add a portal
existence check by `external_id` before recreation, and reconcile the control table from the answer,
so an OC whose creation succeeded at the portal but whose acknowledgement was lost stops feeding a
permanent 409 → `ERROR` deadlock.

## Gaps Summary

No must-have truth failed. All 6 ROADMAP Success Criteria, all 8 RETRY-D requirements, and all 16 SPEC
acceptance checkboxes are backed by direct code evidence that I traced myself — source reads, greps,
an independently-run `npm test`, and an independent extraction of the swagger contract — not by
trusting SUMMARY.md's or REVIEW.md's narrative.

Three things keep this phase out of a clean `passed`:

1. **Human verification is required** for production-only checks (the log projection reaching real data,
   the summary-line invariant against a real portal, and the first-tick step-duration risk). These are
   correctly out of reach of static/Jest verification per HANDOFF §6 (no local Sage DB, no staging) and
   are not gaps — they are the deploy-time checks the phase's own SUMMARYs already flagged.

2. **A code review ran after execution and found 1 critical + 6 warnings + 4 info findings.** Three were
   fixed under explicit user instruction (CR-01, WR-01, WR-02), and I independently confirmed all three
   fixes are genuinely present in the code (not just claimed): `GetPurchaseOrders.js` now returns
   `{outcome:'unknown', reason:'malformed-response'}` for an unusable 200 body instead of silently
   defaulting to `absent`; the helper's `catch` no longer repeats the operation that could have thrown;
   and the controller's `catch` now names the failing stage and preserves the `probed === found+absent+skipped+unknown`
   invariant even when the reconciliation write itself fails. The remaining 8 findings (WR-03 through
   WR-06, IN-01 through IN-04) are open by explicit user scoping, not silently missed — I verified each
   one is genuinely still present in the current code, and elevated **WR-03** for particular attention:
   the exact key-correspondence that opens the probe gate (the mechanism the entire phase depends on) is
   provably correct today by direct trace of the two shared utilities it passes through, but is never
   exercised by any test using those real utilities — both test suites replace them with tautological
   stand-ins. This means a future, unrelated change to `OC_GroupOrdersByNumber.js` or
   `parseExternPurchaseOrders.js` could silently disable the entire phase (reopening the exact 409
   deadlock it exists to close) with all 77 phase tests staying green.

3. **The CR-01 fix added a fifth `reason` constant (`malformed-response`)** beyond the four the locked
   SPEC/CONTEXT enumerate. I judge this consistent with, not a deviation from, RETRY-D1/D2's intent: the
   locked requirement is that a non-200 (and, per REVIEW's finding, an unusable 200 body) must never be
   misread as "the OC does not exist" — the fifth reason is a more precise implementation of that same
   rule, not a new category of behavior outside it. No locked acceptance criterion pins an exact count
   of four reason strings. Noted here for visibility since SPEC.md and CONTEXT.md were not retroactively
   edited to mention it (a normal, accepted practice for frozen planning artifacts — the reconciliation
   lives in REVIEW.md and STATE.md instead).

None of the above falsifies the phase's goal. The mechanism that stops the re-POST/409/ERROR deadlock is
real, wired, and tested with unusually rigorous negative-control-mutation discipline (three separate
occasions in this phase where a reviewer or planner required proving a guard actually detects the
regression it claims to catch, not just that it exists). The gaps that remain are genuine but
non-blocking: production-only checks, and known, explicitly-scoped technical debt.
