<objective>
Bound every SMTP send by `MAIL_TIMEOUT_MS` at both `EmailSender` call sites, and prove it against a real socket that never answers.

Purpose: Q3-06. `src/utils/EmailSender.js` sets no timeouts at all today. Nodemailer's `socketTimeout` default is **600 000 ms** — twice `STEP_TIMEOUT_MS` and equal to `CHILD_PROCESS_TIMEOUT_MS`. The month-close path already sits inside a `withStepTimeout` wrapper, so the step aborts at five minutes, but the abandoned promise keeps running — the phantom-continuation shape recorded at `src/background.js:88-90`. Phase 20.5 adds a second SMTP call site inside a cron step and a third dispatch path, which turns an unbounded send from a latent hazard into a live one.

Output: three nodemailer timeout options on both `transportConfig` objects, sourced from `config.notifications.mailTimeoutMs`, plus a mocked-wiring test and a real-socket behavioural test.

## The one design decision this plan makes, and why

`src/utils/EmailSender.js` is loaded by suites whose `jest.mock('../src/config', ...)` factories predate this phase and therefore have no `notifications` key. A bare `config.notifications.mailTimeoutMs` at module scope would throw `Cannot read properties of undefined` in every one of them and manufacture new failures against the CLAUDE.md §6 baseline — which is the one thing this milestone does not tolerate.

The resolution is a **single module-level accessor read at send time**, not at module load, with an explicit integer check and the documented default as its only fallback. Three properties make that safe rather than fail-open:

1. It is unreachable in production. Plan 01's guards exit 1 unless `config.notifications.mailTimeoutMs` is an integer at or above 1000 and strictly below `STEP_TIMEOUT_MS`, so the process cannot start with the key missing or non-integer. The fallback branch exists for legacy test mocks only, and the comment must say exactly that.
2. It cannot drift silently. Task 2 asserts that a mock supplying `mailTimeoutMs: 7777` produces `socketTimeout: 7777` on the object handed to `createTransport`. If a future edit hardcodes the constant instead of reading config, that assertion fails.
3. It is read per send, not per module load, so a test can change the mock between cases without resetting modules.

Do NOT "simplify" this to a module-scope `const` initialised at require time. That would freeze the value at load, which is both harder to test and a silent divergence from every other config read in this codebase.
</objective>
