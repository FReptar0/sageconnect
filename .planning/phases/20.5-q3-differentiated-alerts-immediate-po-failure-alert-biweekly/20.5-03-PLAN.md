<objective>
Add the biweekly gate predicate and its period helper to `src/utils/EomNotification.js`, and give `buildEomEmailHtml` a second variant for the immediate PO alert — without moving a single byte of the month-close path.

Purpose: Q3-03 (the day-1/day-16 gate) and Q3-05 (the month-close email retained byte-for-byte). This plan is pure library work with no dispatch and no I/O beyond the sentinel `existsSync` that `shouldDispatchEom` already does, which is what lets both plan 04 (the PO alert) and plan 05 (the dispatcher) build on it in wave 3 without touching each other's files.

Output: `paymentPeriodOf(date)`, `shouldDispatchPaymentReport(now, sentinelPath, reportConfig)`, a third `variant` parameter on `buildEomEmailHtml`, all three exported, and their tests.

## D-07 is the decision this plan exists to make un-revertible

The gate fires **on the first tick at or after the period start**, not only on day 1 or day 16 exactly. If the service is down, restarting or licence-blocked on the 16th, the report must still go out on the 17th, the 20th or the 28th. The literal reading of "days 1 and 16" produces a report that silently never goes out for that period, and nothing anywhere would say so.

This is also why the predicate follows `shouldDispatchEom`'s shape rather than inventing one: calendar condition, then hour, then sentinel absent, with the kill-switch short-circuiting first. The sentinel is what makes "at or after" idempotent — the report goes out once per period no matter how many ticks land inside it. Task 2 pins the day-20 case explicitly, so a later "correction" to `day === 1 || day === 16` turns the suite red.

## Conflict found during planning — read before Task 1

D-12 lists `buildEomEmailHtml` among the assets this phase reuses, and the SPEC's Q3-01 requires the immediate PO alert to list "each failed PO with its PO number, tenant, and the portal's error text" — which is exactly the six-column shape the `pos` branch already renders. But the function's heading is hardcoded to `SageConnect: Pendientes fin de mes — ${monthLabel}`, its intro says "al cierre del mes", and its fourth column header reads "Fecha autorización". An immediate alert carrying a month-close heading would mislead the operator on the one email that is supposed to be urgent.

Three resolutions exist and only one is correct:

- **Reuse the function unchanged.** Rejected. The operator receives an email titled "Pendientes fin de mes" on the 3rd of the month. That is a defect, not a tradeoff.
- **Build separate HTML inside the controller.** Rejected. It duplicates `escapeHtml`, the truncation rule and the table markup in a file that has no business owning them, and it puts the T-20-14 HTML-injection defence in two places where only one is tested.
- **Add an optional third parameter `variant`, defaulting to `'eom'`.** Adopted. The default path is byte-identical, so `tests/fixtures/eom-email-sample.html` still matches and every Q3-05 assertion passes unchanged. Only `variant === 'po-alert'` changes the heading, the intro sentence and one column header. The column COUNT does not change, so the D-11 rule that "el encabezado y el cuerpo DEBEN ramificar juntos" is not violated — that rule is about six headers over five cells, and both variants here are six over six.

**`paymentPeriodOf(date)`** — returns `1` when `date.getDate() <= 15`, otherwise `2`. Returns `null` for anything that is not a valid `Date`, mirroring the fail-closed posture of the module. JSDoc states D-06: the periods are natural, 1 to 15 and 16 to the end of the month, whatever that end happens to be. **`shouldDispatchPaymentReport(now, sentinelPath, reportConfig)`** — same argument order, same injection pattern and the same fail-closed ordering as `shouldDispatchEom`, so the two can be read as a pair:

  1. `reportConfig` missing or not an object -> `false`
  2. `!reportConfig.enabled` -> `false`   (short-circuit kill-switch, Q3-04)
  3. `now` not a valid `Date` -> `false`
  4. `sentinelPath` not a non-empty string -> `false`
  5. `now.getHours() < reportConfig.hour` -> `false`
  6. `fs.existsSync(sentinelPath)` -> `false`
  7. otherwise `true`

There is deliberately **no** step that checks the day. That absence IS D-07 and the JSDoc must say so in those words: the period is carried by the sentinel PATH, which the caller builds from `paymentPeriodOf(now)`, so the predicate is true on the first tick at or after the period start and false on every tick after the sentinel lands. A `day === 1 || day === 16` term here would mean that a service down on the 16th loses that period's report permanently and silently. The sentinel makes "at or after" idempotent without needing an exact-day term at all.

Note in the JSDoc that the kill-switch read is `reportConfig.enabled` and not `reportConfig.notificationEnabled`: the two namespaces have deliberately different key names because they are independent switches (D-09, Q3-04), and reusing the EOM key name here would invite a later merge of the two namespaces.

Update `module.exports` to `{ shouldDispatchEom, shouldDispatchPaymentReport, paymentPeriodOf, buildEomEmailHtml, writeSentinelAtomically, readSentinelPayload }`. Do not reorder the existing four; append.

Do not add any timer, listener, module-scope `Map`/`Set` or cache. Both functions are pure apart from the one `fs.existsSync`, which is the same call `shouldDispatchEom` already makes and which retains nothing (CLAUDE.md §3).
