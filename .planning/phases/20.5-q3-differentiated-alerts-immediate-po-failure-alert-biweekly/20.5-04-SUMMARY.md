# Phase 20.5 Plan 04: The immediate PO failure alert — Summary

One operator email per tick lists the POs that failed their **first** upload attempt, the state that says "already alerted" is derived from a Map Phase 20.3 already built rather than stored anywhere, and nine identifier-anchored guards make both decisions fail loudly if reverted.

## What shipped

**Q3-01 — the alert exists and it is one email.** A function-scoped `poAlerts` array joins the 20.4 tick counters. Both failure sites — the Joi rejection and the portal POST rejection — append synchronously; neither touches the network. A single `await sendOperatorReport` sits after the `[PORTAL-CHECK-SUMMARY]` block, outside the loop. Cost: exactly one SMTP round-trip per tick regardless of how many POs failed. `DEVIATIONS.md`'s proposal to fire from the `catch` would have produced N emails and N round-trips inside the very step budget Phase 20.4 exists to protect.

**Q3-02 / D-03 — nothing is stored.** The alert fires when the PO's **prior** `errorCount` is `0`, read from the `errorCounts` Map the 20.3 wiring already builds from the same SELECT. No sentinel file, no module-scope collection, no new query, no schema change. Guarda 4 forbids `writeFileSync` / `existsSync` / `readFileSync` / `writeSentinelAtomically` in the controller so the two rejected designs stay rejected; Guarda 5 pins the declaration between the function opening and the loop head.

**D-04 — the 3,313-row backlog is proven silent, not argued silent.** Every PO behind those accumulated `ERROR` rows arrives at the first tick after deploy with `errorCount > 0`. A named case drives fixtures at `errorCount: 1` and `errorCount: 7`, asserts both actually reach and fail the POST, and asserts zero sends — so the silence is attributable to the derived condition and not to a path that stopped short before failing.

**Q3-04 — the off switch, read once.** `config.notifications.poAlert.enabled` appears exactly once in the controller, at the send site, after the summary. When it is off and POs failed, the tick still logs `sent=false reason=disabled`: a silenced alert that leaves no trace is indistinguishable from a broken one.

**The mock-fidelity hazard the plan flagged was real, and larger than stated.** All three pre-existing controller suites run the real `createPurchaseOrders`. Without `EmailSender` mocked they would have attempted outbound SMTP against a fabricated host; without `notifications` in their config factories the switch would have read `undefined` and silently disabled the alert across ~90 cases — the same fail-open shape Phase 20.4 had to close in two of these same mocks. Both edits landed in all three, in the same commit that introduced the feature, so no intermediate commit left a red or network-touching suite on a production-bound branch. `regression-verification.test.js` was checked and only smoke-tests `require()`, so it is not exposed; no fourth suite has the exposure.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — Missing critical functionality] The send IS wrapped in try/catch. The plan's prose forbade it; the plan's own acceptance criterion required it.**

- **Found during:** Task 2, case "resiliencia: aunque el envío RECHACE".
- **Issue:** Edit 5 of Task 1 says "Do not wrap the send in a `try`/`catch` … Say so in the comment." Task 2's acceptance criteria say "a case in which `sendOperatorReport` rejects still sees `createPurchaseOrders` resolve." Implemented literally, the first makes the second impossible: with no catch the rejection propagates and `createPurchaseOrders` rejects. Measured directly — the case failed with `Rejected to value: [Error: smtp caido]`.
- **Fix:** a `try`/`catch` around the subject/HTML/send block, logging `[PO-ALERT] … sent=false reason=error` at `warn`. The plan itself supplies the decision rule for this exact outcome: *"if it fails, the send needs a catch after all and this plan's reasoning was wrong."*
- **Why this is right on the merits, not just procedurally:** the catch is **not** about SMTP. `sendOperatorReport` already swallows mail failures and logs at `warn` (`EmailSender.js`), and that remains the mechanism by which a dead mail server degrades notifications and nothing else — the plan's premise there was verified and holds. The catch exists because the **whole notification path** runs at that point: `buildEomEmailHtml`, the subject build, and the send. `createPurchaseOrders` runs inside `withStepTimeout` inside `forResponse`, so any throw there fails the tenant's entire step **after** the control-table `INSERT`s have already committed — trading the tick for an email. Nothing is lost silently either: a PO alerted once and never resolved still appears in the month-close consolidated email (Q3-05), which is the backstop that makes single-alert semantics safe (D-05).
- **Guarded against the plan's stated worry:** the comment states in capitals that this catch must **never** rethrow, and says why — rethrowing is the single change that would put the tick back at the mercy of the notification path.
- **Files modified:** `src/controller/PortalOC_Creator.js`
- **Commit:** `d69c2cb`

**2. [Rule 3 — Blocking] The dispatch guard is NESTED, not the conjunction the plan wrote.**

- **Found during:** Task 1, Edit 5.
- **Issue:** three of the plan's requirements are jointly unsatisfiable in the flat form. Edit 5 specifies `if (config.notifications.poAlert.enabled && poAlerts.length > 0)`; it also requires the `sent=false reason=disabled` line to fire only "when the switch is off **but** `poAlerts.length > 0`"; and Task 3's Guarda 8 requires `config.notifications.poAlert.enabled` to appear **exactly once**. A flat conjunction with an `else` logs `pos=0 sent=false` on every clean tick; a flat conjunction with a second guarded branch reads the switch twice.
- **Fix:** `if (poAlertCount > 0) { if (config.notifications.poAlert.enabled) { … } else { … } }`. Semantically identical to the conjunction for the send, satisfies the disabled-branch condition exactly, and reads the switch once. The reason is written into the comment.
- **Files modified:** `src/controller/PortalOC_Creator.js`
- **Commit:** `3f4c861`

**3. [Rule 1 — Bug] My own comment tripped Guarda 9 of the 20.3 suite by naming the forbidden tag.**

- **Issue:** the comment explaining *why* the tag must not be renamed wrote the forbidden sibling tag literally, between brackets. Guarda 9 reads the whole source, comments included, and `portal-check` plus `probe-budget` both went red.
- **Fix:** tag names are now written in prose without brackets, and the comment says explicitly that no comment in this file may bracket a tag name because the guards count literal occurrences over the entire source. This is now a file convention, not a one-off dodge.

### Cross-agent incident (resolved, no work lost)

**4. [Rule 3 — Blocking] My first commit swept in the sibling agent's in-progress `src/background.js`.**

- **Found during:** post-commit verification of Task 1 (`git diff-tree` on `HEAD`).
- **Issue:** plans 20.5-04 and 20.5-05 ran concurrently on the **same working tree and the same index**. I staged my four files explicitly and `git diff --cached --name-only` confirmed only those four — but between that `git add` and the `git commit`, the sibling staged `src/background.js`. `git commit` without a pathspec commits the whole index, so 135 lines of the sibling's uncommitted work landed in my commit `7cd91db`.
- **Fix:** `git reset --soft HEAD~1` → `git restore --staged src/background.js` → re-commit. Both operations are index-only; the working tree was never touched. Executed as a single shell invocation guarded by `[ "$(git rev-parse HEAD)" = 7cd91db ]`, so a sibling commit landing in the window would have aborted the repair rather than rewinding the sibling's commit. `src/background.js` was verified byte-identical (SHA-256) before and after, and returned to the sibling as an unstaged modification, exactly its prior state. The sibling has since committed it itself (`6fc8162`, `b51e202`). Final commit `3f4c861` contains exactly the four intended files. No `git clean`, no `git reset --hard`, no force-push, no protected ref touched.
- **Prevention for the rest of the plan:** commits 2 and 3 used the pathspec form `git commit -F - -- <paths>`, which commits the named paths from the working tree and ignores whatever else sits in the shared index. Both were verified with `git diff-tree` and contained exactly the intended files.
- **Recommendation for future concurrent waves:** `git add` + `git commit` is **not** race-safe on a shared index. Either use `git commit -- <paths>` throughout, or give concurrent executors separate worktrees.
