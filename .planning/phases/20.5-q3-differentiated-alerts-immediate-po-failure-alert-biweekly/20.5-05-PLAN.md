<objective>
Wire the biweekly pending-payment report into the cron tick: a dispatcher, a widened query window, and a `forResponse` block that fails independently of the month-close path.

Purpose: Q3-03 (biweekly report of all accumulated pendings), the payments half of Q3-04 (independent kill-switch) and Q3-05 (the month-close email retained byte-for-byte). Accounts payable pays twice a month, so the cadence matches a rhythm that already exists; today a payment pending since a prior month is invisible even at month close, because the payments query is restricted to the current calendar month.

Output: `dispatchPaymentReportIfDue(now, cfg)`, an optional third parameter on `buildEomDataQuery`, an independent wiring block in `forResponse`, both exported, and an integration suite.

## Conflict found during planning — read before Task 1

**D-08 says `PAYMENT_REPORT_LOOKBACK_DAYS` "replaces the `buildScopeWhere({ scope: 'current_month' })` restriction in the payments branch of `buildEomDataQuery`". Q3-05 says the month-close email is retained byte-for-byte. `buildEomDataQuery` serves both.** Read literally, an unconditional replacement widens the month-close payments email too, which is a change to an email the SPEC lists under "Out of scope".

Three resolutions exist and only one is correct:

- **Replace unconditionally.** Rejected. It changes the row set of an email whose only requirement this phase places on it is that it not change, and it does so in a way no assertion currently catches — `tests/integration/eom-dispatch.test.js` asserts the payments branch has no `responseAPI`, no `lastUpdate` and no `lastError`, and a `last_n_days` fragment satisfies all three. A silent content change on a customer-facing email is precisely the failure mode Q3-05 exists to prevent.
- **Write a second query builder for the report.** Rejected. Two copies of a query whose payments branch was made schema-valid at real cost in Phase 20.2, with the 20.2-05 comment block that explains why it cannot carry an error column living in only one of them.
- **Add an optional third parameter `scope`, defaulting to `{ scope: 'current_month' }`.** Adopted. The month-close call site omits it and gets a byte-identical string, so Q3-05 holds literally. The report call site passes `{ scope: 'last_n_days', lookbackDays: config.notifications.paymentReport.lookbackDays }`, which is exactly what D-08's own rationale asks for — its argument is about *what the operator still needs to see in the report*, not about the month-close email. The decision's intent is honoured; only its scope of application is narrowed to the thing it was reasoning about.

Apply the parameter to **both** branches of `buildEomDataQuery`, not only to payments. A function that silently ignores a caller-supplied scope for one category is the implicit-default trap of CLAUDE.md §6 #2 — the same shape as `runQuery(query, db = ...)` that broke seven callers in PR #16. The POs branch never receives a non-default today; it accepts one anyway so that it cannot lie about it later.

## The wiring decision, and why it is not the minimal diff

The EOM block at `src/background.js:46-65` is a kill-switch check followed by a `withStepTimeout` inside a try/catch that deliberately does not re-throw. The biweekly report gets its **own** block of the same shape immediately after it, not a second `await` inside the existing try.

The minimal diff would be to append the call inside the existing try. That is wrong: if `dispatchEomIfDue` throws, the catch fires and the payment report never runs — a month-close failure would silence a biweekly report that has nothing to do with it. Q3-04 asks for independent kill-switches; independent failure domains are the same requirement expressed at runtime. Two blocks of eighteen lines each is the correct cost.

Each block keeps its own `__step` name so a `[TIMEOUT]` line names the flow that actually stalled: `eomDispatch` stays as it is, the new one is `paymentReport`. Per-step `withStepTimeout` is the established pattern — `forResponse` already wraps each of its seven steps individually — so this adds a tier of nothing; `STEP_TIMEOUT_MS` continues to bound each step and `LOCK_TIMEOUT_MS` continues to bound the tick.

**No admin fallback.** `dispatchEomIfDue` falls back to `sendAdminAlert` when its operator send fails. The payment report does not. `LICENSE_ADMIN_EMAIL` is reserved for the child-process timeout (D-15) and must not receive these; the constraint is explicit in CONTEXT and in the SPEC. The sentinel is still always written, so a failed period is recorded and not retried into a loop.
