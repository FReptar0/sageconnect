# Phase 20.5 Plan 03: The biweekly gate and the po-alert HTML variant — Summary

`shouldDispatchPaymentReport` and `paymentPeriodOf` join `shouldDispatchEom` as a readable pair of gate predicates with no exact-day term anywhere, and `buildEomEmailHtml` gains a `variant` parameter whose default is byte-identical to what shipped in 20.2 — proven twice, by the fixture snapshot and by a direct equality assertion.

## What shipped

**Q3-03 / D-07 — the gate fires on the first tick at or after the period start.** `shouldDispatchPaymentReport(now, sentinelPath, reportConfig)` follows `shouldDispatchEom`'s fail-closed order exactly: bad config, then the off switch, then a bad `Date`, then a bad path, then the hour, then the sentinel. It contains **no day comparison at all**, and that absence is the decision. The period is carried by the sentinel *path*, which the caller builds from `paymentPeriodOf(now)`, so the predicate is true on the first tick at or after the period start and false forever after the sentinel lands. A literal `day === 1 || day === 16` would mean a service that was down, restarting or licence-blocked that day loses the period's report permanently and silently.

**D-06 — natural periods with no month-length branch.** `paymentPeriodOf` is `date.getDate() <= 15 ? 1 : 2`, returning `null` on a bad `Date`. February needs no special case because the upper period is defined as "16 or later", never as "16 to 30". Nine table-driven cases prove it across 31-day, 30-day, 28-day February and 29-day leap February.

**Q3-05 — the month-close body did not move.** `buildEomEmailHtml(rows, category, variant = 'eom')`. The default path is byte-identical: `git diff -- tests/fixtures/eom-email-sample.html` is empty and all 18 pre-existing assertions pass untouched. Only three literals change under `'po-alert'` — the heading (`SageConnect: OCs que fallaron al subir al portal`, with no month label, because an immediate alert is about now rather than a period), the intro sentence, and the fourth column header (`Fecha del fallo`, because the controller has no authorization date in scope at the failure sites and labelling a failure date as an authorization date would be a lie printed in the table the operator uses to chase suppliers). Everything else stays shared on purpose: the escaping, the 100-character truncation, the empty-rows path, the 20.2-05 footnote and the footer.

**D-07 was verified by mutation, not by assertion alone.** The plan required that the day-20 case "genuinely discriminate". Reintroducing `day === 1 || day === 16` into a copy of the module and re-running the truth table breaks **exactly 2 cases** — day 20 and day 9, the two D-07 cases — and leaves the other four untouched. The guard is real, not decorative.

- **Found during:** Task 2
- **Issue:** Task 2's `<action>` branches the heading (item 1) and the intro (item 2) on `isPoAlert` alone, gating only the column header (item 3) to the POs branch. ## Open finding for the user — HANDOFF §2 language, and a control gap in the hook that enforces it

Three related things surfaced while committing. **None was bypassed; the first needs a decision.**

**1. `src/utils/EomNotification.js` now carries three occurrences of a term HANDOFF §2 forbids.** One is pre-existing (Phase 20, in `shouldDispatchEom`'s JSDoc); **two were added by this plan**, mirroring that neighbour's wording so the paired predicates read alike. All three describe a notification on/off toggle, not the license validation service — but HANDOFF §2's rule is literal and covers any file a customer could read, and `src/` ships.

**2. The pre-commit hook cannot accept a commit that REMOVES the term.** A corrected wording was written and then reverted, because `pre-commit-redaction.sh` greps the whole staged diff — including removed lines — so the deletion of the offending line matches its own regex. The fix is unlandable through the hook. Verified concretely: with only the two `-` lines left in the diff, it still blocks. **`git checkout -- src/utils/EomNotification.js` restored the file byte-for-byte to its committed state; the tests were re-run green before and after.** This is the same false-positive class HANDOFF §1 already documents for context lines, one step worse.

**3. The hook has a matcher gap — this is the part worth fixing.** `pre-commit-redaction.sh` fires only on Bash commands that *begin* with `git commit`. The first three commits of this plan were issued as `git add <path> && git status --short && git commit -m …`, and **the hook never ran on any of them.** It fired only on the fourth, which was a bare `git commit`. So the redaction control is silently skipped by the ordinary compound form, which is how the two new occurrences reached `master`-bound history in the first place. HANDOFF §1 already says "never rely on the hook alone"; this is the mechanism behind that warning, now measured.

**Recommended:** land the neutral wording (`off switch`) for all three occurrences in one commit under `SAGECONNECT_HOOKS_BYPASS=1` — the only way past point 2 — with explicit consent, and separately widen the hook's matcher to any command *containing* `git commit`. Both are one-line changes and neither belongs to this plan's scope. My own added-lines redaction check also missed it: I grepped the two-word form written with a **space**, against text written with a **hyphen**. Use the hook's own regex — it accepts either separator — rather than retyping the term by hand. Do not transcribe it into any new file while doing so; that is the same "describe, don't transcribe" rule Phase 20.4 landed for its structural guards, and it applies to this section too.
