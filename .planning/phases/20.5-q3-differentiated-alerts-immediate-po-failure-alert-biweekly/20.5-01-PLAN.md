## Two hazards found while scouting — read before Task 1

**Hazard 1 — `buildMailing()` returns `{}` when `MAIL_TRANSPORT` is unset.** `src/config.js` builds `config.mailing` through a helper whose first branch is `if (!transport) return {};`. Putting `timeoutMs` inside that helper would make it `undefined` on any deployment that has not set `MAIL_TRANSPORT`, and `undefined < 1000` is `false`, so the floor guard would pass and nodemailer would fall back to its 600 000 ms default with no error anywhere. That is precisely the fail-open shape `parseStrictInt` was introduced to close in Phase 20.4. **`mailTimeoutMs` therefore lives on `config.notifications`, an unconditional object literal, not on `config.mailing`.** Write that reason into the comment above the key.

**Hazard 2 — `parseEnvNumber` alone is not enough.** The three numeric vars use `parseEnvNumber(raw, parseStrictInt, default)`, not `parseEnvNumber(raw, (v) => parseInt(v, 10), default)`. `parseInt` returns the integer prefix and discards the rest, and that prefix is a genuine integer, so `Number.isInteger` accepts it: `MAIL_TIMEOUT_MS=1e5` from an operator trying to raise the ceiling would become `1`, below the floor — which the floor guard happens to catch — while `PAYMENT_REPORT_LOOKBACK_DAYS=365abc` would become `365` and boot silently at a value the operator did not write. `parseStrictInt` returns `NaN` for both, and `Number.isInteger(NaN)` is `false`, so the guard exits 1 naming the variable. This is the WR-09 finding of Phase 20.4 applied to new variables rather than reintroduced. **Also update `parseStrictInt`'s own comment in `src/config.js`**, which today says it is used SOLO by the two probe vars: after this plan five variables use it, and leaving that comment would make the next reader think the helper is probe-specific and reach for `parseEnvNumber` alone on the next var — reopening the exact hole it exists to close.
