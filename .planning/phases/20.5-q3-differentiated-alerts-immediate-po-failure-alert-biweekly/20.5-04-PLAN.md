<objective>
Emit one operator email per tick listing the purchase orders that failed their **first** upload attempt, and prove that the pre-existing backlog emits nothing.

Purpose: Q3-01 (immediate PO failure alert), Q3-02 (one alert per PO, no retroactive flood) and the PO half of Q3-04 (independent kill-switch). Today a PO that fails on the 3rd is invisible to the operator until the 30th, while suppliers upload invoices daily and complain the same day. This is the deviation `DEVIATIONS.md` marks **BLOQUEANTE PARA DEPLOY**.

Output: a function-scoped `poAlerts` array, two capture points, one send, a new behavioural + structural suite, and a mock-fidelity correction across the three existing controller suites.

## The two decisions this plan must make impossible to get wrong

**D-01 — the send goes at the END of `createPurchaseOrders()`, never inside the per-PO `catch`.** `DEVIATIONS.md` proposes the catch. That is wrong here for three compounding reasons: the catch runs once per failing PO inside the tenant loop, so an `await` on SMTP there multiplies by the failure count and spends the very step budget Phase 20.4 exists to protect; it lands inside the block whose 20.3 S-3 comment claims nothing can throw outward, a claim already known to be false for `logGenerator`; and it produces N emails where the requirement asks for one. One send at the end costs exactly one SMTP round-trip per tick regardless of how many POs failed. Task 3 pins the placement structurally and Task 2 pins it behaviourally, so both a code reader and the suite reject the catch form.

**D-03 — the "already alerted" state is DERIVED, not stored.** Alert a PO when its **prior** `errorCount` is `0` — that is, when this tick is its first recorded failure — read from the `errorCounts` Map that Phase 20.3 already builds before the loop from the same SELECT. The two obvious alternatives were rejected and must stay rejected: a file per PO (`logs/po-alert-<oc>.sent`) grows without bound against a table already holding 3,313 `ERROR` rows and nothing ever reclaims it, which is the exact class of retained state CLAUDE.md §3 forbids; a module-scope `Map` survives ticks and is never reclaimed in a service that never restarts, which is the same violation and worse. Deriving it costs zero new state, is self-cleaning by construction and needs no new query.

**D-04 falls out of D-03 and is desirable, not incidental.** Every PO behind the 3,313 accumulated `ERROR` rows already has `errorCount > 0`, so the first tick after deploy emits zero alerts. Q3-02's no-flood requirement is satisfied by construction rather than by a suppression mechanism. Task 2 proves it with a fixture, because "satisfied by construction" is exactly the kind of claim that stops being true after one careless edit.

**D-05, the accepted limitation, recorded rather than engineered around.** A PO that is resolved and later fails again will not re-alert, because its historical `ERROR` rows keep `errorCount > 0`. That path is not reachable through the cron today: the RETRY-C7 dedupe excludes any PO holding a `POSTED`/`CLOSED` row from selection permanently. The backstop that makes single-alert semantics safe is Q3-05 — a PO alerted once and never resolved still appears in the month-close consolidated email. The two decisions are load-bearing together; do not weaken one without revisiting the other.

## Hazard found during planning — read before Task 1

Three existing suites call the **real** `createPurchaseOrders` with `jest.mock('../../src/config', ...)` factories that predate this phase. Adding an alert to the controller breaks them in two independent ways at once:

1. **They would attempt real SMTP.** `tests/controller/PortalOC_Creator.portal-check.test.js` drives POST-failure paths with fixtures whose `errorCount` is 0, which is precisely the first-failure condition. With `EmailSender` unmocked, each such case would hand a bogus host to nodemailer and make a real network attempt — nondeterministic latency in a suite that is otherwise hermetic.
2. **The kill-switch would read `undefined`.** Those config mocks have no `notifications` key, so `config.notifications.poAlert.enabled` would throw, or — if written defensively — evaluate falsy and silently disable the alert across all of them. That is the same silent-disable shape Phase 20.4 had to fix in two controller mocks (its Edits 4 and 5), and it is why those mocks are in this plan's `files_modified` rather than left for someone to discover.

Both are fixed in Task 1, in the same change that introduces the feature, so no intermediate commit leaves a red or a network-touching suite on a production-bound branch.
