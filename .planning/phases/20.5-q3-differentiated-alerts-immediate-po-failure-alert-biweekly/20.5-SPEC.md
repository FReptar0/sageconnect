# Phase 20.5: Q3 differentiated alerts — Specification

**Created:** 2026-09-08
**Ambiguity score:** 0.124 (gate: ≤ 0.20)
**Requirements:** 6 locked
**Milestone:** v2.4 — Retry policies · **Branch:** `feat/reintentos`
**Closes:** the Q3 deviation, open since `DEVIATIONS.md` (2026-06-02)

## Goal

Replace the single end-of-month notification with the **differentiated model the customer agreed on 2026-05-20**: a purchase order that fails to upload produces an operator email in the same cron tick that detected it, and pending payments are reported on a fixed twice-monthly cadence — while the existing month-close consolidated email is retained as the backstop that makes single-alert semantics safe.

## Background

**The deviation.** Phase 20 was built 13–15 May from an initial reading of the customer's criteria. The 20 May meeting closed those criteria formally, and **two of four answers came back different from what had been built**. `DEVIATIONS.md` records both. Q2 (retry frequency) was closed by Phase 20.1. **Q3 is the last one still open**, and it is a deploy blocker for the same reason Q2 was: shipping as-is delivers a system that does not behave the way the customer agreed.

**What the customer decided** (`MEETING-2026-05-20-NOTES.md` § Q3, textual):

- **POs — immediate.** Guillermo: *"órdenes de compra pendientes... requerimos que sea más continuo porque los proveedores suben facturas todos los días... no sería bueno que fuera cada mes. Ok, entonces que sea un alerta inmediata, ¿no?"* The operational reason is concrete: suppliers upload invoices daily, and an absent PO produces supplier complaints the same day.
- **Payments — every 15 days.** Guillermo: *"Y en pagos a lo mejor cada 15 días sí estaría perfecto."* Accounts payable pays twice a month, so the cadence matches an existing rhythm.

**What exists today.** `src/background.js:373` `dispatchEomIfDue(now, cfg)` loops `['pos', 'payments']` through **one** gate — `shouldDispatchEom` (`src/utils/EomNotification.js:58`): last calendar day of the month, hour ≥ `EOM_NOTIFICATION_HOUR` (default 18), sentinel `logs/eom-{YYYY-MM}-{category}.sent` absent, `EOM_NOTIFICATION_ENABLED` true. One cadence, both categories, no immediate path and no biweekly path. A PO that fails on the 3rd is invisible to the operator until the 30th.

**What is already built and reusable.** This phase is two new dispatch triggers over infrastructure that exists and is under test — not a rewrite:
- `EmailSender.sendOperatorReport({subject, html, callerLogFile})` — operator channel (`MAILING_NOTICES` + CC `MAILING_CC`), already swallows SMTP failures rather than throwing.
- `EomNotification.buildEomEmailHtml(rows, category)` — HTML table builder, with the honest footnote 20.2-05 added on the payments side.
- `writeSentinelAtomically` / `readSentinelPayload` — write-then-rename, already tested.
- `buildEomDataQuery(category, tenantDb)` — both queries, made schema-valid by Phase 20.2.

**Not blocked by CR-03** (verified 2026-09-08 against the code). The customer asked for a list of **pending** payments, not a diagnosis of each failure. The payments query counts `status NOT IN ('PAID','PARTIAL')` and lists `DOCNBR` without touching any error column, and its email table already carries the footnote declaring that gap. The PO query already selects `responseAPI` as `lastError`. CR-03 remains open for a different question — whether payments should record *why* they failed — and does not gate this phase.

**A hazard found while scouting.** `src/utils/EmailSender.js` sets **no timeouts at all**. Nodemailer's defaults leave `socketTimeout` at **10 minutes** — twice `STEP_TIMEOUT_MS` and equal to the child-process tier. SMTP already sits inside a `withStepTimeout` wrapper on the EOM path, so the step aborts at 5 minutes, but the abandoned promise keeps running (phantom continuation, D-10 at `background.js:88-90`). This phase adds a second SMTP call site inside a cron step, on the hot path of the tenant loop, which makes an unbounded SMTP a materially worse bet than it is today. Bounding it is in scope.

## Requirements

1. **Q3-01 — Immediate PO failure alert**: a PO whose upload fails produces an operator email within the same cron tick.
   - Current: no immediate path exists. `dispatchEomIfDue` fires only on the last calendar day at/after hour 18; a PO failing on the 3rd waits until the 30th.
   - Target: in a tick where one or more POs fail to upload for a tenant, exactly one operator email is dispatched for that tenant listing each failed PO with its PO number, tenant, and the portal's error text (`responseAPI`, the same value written to the control row).
   - Acceptance: a tick in which N POs fail produces exactly **one** email whose body contains all N PO numbers and their error text; a tick with zero failures produces **zero** emails. Asserted on the `sendOperatorReport` mock, not on log text.

2. **Q3-02 — One alert per PO, and no retroactive flood on first deploy**: the same PO does not re-alert while it remains unresolved, and the pre-existing backlog does not alert at all.
   - Current: no suppression exists because no alert exists. Production holds **3,313 `ERROR` rows** in `fesaOCFocaltec` (measured 2026-07-27) whose distinct-PO cardinality has never been measured.
   - Target: a PO that has already produced an alert produces no further alert while it stays unresolved; a PO whose failure history predates this phase's first tick produces no alert for that history.
   - Acceptance: a PO failing on three consecutive ticks yields exactly **1** email mentioning it. On the first tick after deployment against a control table that already holds `ERROR` rows, **zero** alerts are emitted for those pre-existing failures. Both proven with a controllable fixture, no live portal required.

3. **Q3-03 — Biweekly pending-payment report**: pending payments are reported on days 1 and 16, covering everything still pending regardless of age.
   - Current: payments are reported only at month close, and `buildEomDataQuery('payments', …)` restricts rows with `buildScopeWhere({ scope: 'current_month' }, …)`, so a payment pending since a prior month is invisible.
   - Target: on calendar day 1 and day 16, at/after `PAYMENT_REPORT_HOUR` (default 18), one consolidated email of pending payments per period, gated by a per-period sentinel; the row set is **not** limited to the current calendar month.
   - Acceptance: with the clock at day 16, hour ≥ 18, and no sentinel for that period, exactly one email is dispatched and the sentinel is written; a second tick in the same period dispatches nothing; a fixture payment dated two months earlier and still pending **appears** in the list.

4. **Q3-04 — Independent kill-switches, all OPTIONAL**: each of the three notification flows can be silenced without affecting the others.
   - Current: one `EOM_NOTIFICATION_ENABLED` and one `EOM_NOTIFICATION_HOUR` govern both categories together; `config.eom` is the only notification namespace.
   - Target: `PO_ALERT_ENABLED` (default `true`), `PAYMENT_REPORT_ENABLED` (default `true`) and `PAYMENT_REPORT_HOUR` (default `18`, range [0,23]) are added; `config.eom.*` is retained unchanged. All new vars are **OPTIONAL** — parsed through `parseEnvNumber` where numeric, with the boolean pattern the existing kill-switch uses.
   - Acceptance: `PO_ALERT_ENABLED=false` suppresses the PO alert while the payment report and the month-close email still dispatch, and the two symmetric cases hold. With none of the three vars set, `node -e "require('./src/config')"` exits 0 at the documented defaults. `PAYMENT_REPORT_HOUR=24` exits 1 with `[CONFIG ERROR]`.

5. **Q3-05 — The month-close consolidated email is retained, byte-for-byte**: it is the backstop that makes Q3-02's single-alert rule safe.
   - Current: `dispatchEomIfDue` sends both categories at month close; `tests/integration/eom-dispatch.test.js` and `tests/utils/EomNotification.test.js` pin that behavior.
   - Target: unchanged gate, unchanged sentinel naming, unchanged HTML. Answer Q1 of the same meeting committed to it explicitly (*"Lo que siga pendiente al cierre sale en un correo consolidado y se atiende manualmente"*), and without it a PO alerted once and never resolved would fall off the operator's radar permanently.
   - Acceptance: every pre-existing assertion in `eom-dispatch.test.js` and `EomNotification.test.js` passes **unchanged**; a PO that was alerted once and remains unresolved is present in the month-close consolidated list.

6. **Q3-06 — SMTP bounded strictly below the step budget**: no email call can outlive the step that contains it.
   - Current: `src/utils/EmailSender.js` builds its `transportConfig` from host/port/secure/auth only. No `connectionTimeout`, `greetingTimeout` or `socketTimeout` is set, so nodemailer's defaults apply and `socketTimeout` is **600000 ms** — twice `STEP_TIMEOUT_MS` and equal to `CHILD_PROCESS_TIMEOUT_MS`.
   - Target: all three nodemailer timeouts are set from one `MAIL_TIMEOUT_MS` (default `30000`, floor `1000`), applied at **both** call sites (`sendMail` and `sendOperatorReport`), with a startup range guard and a relational guard that `MAIL_TIMEOUT_MS < STEP_TIMEOUT_MS`. This extends the CLAUDE.md §9 chain with the SMTP tier alongside the axios tier.
   - Acceptance: with a stub SMTP server that accepts the connection and never answers, `sendOperatorReport` settles within the configured timeout rather than hanging; `MAIL_TIMEOUT_MS=300000` alongside `STEP_TIMEOUT_MS=300000` exits 1 with a `[CONFIG ERROR]` naming both values; `MAIL_TIMEOUT_MS=500` exits 1.

## Boundaries

**In scope:**
- The immediate PO failure alert, its per-tick grouping and its one-alert-per-PO suppression
- The biweekly pending-payment report, its day-1/day-16 gate and its per-period sentinel
- Widening the payments report row set beyond the current calendar month
- `PO_ALERT_ENABLED`, `PAYMENT_REPORT_ENABLED`, `PAYMENT_REPORT_HOUR`, `MAIL_TIMEOUT_MS` in `src/config.js`, with guards, and all four documented in `.env.example`
- Explicit nodemailer timeouts at both `EmailSender` call sites
- Jest coverage for both new flows, all three kill-switches, the suppression rule, the no-flood-on-first-deploy rule, and the four config-guard outcomes

**Out of scope:**
- **CR-03** (recording *why* a payment failed) — the customer asked for a list of pending payments, not a per-payment diagnosis; the existing footnote already declares the gap. Separate decision, separate work.
- **CR-02** (`CANCELLED` in the dedupe IN-list) and **CR-04** (the `lastUpdate` `ALTER TABLE`) — unrelated to notifications, each with its own caller audit.
- **Any change to the month-close email** — Q3-05 requires it stay identical; it answers Q1, a different question.
- **Any change to retry timing, the 30-day scope, the dedupe, or the portal probe** — this phase adds notification paths, it does not change what the cron selects or uploads.
- **Any schema change** — no column is added to hold alert state.
- **Re-alerting a PO that was resolved and later fails again** — the RETRY-C7 dedupe excludes any PO holding a `POSTED`/`CLOSED` row from selection permanently, so through the cron this path is not reachable. Accepted limitation, recorded rather than engineered around.
- **Converting `EmailSender` to a pooled singleton** — it creates a transport per call, which is inconsistent with the `PortalClient` / SQL-pool discipline, but non-pooled SMTP closes its socket per send, so this is a tidiness issue and not the EMFILE class of §3 bug. Bounding the timeout (Q3-06) is the part that is actually load-bearing here.

## Constraints

- **Always-on (CLAUDE.md §3):** any per-tick accumulator is function-scoped and dies with the tick. Alert-suppression state that must outlive a tick may not be an unbounded module-scope `Map` and may not be an ever-growing set of files — whatever carries it must have a stated, bounded lifetime.
- **No SMTP round-trip inside the per-PO error path.** The failure path runs once per failing PO inside the tenant loop; an `await` on the network there multiplies by the failure count and spends the very step budget Phase 20.4 exists to protect. This constrains where the alert may fire, not whether.
- **Operator channel only:** `MAILING_NOTICES` with CC `MAILING_CC`, via `sendOperatorReport`. `LICENSE_ADMIN_EMAIL` is reserved for the child-process timeout (decision D-15) and must not receive these.
- **SMTP failure must never break a tick.** `sendOperatorReport` already swallows and logs; the new call sites must preserve that, so a dead mail server degrades notifications and nothing else.
- **The payments query must stay bounded.** Removing the calendar-month restriction must not become an unbounded scan of Sage payment history; the widened window needs an explicit, finite bound.
- **OPTIONAL, never REQUIRED**, for all four new vars — the October server boots from a fresh `.env`, and a missing REQUIRED var fail-fasts the service (decision 20.1-01).
- **No new SQL string interpolation** (CLAUDE.md §6 #1); **`runQuery`'s signature is untouched** (CLAUDE.md §6 #2).
- **No local Sage DB and no staging** (HANDOFF §6): verification is structural + Jest, with live confirmation on `zcl-rds-test` before the October migration.
- **Test baseline:** the CLAUDE.md §6 failing set. Last measured on this branch at the close of 20.3: 6 failed suites / 7 failed tests / 565 passed / 573 total. No NEW failures.

- [ ] `PAYMENT_REPORT_ENABLED=false` suppresses only the payment report
