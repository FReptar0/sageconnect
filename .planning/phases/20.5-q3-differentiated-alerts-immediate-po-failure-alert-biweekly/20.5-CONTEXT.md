# Phase 20.5: Q3 differentiated alerts - Context

**Gathered:** 2026-09-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Two new notification triggers on top of infrastructure that already exists and is under test: an **immediate PO failure alert**, grouped per tick and emitted once per PO, and a **biweekly pending-payment report** on days 1 and 16. The Phase 20 month-close email is retained unchanged as the backstop. Plus one hardening item the code review surfaced: bounding SMTP so a hung mail server cannot spend a cron step's budget.

This phase adds **dispatch paths**. It does not change what the cron selects, what it uploads, the retry timing, the dedupe, or the schema.

</domain>

<decisions>
## Implementation Decisions

The user delegated the implementation decisions, as throughout this milestone, with a standing bar carried from 20.3 and 20.4: **satisfy the locked SPEC, minimum diff, do not knock existing structures out of alignment** — and on 2026-09-09 added an explicit priority: *"solo debe de funcionar y ya... quiero salir de estos pendientes."* Read that as: prefer the option that ships correctly with the least new machinery, not the most elegant one.

### Where the PO alert fires

- **D-01: One email at the END of `createPurchaseOrders()`, never inside the per-PO `catch`.**

  *Why:* `DEVIATIONS.md` proposes the catch, and that is wrong here. The catch runs once per failing PO inside the tenant loop; an `await` on SMTP there multiplies by the failure count and spends the very step budget Phase 20.4 exists to protect. It also lands inside the block whose S-3 comment claims nothing can throw outward — a claim already known to be false for `logGenerator` (open finding from the 20.4 review). One send at the end of the function costs one SMTP round-trip per tick regardless of how many POs failed.

- **D-02: The accumulator is a function-scoped array**, declared beside the 20.3/20.4 counters (`probed`, `probeFound`, …, `probeDeferred`). It dies with the tick, needs no cleanup, and is the same §3 shape those counters already carry.

### What carries the "already alerted" state — the one decision that could have gone badly

- **D-03: Nothing new. Derive it from `errorCounts`, which already exists.**

  Alert a PO when its **prior** `errorCount` is `0` — that is, this tick is its **first** recorded failure. The `errorCounts` Map is already built at the top of `createPurchaseOrders()` (20.3 D-02), keyed by trimmed `ocKey`, from the same SELECT.

  *Why this and not the obvious alternatives:*
  - **A file per PO** (`logs/po-alert-<oc>.sent`) grows without bound against a table already holding 3,313 `ERROR` rows, and nothing ever reclaims it — the exact class of retained state CLAUDE.md §3 forbids.
  - **A module-scope `Map`** survives ticks and is never reclaimed in a service that never restarts. Same §3 violation, worse.
  - Deriving it costs **zero new state**, is self-cleaning by construction, and needs no new query — the data is already in the recordset.

- **D-04: Accepted and desirable consequence — the pre-existing backlog never alerts.** Every PO behind the 3,313 accumulated `ERROR` rows already has `errorCount > 0`, so the first tick after deploy emits **zero** alerts. That is exactly the no-flood requirement of Q3-02, satisfied by construction rather than by a suppression mechanism.

- **D-05: Accepted limitation, recorded rather than engineered around.** A PO that is resolved and later fails again will not re-alert, because its historical `ERROR` rows keep `errorCount > 0`. This is not reachable through the cron today: the RETRY-C7 dedupe excludes any PO holding a `POSTED`/`CLOSED` row from selection permanently. If that dedupe ever changes, revisit this.

  The **backstop that makes single-alert semantics safe** is Q3-05: a PO alerted once and never resolved still appears in the month-close consolidated email. The user chose "una sola vez, hasta que se resuelva" (2026-09-08) on that understanding; the two decisions are load-bearing together.

### The biweekly cadence

- **D-06: Periods are natural — 1 to 15, and 16 to end of month.** Sentinel `logs/payment-report-{YYYY-MM}-{1|2}.sent`, written with the existing `writeSentinelAtomically` (write-then-rename, already tested).

- **D-07: The gate fires on the first tick at/after the period start, not only on day 1 or day 16.** Predicate: compute the period from the day (`day <= 15 ? 1 : 2`), require `hour >= config.notifications.paymentReport.hour` and the period's sentinel absent.

  *Why not "day is exactly 1 or 16":* the service could be down, restarting, or licence-blocked that day, and the report would silently never go out for that period. The existing `shouldDispatchEom` has the same shape (last day + hour + sentinel), so this follows the established predicate rather than inventing one.

### The payments query window

- **D-08: `PAYMENT_REPORT_LOOKBACK_DAYS`, OPTIONAL, default 365, range [30, 3650].** Replaces the `buildScopeWhere({ scope: 'current_month' })` restriction in the payments branch of `buildEomDataQuery`.

  *Why a dedicated var rather than reusing `config.retry.lookbackDays`:* they answer different questions. The retry window (30 days) is *what the cron still tries to upload*; the report window is *what the operator still needs to see*. A payment the cron gave up on is precisely what belongs in a report. Coupling them would silently shrink the report the day someone tunes the retry window.

  A generous finite default satisfies the user's "todos los pendientes acumulados sin importar antigüedad" (2026-09-08) while keeping the query bounded — an unbounded scan of Sage payment history is not acceptable on this server.

### Config surface

- **D-09: Add, do not rename.** `config.eom.*` stays exactly as it is; `config.notifications.poAlert` and `config.notifications.paymentReport` are added alongside. `DEVIATIONS.md` proposes deleting the `eom` namespace — renaming is cosmetic, widens the diff across guards and passing tests, and Q3-05 requires the month-close path to stay byte-identical anyway.

- **D-10: Four new OPTIONAL env vars**, all through `parseEnvNumber` where numeric and the established boolean pattern for the switches: `PO_ALERT_ENABLED` (true), `PAYMENT_REPORT_ENABLED` (true), `PAYMENT_REPORT_HOUR` (18, [0,23]), `PAYMENT_REPORT_LOOKBACK_DAYS` (365, [30,3650]). Plus `MAIL_TIMEOUT_MS` (Q3-06). **OPTIONAL is load-bearing** — the October server boots from a fresh `.env` and a missing REQUIRED var fail-fasts the service (decision 20.1-01).

- **D-11: `MAIL_TIMEOUT_MS` mirrors `PORTAL_HTTP_TIMEOUT_MS`** — default 30000, floor 1000, plus a relational guard `< STEP_TIMEOUT_MS`. Applied to nodemailer's `connectionTimeout`, `greetingTimeout` and `socketTimeout` at **both** `EmailSender` call sites. Today none are set, so `socketTimeout` defaults to **600000 ms** — twice the step budget and equal to the child-process tier.

  Follow the guard shape Phase 20.4 established, including `parseStrictInt`: the four original timeout guards accept `'1e5'` and `'50abc'` truncated, and that fail-open trap should not be reintroduced in a new var.

### Reuse — this phase writes little new code

- **D-12:** `sendOperatorReport` (already swallows SMTP failures rather than throwing — preserve that), `buildEomEmailHtml` (already carries the 20.2-05 footnote on the payments side), `writeSentinelAtomically` / `readSentinelPayload`, and both branches of `buildEomDataQuery`. The PO query already selects `responseAPI AS lastError`, so the alert body has its error text with no query change.

### Claude's Discretion

All of the above. Where "ship it" and "most elegant" pulled apart, the record says which won: D-03 (zero new state beat a purpose-built store), D-07 (robust predicate beat the literal reading of "days 1 and 16"), and D-09 (add beat rename).

</decisions>

## Existing Code Insights

### Reusable Assets
- **`errorCounts`** (`PortalOC_Creator.js`, built before the loop) — already keyed by trimmed `ocKey`; D-03 reads it and adds nothing.
- **The five/six probe counters** — the declaration site, scope and lifetime the new accumulator copies.
- **`parseEnvNumber` + `parseStrictInt`** (`src/config.js`) — the second was added in 20.4 precisely because the first lets truncated input through.
- **`sendOperatorReport({subject, html, callerLogFile})`** — operator channel (`MAILING_NOTICES` + CC `MAILING_CC`), never throws.

### Established Patterns
- **Function-scoped state only** — 20.3's `errorCounts` and 20.4's `tickStart` both carry a written §3 lifetime argument in their comment blocks. Anything new here needs the same.
- **Sentinel gating** — `shouldDispatchEom` is the predicate shape to follow: calendar condition + hour + sentinel absent + kill-switch.
- **Bracketed log tags** — `[EOM-GATE]`, `[EOM-SKIP]`, `[EOM-DISPATCH]`, `[OPERATOR-EMAIL]`. New tags follow the same convention.

### Integration Points
- **`src/background.js` L42-64** — the EOM dispatch already sits inside a `withStepTimeout` wrapper (`__step = 'eomDispatch'`) and deliberately does not re-throw: an EOM failure must not break the tick. The payment report joins that same guarded path.
- **`LICENSE_ADMIN_EMAIL` is reserved** for the child-process timeout (D-15) and must not receive operator mail.

</code_context>
