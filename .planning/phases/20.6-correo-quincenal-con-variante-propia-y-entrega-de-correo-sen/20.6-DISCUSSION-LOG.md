## Señalización de entrega

| Option | Description | Selected |
|--------|-------------|----------|
| Objeto de resultado `{ delivered, error }` | Retrocompatible, más rico que un booleano, absorbe señales futuras sin cambiar la firma | ✓ |
| Booleano | Más simple, pero pierde el motivo del fallo, que el requisito 6 necesita registrar | |
| Parámetro `throwOnFailure` | Deja al llamador decidir, pero reintroduce la posibilidad de que el correo tumbe el tick | |
| EventEmitter | Estado retenido nuevo (§3) sin beneficio sobre el valor de retorno | |

**Elección:** objeto de resultado. **Notas:** D-12 de la 20.5 ordena conservar el «traga y no lanza»; el objeto lo respeta. El `throwOnFailure` se descartó de forma deliberada y no por gusto: un interruptor así acaba encendido desde `createPurchaseOrders`, y ahí un SMTP caído reprueba el paso del tenant **después** de que los INSERT de la tabla de control ya se comprometieron.

## Ramificación de la variante de pagos

| Option | Description | Selected |
|--------|-------------|----------|
| `'payment-report'` con `!isPos && variant === …` | Simétrico al `isPoAlert` existente; es lo que prescribe el comentario del módulo | ✓ |
| Tabla de búsqueda `category × variant` | Generaliza, pero esconde la propiedad «lo no soportado degrada seguro» | |
| Partir en funciones por categoría | Amplía el diff a todo el módulo y arriesga el requisito 3 | |

**Elección:** la forma simétrica. **Notas:** el autor de la 20.5 dejó la instrucción por escrito — *«Si alguna vez se necesita una variante del lado de pagos, tendrá que ramificar también por `category`»*. La conjunción con la categoría no es un detalle de estilo: es lo que hace que una pareja no soportada caiga al cuerpo genérico en vez de mandar la tabla de pagos bajo el título de OCs.

## Origen del rótulo de periodo

| Option | Description | Selected |
|--------|-------------|----------|
| Pasarlo desde el sitio de llamada, en un objeto de opciones | Un solo reloj: el que ya usó el gate y el asunto | ✓ |
| Recalcularlo dentro con `new Date()` | Sin cambio de firma, pero crea un segundo reloj | |
| Seguir derivándolo de la primera fila del lote | Es el defecto que la fase viene a quitar | |

**Elección:** pasarlo, como cuarto parámetro **objeto de opciones**. **Notas:** recalcular adentro parece inocuo hasta que un tick cruza la medianoche del 15 al 16 y el cuerpo dice una quincena mientras el asunto dice otra. El objeto de opciones (en vez de un cuarto posicional) es para que la quinta variante agregue una llave y no una posición.

## Centinela y escalamiento

| Option | Description | Selected |
|--------|-------------|----------|
| Escribir siempre el centinela, con payload honesto | Respeta EOM-04 / D-07 de la fase 20; cierra CR-03 sin tocar la regla | ✓ |
| No escribirlo si el envío falló, y reintentar | Lo elegido en la ronda 1 del spec — **revertido**, ver notas | |
| Reintento acotado por periodo | Atractivo, pero cambia el predicado del gate; se difiere | |

**Elección:** payload honesto, centinela siempre. **Notas:** **ésta revierte una respuesta del usuario.** En la ronda 1 del spec eligió «no escribir centinela y reintentar al siguiente tick»; la opción se le presentó antes de leer el CONTEXT de la 20.5, o sea sin saber que **SPEC EOM-04 / CONTEXT D-07 de la fase 20** fija lo contrario con su razón escrita en el código: *«para que un servidor de correo muerto no convierta el reporte en un reintento cada quince minutos contra el buzón del operador»*. Al revisarlo salió además que el hallazgo CR-03 nunca fue «el centinela se escribe», sino «su payload dice `success: true` cuando el correo no salió» — la rama de fallo ya existe completa en el código y es inalcanzable. Arreglar la mentira cierra el hallazgo y deja la regla previa intacta.

El `sendAdminAlert` de REQ EOM-04 sí se recupera para el cierre de mes (D-11): bajo D-03 ese correo es el control compensatorio de la alerta de OCs, y un control compensatorio que falla en silencio no es un control. El reporte quincenal sigue sin respaldo al buzón de administración, porque `LICENSE_ADMIN_EMAIL` está reservado por D-15 de la 20.5.
