<objective>
Make the error-stats `OUTER APPLY` schema-valid for `fesa.dbo.fesaPagosFocaltec`, which has only four
columns (`idCia`, `NoPagoSage`, `status`, `idFocaltec`) and no `lastUpdate`. `buildErrorStatsApply`
gains a **required** `timestampColumn` selector drawn from a closed two-value set; the payments branch
emits `CAST(NULL AS datetime) AS lastErrorAt` instead of `MAX(lastUpdate) AS lastErrorAt`, and the OC
branch stays byte-identical.

Purpose: today the payment cron query raises `Invalid column name 'lastUpdate'`, the `.catch()` at
`PortalPaymentController.js:103` swallows it and returns `{ recordset: [] }`, so the payment cron would
process **zero payments on every tick, forever** — with a `[RETRY] candidates=0 deferred=0 processing=0`
summary that reads as normal. This is the phase's deploy blocker.

Output: a fragment builder that cannot silently emit an invalid column, plus all 7 call sites audited
and updated in the same wave the parameter becomes required.

Decisions implemented (CONTEXT traceability) — D-06: required parameter that throws when absent, never
an optional default (CLAUDE.md §6 pitfall #2 — PR #16 changed a shared util's implicit default and
silently broke 7 callers) · D-07: throw posture and message shape mirror `getRetryIntervalMinutes` ·
D-08: all call sites state their table shape explicitly; the forced audit is the point of the required
parameter.
</objective>

<!-- Contract this plan establishes. Downstream plans (20.2-03, 20.2-04) consume it directly. -->
buildErrorStatsApply({ fesaTable, joinColumn, joinKey, dbAlias, dbColumn, timestampColumn }): string

timestampColumn is REQUIRED and drawn from a closed set of exactly two values:
  'lastUpdate' -> emits `SELECT COUNT(*) AS errorCount, MAX(lastUpdate) AS lastErrorAt`   (fesaOCFocaltec)
  'none'       -> emits `SELECT COUNT(*) AS errorCount, CAST(NULL AS datetime) AS lastErrorAt` (fesaPagosFocaltec)
  anything else (missing, null, wrong case, arbitrary identifier) -> throws
    `buildErrorStatsApply: invalid timestampColumn <value>`

Because the set is closed, NO caller-supplied string ever reaches the emitted SQL for this column —
each branch emits a fixed literal. joinColumn / dbColumn keep their existing `||` defaults (out of scope).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller arguments -> `buildErrorStatsApply` -> emitted SQL string | Hardcoded identifiers and controlled tenant aliases chosen by the caller cross into a template literal (pre-existing pattern, CLAUDE.md §6 #1). |
| emitted SQL -> SQL Server (`fesa` + tenant DBs) | A statement referencing a non-existent column aborts the whole query; the caller's `.catch()` converts that into an empty recordset. |

No endpoint, no auth surface, no external/operator input is introduced by this plan. `timestampColumn`
becomes the only new parameter, and it is a closed two-value set: neither value is ever interpolated —
each branch emits a fixed literal SELECT line — so this plan adds **zero** new interpolation sites.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-20.2-01 | Denial of Service | payment cron query (`PortalPaymentController.js:103` swallow) | mitigate | The invalid `MAX(lastUpdate)` against `fesaPagosFocaltec` is what makes the cron process zero payments every tick with a normal-looking `[RETRY]` summary. Task 1 removes the reference; Task 3 pins it with `not.toMatch(/lastUpdate/)` on the generated fragment. |
| T-20.2-02 | Tampering | `timestampColumn` -> emitted SQL | mitigate | Closed two-value set with strict equality and an early throw. No caller string reaches the SQL for this column; an unknown or near-miss value fails loudly before any string is produced (D-06/D-07). Seven bad values are asserted to throw. |

| T-20.2-04 | Injection (SQL) | `fesaTable` / `joinKey` / `dbAlias` / `dbColumn` interpolation | accept | Pre-existing template-literal interpolation of hardcoded caller literals and controlled tenant values (CLAUDE.md §6 #1; `RetryPolicy.js:146-148` records the rationale). | T-20.2-05 | Information disclosure | emitted fragment content | accept | The fragment contains table and column identifiers only — no secrets, no PII, no payment amounts. |
