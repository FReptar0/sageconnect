## Q1 — Precedent for a shared SQL-fragment builder that varies output by table/shape

**Analog: `buildScopeWhere`, `src/utils/RetryPolicy.js:112-127`** — the only other builder in the repo that changes its emitted SQL based on a caller-supplied identifier. Full body:

```javascript
function buildScopeWhere(scopeConfig, options = {}) {
    const cfg = scopeConfig || {};
    const opts = options || {};
    const dateField = opts.dateField || 'Fecha';

    if (cfg.scope === 'current_month') {
        const monthStart = 'DATEFROMPARTS(YEAR(GETDATE()), MONTH(GETDATE()), 1)';
        return `${dateField} >= ${monthStart} AND ${dateField} < DATEADD(month, 1, ${monthStart})`;
    }

    if (cfg.scope === 'last_n_days') {
        return `${dateField} >= DATEADD(day, -${cfg.lookbackDays}, CAST(GETDATE() AS DATE))`;
    }

    throw new Error('buildScopeWhere: invalid scope ' + cfg.scope);
}
```

Its JSDoc states the varying-shape contract explicitly (`src/utils/RetryPolicy.js:100-102`):

```
 * `options.dateField` lets the caller name the column or supply a qualified expression:
 * POs default to `'Fecha'`; payments override with `'P.AUDTDATE'`.
```

**How it constrains the new parameter — three ways:**

1. **Shape:** variation is driven by a *named identifier the caller supplies*, and the invalid-input case throws (L126) while the *valid* branches return a template literal. The new timestamp-column selector should follow the same "caller names the column, builder shapes the SQL" model.
2. **Placement:** `buildScopeWhere` puts the varying identifier in a **second options object** (`options.dateField`). `buildErrorStatsApply` does not have that shape — it takes **one destructured object** (`src/utils/RetryPolicy.js:158`):
   ```javascript
   function buildErrorStatsApply({ fesaTable, joinColumn, joinKey, dbAlias, dbColumn } = {}) {
       const resolvedJoinColumn = joinColumn || 'ocSage';
       const resolvedDbColumn = dbColumn || 'idDatabase';
   ```
   The new parameter belongs **inside that same destructured object**, alongside `fesaTable`/`joinColumn`/`dbColumn` — not as a second positional argument. All 5 call sites already pass an object literal, so this keeps the diff to one added key per site.
3. **Anti-pattern warning — do NOT copy `buildScopeWhere`'s *defaulting*.** L115 (`opts.dateField || 'Fecha'`) and L159-160 (`joinColumn || 'ocSage'`, `dbColumn || 'idDatabase'`) are exactly the implicit-default pattern D-06 forbids. The analog supplies the *structure*; D-06 inverts the *semantics*. The new key must have **no `||` fallback** — the absence of a fallback is the mechanism that forces the D-08 audit.

**Byte-identical OC constraint (SPEC acceptance #3).** Today's template is `src/utils/RetryPolicy.js:162-168`:

```javascript
    return `OUTER APPLY (
    SELECT COUNT(*) AS errorCount, MAX(lastUpdate) AS lastErrorAt
    FROM ${fesaTable}
    WHERE ${resolvedJoinColumn} = ${joinKey}
      AND ${resolvedDbColumn} = '${dbAlias}'
      AND status = 'ERROR'
) AS ef`;
```

Only the **second line** varies. The OC branch must reproduce `    SELECT COUNT(*) AS errorCount, MAX(lastUpdate) AS lastErrorAt` including its 4-space indent; the payments branch swaps only the second column expression to a typed NULL. Interpolating the whole `SELECT` line (rather than branching the whole template) is the smallest change that keeps the OC output provably byte-identical.

## Q2 — How this codebase expresses "required argument, throw when absent"

Three throw sites, quoted verbatim. All three share one message shape: **`'<functionName>: <lowercase problem>'`, with the offending value appended by `+` string concatenation (never a template literal).**

**`src/utils/RetryPolicy.js:38`** — the posture D-07 names:
```javascript
    throw new Error('getRetryIntervalMinutes: invalid docType ' + docType);
```
Its JSDoc rationale (L18-20) is the argument D-07 reuses for the new parameter:
```
 * An unknown `docType` throws: the two call sites are hardcoded ('payment' in the payment
 * controller, 'po' in the PO controller/diagnostic), so a third value is a programmer error
 * worth surfacing loudly — same posture as buildScopeWhere's invalid-scope throw.
```

**`src/utils/RetryPolicy.js:126`** — same shape, reached by fallthrough after the valid branches:
```javascript
    throw new Error('buildScopeWhere: invalid scope ' + cfg.scope);
```

**`src/utils/EomNotification.js:172-174`** — the closest analog for *missing* (rather than *unknown*) input, i.e. the D-06 case:
```javascript
    if (!payload || typeof payload !== 'object') {
        throw new Error('writeSentinelAtomically: payload must be an object');
    }
```

**Constraint:** the new throw must (a) prefix with `buildErrorStatsApply:`, (b) name the parameter, (c) append the received value with `+` when the failure is "unknown value", and (d) fire on a falsy/missing value as an **early guard at the top of the function** (the `writeSentinelAtomically` shape) rather than only as a fallthrough — because the payments case must be an explicit opt-in, not the residue of an `else`.

**Matching test assertion shape** — `tests/utils/RetryPolicy.test.js:68-72`:
```javascript

        expect(() => getRetryIntervalMinutes(intervalCfg, 'invoice')).toThrow(/invalid docType/i);
        expect(() => getRetryIntervalMinutes(intervalCfg, undefined)).toThrow(/invalid docType/i);
        expect(() => getRetryIntervalMinutes(intervalCfg, 'PO')).toThrow(/invalid docType/i);
    });
```
Note the third case: a *near-miss* value (`'PO'` vs `'po'`) is asserted too. The new throw test should include the equivalent near-miss (e.g. a wrong-cased or plausible-but-wrong column name) plus the omitted-key case.

function findProcessExitCalls(filePath) {

### Measured scope of the guard, and the false-positive that shapes its design

I enumerated every `fesaPagosFocaltec` reference in `src/` (27 occurrences across 11 files). **Only two files contain both `fesaPagosFocaltec` and `lastUpdate`/`responseAPI`:**

| File | Lines | Verdict |
|---|---|---|
| `src/background.js` | 495, 497 (payments branch) | **The real violation** this phase fixes. Note L463/L465 are the *POs* branch and are legitimate (D-11). |
| `src/utils/RetryPolicy.js` | 58 (JSDoc prose), 163 (the shared template) | **Permanent false positive** for any file-level check. |

The other 9 files (`upload-single-payment.js`, `portal-payments-generator.js`, `payment-reconciliation.js`, `pending-payments-diagnostic.js`, `payment-uuid-repair.js`, `payment-uuid-diagnostic.js`, `mark-payment-invoices-paid.js`, plus the two in scope) touch `fesaPagosFocaltec` but contain **zero** `lastUpdate`/`responseAPI` lines — they are clean today and will stay clean.

**Constraint:** a naive file-level "contains both" grep flags `src/utils/RetryPolicy.js` forever, because the shared builder legitimately emits `MAX(lastUpdate)` for the OC case and mentions it in prose at L58. And `src/background.js` legitimately contains both strings after the fix (POs branch, L463-465). So the guard **cannot be file-level**. Two viable designs, both consistent with the analog (CONTEXT explicitly leaves the choice to discretion):

- **(a) Proximity/statement-scoped scan** — for each occurrence of `fesa.dbo.fesaPagosFocaltec`, examine the enclosing SQL statement or an N-line window and assert no `lastUpdate`/`responseAPI` inside it. Reuses `scanDir` + comment-stripping verbatim; needs an `ALLOWED_FILES`-style exemption for `RetryPolicy.js` (or comment-stripping alone handles L58, leaving only L163 to exempt).
- **(b) Assert on generated fragments** — call `buildErrorStatsApply({... fesaPagosFocaltec ...})` and `buildEomDataQuery('payments', 'COPDAT')` and assert `not.toMatch(/lastUpdate|responseAPI/)` on the emitted strings. Zero false positives and it tests the actual emitted SQL, but it covers only known emitters — it would *not* catch a new file this phase never touches, which is the stated purpose of D-12 #3.

A hybrid (b for the two known emitters + a for the repo sweep with a documented exemption) is the only option that satisfies "covers files this phase never touches" without a permanent red test. `buildEomDataQuery` is already exported (`src/background.js:729`), so option (b) needs no production change.

## Hazards discovered (not in CONTEXT.md or SPEC.md)

### H-1 — `computeRetryEligibility` fails **CLOSED** on a bad `now`, but fails **OPEN** on everything else

The helper's contract (L53-55) promises fail-open:
```
 * Fails OPEN, never throws: an unusable `intervalMinutes` (missing/NaN/negative) or an
 * unparseable `lastErrorAt` yields "eligible now" rather than a permanently deferred row.
```
That guarantee **does not extend to `now`**, which D-01 turns into a new SQL-sourced data path. Verified by execution:

| `now` value | Result | Why |
|---|---|---|
| `undefined` | falls back to `new Date()` (Node clock) | ES6 default at L67 fires only on `undefined` |
| `null` | **`eligible: false` — permanently deferred** | L82 `new Date(null).getTime() === 0`, so `0 >= nextEligibleAt` is always false |

So if `dbNow` ever arrives as `null` (a driver quirk, a hand-edited fixture, a future query variant), **every candidate row defers forever** — silently, with `[RETRY-DEFER]` lines that look normal. That is the same class of invisible stall this phase exists to eliminate, re-introduced from the other direction. And if `dbNow` is simply *missing* from a row, the code silently reverts to the Node clock — the exact defect being fixed, with no test failure.

**Implication for the planner:** the call sites need an explicit decision on the `row.dbNow` guard (coerce falsy → `undefined` to preserve fail-open? throw? log?), and the D-12 helper test should cover the `now: null` case. Neither CONTEXT nor SPEC addresses this.

### H-2 — Existing test fixtures will silently mask the D-01 wiring

Every current recordset fixture builds rows without a `dbNow` key (`tests/controller/PortalPaymentController.cron-where.test.js:62-82` factory; `tests/controller/PortalOC_Creator.cron-where.test.js:100-104`; both `tests/scripts/retry-month-*.test.js`), and derives `lastErrorAt` from `Date.now()`. Per H-1, `now: row.dbNow` → `undefined` → Node clock → **all four eligibility cases keep passing unchanged**.

This is good for RETRY-S5 (no regressions from fixture churn) but it means:
- The **helper test (D-12 #2) must set `dbNow` explicitly** on its fixture, or it proves nothing.
- The **SQL-shape test (D-12 #1) is not redundant** — it is the only thing that catches removal of `GETDATE() AS dbNow`, exactly as D-12 argues.
- Any new fixture that sets `dbNow` must also switch its `lastErrorAt` to be **relative to `dbNow`**, not to `Date.now()`, or the +360-minute skew scenario cannot be expressed.

### H-3 — Seven call sites, not five

D-08 counts 5 production call sites of `buildErrorStatsApply`. Making the parameter required also breaks the **2 test call sites** in `tests/utils/RetryPolicy.test.js:190-195` and `:206-212`. Total 7 edits, or the RetryPolicy suite goes red — which would violate RETRY-S5's "identical failing-suite set".
