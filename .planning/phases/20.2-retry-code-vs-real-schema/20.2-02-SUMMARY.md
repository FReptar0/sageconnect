## The normalization, as shipped

`src/utils/RetryPolicy.js`, replacing the single expression that was `const nowMs = (now instanceof Date ? now : new Date(now)).getTime();`:

```js
const candidateNowMs = (now instanceof Date ? now : new Date(now)).getTime();
const nowMs = (!now || !Number.isFinite(candidateNowMs)) ? Date.now() : candidateNowMs;
```

Both predicates are load-bearing and they catch disjoint failure sets:

| Predicate | Catches | Why the other one misses it |
|---|---|---|
| `!now` | `null`, `''`, `0` | Each yields the Unix epoch — a **finite** timestamp, so `Number.isFinite` accepts it |
| `!Number.isFinite(candidateNowMs)` | `NaN`, `'not-a-date'`, `{}`, `[]` | Truthy values, so the falsy test never fires |

`undefined` is handled upstream by the untouched ES6 default (`now = new Date()`).

Measurement shows `'not-a-date'` and `NaN` deferred permanently too: the old code took `.getTime()` on an Invalid Date, got `NaN`, and `NaN >= anything` is `false`. So the pre-change helper failed **closed** on *every* unusable `now` without exception, not just the three falsy ones — and the JSDoc claiming an unparseable input yields "eligible now" was already wrong for `now` before this phase touched it.

## The replaced JSDoc paragraph

Removed (it was false on both counts after this phase):

```
 * Clock basis: `now` is the Node process clock while `lastErrorAt` comes from SQL Server
 * (`MAX(lastUpdate)`). Any skew between the two hosts shifts the boundary by that skew —
 * a pre-existing Phase 20 assumption, explicitly out of scope for 20.1.
```

Shipped in its place:

```
 * Clock basis (D-01): `now` MUST originate from the SAME SELECT statement that produced
 * `lastErrorAt` — the `GETDATE() AS dbNow` column each caller adds to its projection. Both
 * operands then come off the same SQL Server, so any driver-level timezone reinterpretation
 * applies identically to both and cancels out of the subtraction. `GETDATE()` in a SELECT list
 * is a per-statement runtime constant (D-05), so every row in one tick shares one identical
 * `dbNow` — no intra-batch drift. This helper cannot detect a caller that violates the rule;
 * the SQL-shape tests on the call sites are the net for that half.
```

## D-04 operator warning — verbatim, for the deploy notes

Lift this into the deploy notes as-is:

> Both operands live in "server-local wall clock labelled UTC" space, so the `nextEligibleAt` that `[RETRY-DEFER]` prints via `.toISOString()` renders SERVER-LOCAL time carrying a `Z` suffix. Read it as Mexico time, not as UTC. Measured 2026-07-27 on the deployed SQL Server host: `DATEDIFF(mi, GETUTCDATE(), GETDATE())` = -360, i.e. six hours. Documented rather than corrected on purpose — the `[RETRY*]` log labels are anchored by `^...$` regexes in the controller tests, so the log line itself must not change.

Operationally: a `[RETRY-DEFER]` line reading `nextEligibleAt=2026-07-28T14:30:00.000Z` means **14:30 Mexico time**, not 08:30. Anyone converting from the `Z` will be six hours off in the wrong direction.

## What this plan does NOT cover

**The helper cannot detect a *missing* `dbNow`.** If a call site never projects the column, `row.dbNow` is `undefined`, the ES6 default fires, and the helper silently evaluates against the Node process clock — the exact defect this phase exists to remove, with no test failure anywhere. The fail-open guard shipped here covers a *bad* `dbNow`; it is structurally blind to an *absent* one.

That half is covered only by the SQL-shape assertions in plans **20.2-03** (both controllers) and **20.2-04** (the three operator tools), which assert `GETDATE() AS dbNow` is present in the emitted query text. This is precisely why D-12 specifies three complementary tests rather than one — they are not redundant, they cover disjoint failure modes:

| D-12 test | Covers | Blind to |
|---|---|---|
| #1 SQL-shape (plans 03/04) | the column is projected | the value being unusable |
| #2 helper skew test (this plan) | a bad value cannot stall or mislead | the column never being added |
| #3 repo-wide guard (plan 06) | files this phase never touches | runtime behaviour |

## Next Phase Readiness

The `<interfaces>` contract that plans 20.2-03 and 20.2-04 are written against is shipped exactly as specified:

```
computeRetryEligibility({ lastErrorAt, intervalMinutes, now }): { eligible, nextEligibleAt }
  lastErrorAt falsy or unparseable   -> { eligible: true, nextEligibleAt: null }
  intervalMinutes unusable           -> treated as 0
  now missing/null/''/0/NaN          -> falls back to the process clock (fail OPEN)
  otherwise                          -> eligible = now >= lastErrorAt + intervalMinutes  (>= inclusive)
```

Signature, parameter names, return shape and the `>=` boundary are unchanged (D-02) — no call site needs adjusting for this plan alone.

**Wave 3 can start.** Plans 20.2-03 and 20.2-04 add the `GETDATE() AS dbNow` projections that make the contract's first sentence true at the call sites. Their SQL-shape tests are the only net for a *missing* `dbNow`, which this plan is structurally unable to detect — treat them as required, not as belt-and-braces.

Note for whoever writes the Wave 3 fixtures: per hazard H-2, any fixture that sets `dbNow` must derive its `lastErrorAt` from `dbNow`, not from `Date.now()`, or the skew scenario cannot be expressed and the test proves nothing.
