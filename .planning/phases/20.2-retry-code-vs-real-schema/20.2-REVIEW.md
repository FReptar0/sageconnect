# Fase 20.2: Reporte de Code Review

**Revisado:** 2026-07-28T17:22:03Z
**Profundidad:** standard

## Resumen

La fase corrige tres defectos (RETRY-S1/S2 columnas inexistentes, RETRY-S4 reloj único, RETRY-S5
sin regresiones) y lo hace de forma consistente en los cinco call sites de `buildErrorStatsApply`.
Las 8 suites del alcance pasan (66 tests, 0 fallos). No se agregó ningún timer, listener, caché de
módulo ni file handle nuevo: el diff es exclusivamente SQL, comentarios y líneas de log, así que la
restricción always-on (CLAUDE.md §3) no se toca.

Dicho eso, la fase **no logra el resultado que declara** en dos de sus tres frentes:

1. **La consulta de pagos del correo de fin de mes sigue siendo inválida en runtime** — ya no por la
   columna inexistente, sino por comparar el entero Sage `P.AUDTDATE` contra una expresión de tipo
   `date`. Es exactamente el mismo modo de falla (statement abortado → `catch` → recordset vacío →
   "Sin pendientes") que la fase existe para eliminar, con otra causa. La misma línea de scope
   existe sin corregir en `retry-month-payments.js`, donde deja el `--apply` sin efecto. El guard
   que sí existe para esto (`CONVERT(Date, CONVERT(VARCHAR(8), P.AUDTDATE))`) está sólo en el
   controlador, y ninguna de las dos suites nuevas lo replica.
2. **El diagnóstico de OC sigue mezclando relojes** — `computeRetryEligibility` ya recibe `dbNow`,
   pero el veredicto que se imprime al operador 30 líneas más abajo vuelve a comparar contra
   `new Date()`. Con el skew medido de −360 min y el intervalo de 240 min, la rama "esperando
   reintento" es inalcanzable: el diagnóstico siempre dirá "lista para reintentar" para una OC que
   el cron difiere — la divergencia que el helper compartido existe para impedir, según el
   comentario que la propia fase agregó ahí.

Además, al arreglar RETRY-S3 la fase hizo alcanzable por primera vez un bug de renderizado que
antes quedaba enmascarado por la consulta rota (CR-04), y el guard estático nuevo
(`tests/schema-guard.test.js`) es una heurística de proximidad con falsos negativos y falsos
positivos demostrables.

Fuera de alcance por instrucción explícita y **no** reportado: la interpolación de alias de tenant
controlados en template literals (CLAUDE.md §6 #1, incluidos los args CLI preexistentes de
`po-cron-diagnostic.js`), D-ITEM-03 (`PortalOC_Creator.js` no proyecta `ef.*`), D-ITEM-01 (bloque r4
del diagnóstico), la raíz de CR-03 (nadie escribe `status='ERROR'` en pagos) y los ~7 fallos de test
preexistentes.

## Critical Issues

### CR-01: La consulta de pagos del correo EOM sigue abortando en runtime (`int` vs `date`)

**File:** `src/background.js:488` y `src/background.js:518`
**Issue:**
`buildEomDataQuery('payments', db)` arma el filtro de scope con `dateField = 'P.AUDTDATE'` sin
envolver. El fragmento generado es (verificado ejecutando el helper):

```sql
P.AUDTDATE >= DATEFROMPARTS(YEAR(GETDATE()), MONTH(GETDATE()), 1)
  AND P.AUDTDATE < DATEADD(month, 1, DATEFROMPARTS(YEAR(GETDATE()), MONTH(GETDATE()), 1))
```

`P.AUDTDATE` es un entero Sage con formato `YYYYMMDD`. La evidencia es del propio repo:
`PortalPaymentController.js:52` lo convierte con `CONVERT(Date, CONVERT(VARCHAR(8), P.AUDTDATE))`,
`payment-reconciliation.js:669` lo compara contra el literal numérico `${getCurrentDateCompact()}`,
y el comentario del guard en `tests/controller/PortalPaymentController.cron-where.test.js:117-121`
lo declara textualmente: *"AUDTDATE is a Sage YYYYMMDD integer — comparing it bare against
DATEFROMPARTS(...) triggers an int->date implicit conversion that errors at runtime"*.
`DATEFROMPARTS` y `DATEADD(month, 1, <date>)` devuelven `date`, y SQL Server no admite la conversión
implícita `int → date`: el statement completo aborta con *Operand type clash: int is incompatible
with date*.

La consecuencia es idéntica al defecto que esta fase vino a eliminar: el `catch` de
`dispatchEomIfDue` (`src/background.js:398-402`) traga el error, `allRows` queda vacío, el correo se
envía diciendo **"Sin pendientes en esta categoría este mes"** y el sentinel se escribe con
`success: true`, bloqueando cualquier reintento en lo que resta del mes. El plan 20.2-05 declara
"make the EOM payments query valid against the real schema"; la consulta sigue sin ser válida.

El scope `last_n_days` (el default desde 20.1) tiene el mismo problema:
`P.AUDTDATE >= DATEADD(day, -30, CAST(GETDATE() AS DATE))` también compara contra `date`.

Ninguna de las aserciones nuevas de `tests/integration/eom-dispatch.test.js:194-212` mira este
punto: sólo verifican ausencia de `responseAPI` / `lastUpdate` / `lastError`.

**Fix:**

```javascript
// src/background.js:488 — misma expresión que PortalPaymentController.js:76
const dateField = 'CONVERT(Date, CONVERT(VARCHAR(8), P.AUDTDATE))';
```

`P.AUDTDATE AS fechaAuth` en la línea 501 debe cambiar junto con esto (ver CR-04). Y replicar en
`tests/integration/eom-dispatch.test.js` el par de aserciones que ya protege al controlador:

```javascript
expect(sql).toMatch(/CONVERT\(Date, CONVERT\(VARCHAR\(8\), P\.AUDTDATE\)\)\s*>=\s*DATEFROMPARTS/);
expect(sql).not.toMatch(/P\.AUDTDATE\s*>=\s*DATEFROMPARTS/);
```

### CR-03: El veredicto de `po-cron-diagnostic.js` sigue comparando contra el reloj de Node

**File:** `src/scripts/po-cron-diagnostic.js:285` y `src/scripts/po-cron-diagnostic.js:289`
**Issue:**
El bloque r6 ya resuelve `dbNow` y se lo pasa a `computeRetryEligibility` (líneas 249-261) — la
corrección RETRY-S4. Pero el resultado `eligible` que ese helper devuelve **se descarta**
(`const { nextEligibleAt } = computeRetryEligibility({...})`) y el veredicto se vuelve a derivar a
mano contra el reloj del proceso:

```javascript
else if (verdict.errorCount > 0 && verdict.nextEligibleAt && new Date(verdict.nextEligibleAt) > new Date())
```

`nextEligibleAt` vive en el espacio "hora local del servidor etiquetada como UTC" (deriva de
`lastErrorAt`/`dbNow`, que tedious con `useUTC: true` devuelve 360 min por detrás del tiempo real).
`new Date()` es UTC real. Con el skew medido de −360 min:

- valor máximo de `nextEligibleAt` = `dbNow + 240 min` = `now_real − 360 min + 240 min` = `now_real − 120 min`
- por lo tanto `nextEligibleAt > new Date()` es **siempre falso**

La prioridad 2 ("ERROR previo … Esperando reintento hasta …") es inalcanzable y la prioridad 3
("intervalo cumplido. Lista para reintentar") se dispara siempre que `errorCount > 0`. El
diagnóstico contradice sistemáticamente al cron — que es literalmente lo que el comentario agregado
en las líneas 245-248 de esta misma fase dice haber impedido.

**Fix:** usar el veredicto que el helper ya calculó, en lugar de recalcularlo con otro reloj:

```javascript
const { eligible, nextEligibleAt } = computeRetryEligibility({
    lastErrorAt,
    intervalMinutes: retryIntervalMin,
    now: dbNow,
});
verdict.eligibleNow = eligible;          // guardar junto a los demás campos del verdict
// ...
// Prioridad 2
else if (verdict.errorCount > 0 && verdict.nextEligibleAt && !verdict.eligibleNow) { ... }
// Prioridad 3
else if (verdict.errorCount > 0 && verdict.nextEligibleAt && verdict.eligibleNow) { ... }
```

Agregar un caso de test que fije la asimetría: `lastErrorAt = dbNow − 5 min` con intervalo 240 debe
producir el veredicto "esperando reintento", no "lista para reintentar".

### CR-04: El correo de pagos EOM rotula el mes como `1969-12` en cuanto CR-01 se corrija

**File:** `src/utils/EomNotification.js:121-126` (con `src/background.js:501`)
**Issue:**

```javascript
if (safeRows.length > 0 && safeRows[0].fechaAuth) {
    const parsed = new Date(safeRows[0].fechaAuth);
    monthLabel = Number.isNaN(parsed.getTime()) ? yyyyMm(new Date()) : yyyyMm(parsed);
}
```

Para la categoría `payments`, `fechaAuth` viene de `P.AUDTDATE AS fechaAuth`
(`src/background.js:501`), es decir el entero `20260512`, no una fecha. `new Date(20260512)` lo
interpreta como **milisegundos desde epoch** → `1970-01-01T05:37:40.512Z`, que no es `NaN`, así que
el guard no lo atrapa. `yyyyMm` usa getters locales, por lo que en el servidor (UTC−6) el título
queda:

```
<h1>SageConnect: Pendientes fin de mes — 1969-12</h1>
```

mientras el asunto del correo, construido aparte en `src/background.js:407` a partir de `now`, dice
`— 2026-07`. La celda de la tabla renderiza además el entero crudo `20260512` frente al
`2026-05-07` de la rama POs.

Hoy está enmascarado porque la consulta nunca devuelve filas (CR-01); **se vuelve visible en el
mismo momento en que CR-01 se corrija**, así que ambos deben arreglarse en el mismo cambio. Ninguna
de las dos suites lo detecta porque sus fixtures usan strings ISO
(`tests/utils/EomNotification.test.js:176-177`, `tests/integration/eom-dispatch.test.js:99`) — una
forma de fila que la consulta de pagos no puede producir. Es el mismo problema de "fixture
optimista" que la fase documentó para D-ITEM-03, aquí sin registrar.

**Fix:** normalizar en la consulta, junto con CR-01, para que ambas categorías entreguen una fecha
real:

```sql
-- src/background.js:501
CONVERT(Date, CONVERT(VARCHAR(8), P.AUDTDATE)) AS fechaAuth,
```

y endurecer el helper para que un valor no-fecha no pase silencioso:

```javascript
const raw = safeRows[0].fechaAuth;
const parsed = (raw instanceof Date) ? raw : new Date(String(raw));
monthLabel = Number.isNaN(parsed.getTime()) ? yyyyMm(new Date()) : yyyyMm(parsed);
```

Cambiar los fixtures de pagos de ambos tests a la forma que la consulta realmente produce.

### WR-01: Un fallo de consulta se convierte en "Sin pendientes" + sentinel que bloquea el mes

**File:** `src/background.js:392-403` y `src/background.js:409-439`
**Issue:** el `catch` por tenant registra `[EOM-DISPATCH] … query-failed` y continúa con
`allRows` vacío; luego `buildEomEmailHtml` emite *"Sin pendientes en esta categoría este mes"* y
`writeSentinelAtomically` graba `success: true` (porque el SMTP sí funcionó), lo que cierra la
puerta a cualquier reenvío durante el resto del mes. Este es el **amplificador** que mantuvo
invisible el defecto de pagos: la fase corrigió una causa y dejó el mecanismo intacto, de modo que
el próximo error de SQL (CR-01 incluido) vuelve a producir un correo que afirma que no hay nada
pendiente.
**Fix:** propagar el estado de la consulta al cuerpo y al sentinel:

```javascript
let queryFailed = false;
// ... en el catch: queryFailed = true;
const html = buildEomEmailHtml(allRows, category, { queryFailed });
sentinelPayload = { ..., queryFailed };
```

y que `buildEomEmailHtml` renderice un bloque explícito ("No se pudo consultar N de M tenants —
este reporte está incompleto") en lugar de "Sin pendientes". Alternativamente, no escribir el
sentinel cuando `queryFailed` es true, para que el siguiente tick reintente.

### WR-02: `buildErrorStatsApply` no valida la pareja `fesaTable` ⇄ `timestampColumn`

**File:** `src/utils/RetryPolicy.js:195-198`
**Issue:** el guard sólo comprueba que `timestampColumn` pertenezca al conjunto cerrado. La
combinación imposible se acepta sin ruido:

```javascript
buildErrorStatsApply({ fesaTable: 'fesa.dbo.fesaPagosFocaltec', ..., timestampColumn: 'lastUpdate' })
// => 'SELECT COUNT(*) AS errorCount, MAX(lastUpdate) AS lastErrorAt FROM fesa.dbo.fesaPagosFocaltec'

que es exactamente el SQL inválido que la fase existe para impedir. El JSDoc (líneas 172-177)
afirma que la trampa de default implícito (CLAUDE.md §6 #2) queda cerrada "antes de construir
cualquier SQL"; sólo está cerrada a medias, y el guard estático de WR-03 no la cubre de forma
fiable.
**Fix:**

const TIMESTAMPLESS_TABLES = new Set(['fesa.dbo.fesaPagosFocaltec']);

    throw new Error(`buildErrorStatsApply: ${fesaTable} has no timestamp column; use timestampColumn 'none'`);
}
```

Un test que fije el throw para esa pareja convierte la invariante en estructural en vez de léxica.

### WR-08: Imports sin usar y ramas muertas en los tres scripts operativos

### WR-11: El parche de `console.*` de los scripts nunca se revierte (always-on)

**File:** `src/scripts/retry-month-payments.js:40-60` y `src/scripts/retry-month-pos.js:39-59`
**Issue:** ambos módulos reemplazan `console.log/warn/error/table` **en tiempo de carga del módulo**
y nunca restauran los originales. Consecuencias: (a) cargar los dos módulos en el mismo proceso
anida los wrappers, duplicando cada línea en dos archivos de log; (b) cualquier `require` futuro de
estos scripts desde el servicio always-on redirigiría *toda* la salida de consola del proceso al
log `RetryMonthPOs`/`RetryMonthPayments`, sin cota (CLAUDE.md §3: todo primitivo que retiene estado
debe acotar su vida). Hoy sólo se alcanza vía `node src/scripts/…` y vía Jest —donde el parche
queda activo durante todo el archivo de test—, así que el riesgo es contenido, pero es el único
primitivo con estado del conjunto revisado y no tiene ruta de limpieza escrita.
**Fix:** envolver el parche en un helper con `restore()` invocado en el `finally` de `main()`, o
—más simple— llamar directamente a `logGenerator` en los puntos que importan y dejar `console`
intacto:

```javascript
function installConsoleMirror() {
    const orig = { log: console.log, warn: console.warn, error: console.error, table: console.table };
    // ... reasignaciones ...
    return () => Object.assign(console, orig);
}
// main(): const restore = installConsoleMirror(); try { ... } finally { restore(); }
```
