# Phase 20.2: Retry code vs. real schema — Specification

**Created:** 2026-07-27
**Ambiguity score:** 0.09 (gate: ≤ 0.20)
**Requirements:** 5 locked

## Goal

Every SQL statement the retry path emits becomes valid against the **real** production schema read on 2026-07-27, and the retry elapsed-time comparison stops mixing two different clocks — so that deploying the Phase 20 / 20.1 code cannot silently stop the payment sync.

## Background

Phase 20 introduced `buildErrorStatsApply` (an `OUTER APPLY` that computes `errorCount` + `lastErrorAt` from the `fesa.*` control tables) into both cron controllers and into the end-of-month notification query. Phase 20.1 migrated the eligibility math onto that data. **Neither has ever run against production** — `master` is ~49 commits ahead of `origin` and Phase 20 was never deployed, and the 20.1 work sits unpushed on `feat/reintentos`.

On 2026-07-27 the production schema was read for the first time (`fesa.INFORMATION_SCHEMA.COLUMNS`, run by Santiago Peláez on `ZCL-SQL-01`; Yahir's own SQL access is blocked pending an IT request). The authoritative column lists are:

| Table | Columns |
|---|---|
| `fesa.dbo.fesaOCFocaltec` | `idFocaltec nchar`, `ocSage nchar`, `status nchar`, `lastUpdate date`, `createdAt date`, `responseAPI nvarchar`, `idDatabase nchar` |
| `fesa.dbo.fesaPagosFocaltec` | `idCia nchar`, `NoPagoSage char`, `status nchar`, `idFocaltec nchar` — **four columns, nothing else** |

Three defects follow directly from that:

1. **The payment cron query references a column that does not exist.** `buildErrorStatsApply` emits `MAX(lastUpdate)` against `fesaPagosFocaltec`. SQL Server raises `Invalid column name 'lastUpdate'`; the `.catch()` at `src/controller/PortalPaymentController.js:103` swallows the error and returns `{ recordset: [] }`. The payment cron would log one line and then **process zero payments on every tick, indefinitely** — no crash, no alarm, and a `[RETRY] candidates=0 deferred=0 processing=0` summary that reads as normal.

2. **The end-of-month payments query has the same defect, twice.** `src/background.js:495-497` selects `responseAPI` and orders by `lastUpdate` on `fesaPagosFocaltec`. The `try/catch` at L398 logs a warn and continues with no rows, so the payments EOM email would always report "Sin pendientes".

3. **The retry elapsed-time comparison mixes two clocks.** `lastErrorAt` is written server-local via `GETDATE()` but read back as UTC — `tedious@18.6.1` defaults `useUTC: true` (`node_modules/tedious/lib/connection.js:485`) and `src/utils/SQLServerConnection.js:14` sets only `trustServerCertificate`. Measured on `ZCL-SQL-01`: `DATEDIFF(mi, GETUTCDATE(), GETDATE())` = **-360**. Since 360 min exceeds both configured intervals (240 PO, 30 payment), every candidate always looks eligible and `[RETRY-DEFER]` can never be emitted.

The OC side of `buildErrorStatsApply` is **correct** — `fesaOCFocaltec` genuinely has `lastUpdate`, `createdAt` and `responseAPI`.

## Requirements

1. **RETRY-S1 — Payment error-stats fragment is schema-valid**: The `OUTER APPLY` built for `fesaPagosFocaltec` must not reference any column absent from that table.
   - Current: `buildErrorStatsApply` unconditionally emits `MAX(lastUpdate) AS lastErrorAt`, which is invalid for `fesaPagosFocaltec` and aborts the whole payment cron query.
   - Target: the fragment built for the payments table emits a valid `errorCount` (`COUNT(*)`, which is legal — `status` exists) and an explicit typed NULL for `lastErrorAt`, so the shape both controllers consume is unchanged. The fragment built for `fesaOCFocaltec` is byte-identical to today.
   - Acceptance: a unit test asserts the payments fragment contains no occurrence of `lastUpdate` and still exposes `errorCount` and `lastErrorAt` aliases; the OC fragment test asserts `MAX(lastUpdate)` is still present. A repo-wide check finds zero statements selecting `lastUpdate` or `responseAPI` from `fesa.dbo.fesaPagosFocaltec`.

2. **RETRY-S2 — Payment cron query executes and processes rows**: The payment cron must reach its post-filter with the rows the database returned, not with the empty-recordset fallback.
   - Current: the query aborts on `Invalid column name`, `.catch()` returns `{ recordset: [] }`, and zero payments are processed every tick.
   - Target: the emitted query is valid, so `payments.recordset` carries the real rows and the existing `[RETRY]` summary reports true counts.
   - Acceptance: the `PortalPaymentController.cron-where` suite asserts the generated SQL references only columns present in the real schema for the `fesaPagosFocaltec` sub-selects, and its existing four eligibility cases still pass. The AUDTDATE `CONVERT`, `>= 60` antiquity, `NOT IN NoPagoSage` dedupe and `idCia` assertions survive verbatim.

3. **RETRY-S3 — EOM payments query is schema-valid and still lists pendings**: The end-of-month payments query must select only existing columns while still reporting pending payments.
   - Current: `background.js:495-497` selects `responseAPI` and orders by `lastUpdate` on `fesaPagosFocaltec`; the query throws, is caught at L398, and the payments email always reads "Sin pendientes".
   - Target: the payments branch of the EOM query drops the error-description column (the data cannot exist) and any ordering by a non-existent column, while keeping the pending-payment rows it can legitimately compute. The POs branch is unchanged — `responseAPI` exists on `fesaOCFocaltec`.
   - Acceptance: the generated payments EOM SQL references only `idCia`, `NoPagoSage`, `status`, `idFocaltec` from `fesaPagosFocaltec`; a test asserts the POs branch still selects `responseAPI`; the payments email body renders its table without an error-description column.

4. **RETRY-S4 — Elapsed time is measured on one clock**: The retry eligibility comparison must not compare a SQL Server timestamp against the Node process clock.
   - Current: `computeRetryEligibility` receives `lastErrorAt` from SQL Server and `now` from `new Date()` in both controllers and all three operator scripts. With the measured -360 min server offset this makes every row eligible.
   - Target: both values in the comparison originate from the same clock, so a server whose UTC offset is non-zero cannot change the outcome. All five call sites are consistent.
   - Acceptance: no call site passes a Node-clock `now` alongside a SQL-sourced `lastErrorAt`; a test proves that a row whose last error is inside its interval is deferred using values that would be wrongly ruled eligible under a 360-minute skew.

5. **RETRY-S5 — No regressions**: The correction introduces no new test failures and does not alter behavior outside the retry path.
   - Current: baseline is 6 failing suites / 7 failing tests (`PaymentReconciliation`, `TransformTime`, `no-process-exit`, `enforcement-wiring`, plus the `config` and `operation-manager` Jest worker crashes), 476 passing of 484.
   - Target: the same 6 failing suites and no new failing test; no timeout tier touched; the RETRY-C7 dedupe (`status IN ('CLOSED','POSTED')`) unchanged.
   - Acceptance: `npm test` reports the identical failing-suite set; a diff review confirms zero changed lines in the four timeout range guards (`src/config.js:221-244`) and in the RETRY-C7 predicates.

## Boundaries

**In scope:**
- Making the `fesaPagosFocaltec` error-stats `OUTER APPLY` schema-valid (typed NULL `lastErrorAt`, real `COUNT(*)` `errorCount`)
- Making the EOM payments query schema-valid and rendering its email table without an error-description column
- Removing the two-clock comparison from the retry eligibility path across all five call sites
- Tests proving each of the above, including a skew-resistant eligibility test

**Out of scope:**
- **CR-04 — restoring the 240-minute PO interval.** `lastUpdate` and `createdAt` are both typed `date`, so no time-of-day is stored for OC errors; the interval cannot work without an `ALTER TABLE`. Deferred deliberately until it is measured whether RETRY-C7 alone stops the portal hammering — a production schema change is not justified on a hypothesis.
- **CR-03 — recording payment failures.** Nothing writes `status='ERROR'` for payments and the table has no column for an error time or message. This needs a design decision, not a fix, and it is complicated by the payment dedupe (`P.DOCNBR NOT IN (SELECT NoPagoSage …)`) having no status filter — inserting an ERROR row would exclude that payment permanently.
- **The 23 uncovered control rows** — `CANCELLED` (18) and `OPEN` (5) match neither side of the RETRY-C7 dedupe. `CANCELLED` is a pre-existing gap, identical before and after RETRY-C7; `OPEN` semantics are unknown and must be asked, not guessed.
- **D-ITEM-01** — `po-cron-diagnostic.js:181` still replicates the old `= 'POSTED'` dedupe. Operator-tool honesty, unrelated to schema validity.
- **Changing `useUTC` on the connection pool** — a one-line change that would reinterpret every datetime read application-wide (payments, CFDIs, reconciliation). Blast radius unacceptable for this fix.
- **Deploying anything.** The August window, lead approval and the notice to Memo are unchanged and out of this phase.

## Constraints

- **Always-on regime** (CLAUDE.md §3): the service never exits between 15-minute cron ticks. Any primitive retaining state must bound its own lifetime.
- **Defense-in-depth invariant** (CLAUDE.md §9): `axios (30s) < step (5m) < child (10m) < lock (14m)` must remain untouched.
- **No schema change.** This phase is code-only by construction; the `ALTER TABLE` question is deferred (see Boundaries).
- **No local Sage DB.** All verification is structural — unit tests on generated SQL shape plus the existing cron-where suites. Live behavior remains a post-deploy observation.
- **No new SQL string interpolation** (CLAUDE.md §6 pitfall #1). Fixed column names only; no operator or portal input crosses into these fragments.
- **`runQuery(query, db)`** — pass the target DB explicitly wherever it is not `config.database.database` (CLAUDE.md §6 pitfall #2).
- **The OC path must not regress.** `fesaOCFocaltec` does have `lastUpdate`; its fragment must stay byte-identical.

## Acceptance Criteria

- [ ] No statement anywhere in `src/` selects `lastUpdate` or `responseAPI` from `fesa.dbo.fesaPagosFocaltec`
- [ ] The payments error-stats fragment still exposes `errorCount` and `lastErrorAt` aliases, with `errorCount` from a real `COUNT(*)`
- [ ] The OC error-stats fragment still emits `MAX(lastUpdate)` and is otherwise unchanged
- [ ] The EOM POs branch still selects `responseAPI`; the EOM payments branch selects only the four columns that exist
- [ ] No retry call site compares a SQL-sourced `lastErrorAt` against a Node-clock `now`
- [ ] A test proves a row inside its retry interval is deferred, using values that a 360-minute skew would wrongly rule eligible
- [ ] `npm test` shows the same 6 failing suites / 7 failing tests as the baseline, with zero new failures
- [ ] Zero changed lines in `src/config.js:221-244` (timeout range guards) and in both RETRY-C7 `status IN ('CLOSED','POSTED')` predicates
