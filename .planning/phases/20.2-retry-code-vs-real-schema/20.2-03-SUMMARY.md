## The projections, as shipped

They differ in shape because the two files differ — 4-space vs 2-space, bare vs bracket-quoted aliases (PATTERNS S-6: match the file, not a global rule).

`src/controller/PortalPaymentController.js`, appended after `ef.lastErrorAt AS lastErrorAt`:

```sql
    GETDATE()      AS dbNow
```

`src/controller/PortalOC_Creator.js`, appended after `) as [WITHHOLD_TAX_SUM]`:

```sql
  GETDATE()                                    as [dbNow]
```

The alias **text** is camelCase in both. Every other alias in `PortalOC_Creator.js` is upper-case, so this is a deliberate exception: the JS side reads `row.dbNow`, and one key name across all five call sites of this phase is worth more than local consistency. A comment in the query records that.

## The batch resolutions

Payments (4-space, underscore-prefixed locals):

```js
const _candidatesCount = payments.recordset.length;
const _dbNow = _candidatesCount > 0 ? payments.recordset[0].dbNow : null;
```

POs (2-space, unprefixed locals):

```js
  const candidatesCount = recordset.length;
  const dbNow = candidatesCount > 0 ? recordset[0].dbNow : null;
```

Read from `recordset[0]` **once per batch**, not per row. `GETDATE()` in a SELECT list is a per-statement runtime constant (D-05), so every row already carries an identical value — reading it per row would imply a drift that cannot occur, and would invite a future "simplification" back to `new Date()`.

## The `[RETRY-CLOCK]` line, verbatim

```
[RETRY-CLOCK] tenant=<db> dbNow=missing fallback=node-clock
```

Level `warn`. Emitted once per tick, gated on `(candidatesCount > 0 && !dbNow)`.

It exists because `computeRetryEligibility` is structurally unable to tell a missing column from a deliberate omission — it fails open to the process clock, which is exactly the defect being removed, and does so silently. Plan 20.2-02's SUMMARY names this as the half it cannot cover.

Gating matters in both directions: per-row emission would be unbounded on an always-on service (CLAUDE.md §3), and an ungated warn would fire on every empty tick, training operators to ignore it.

## The skew constants and why the fixtures had to move

Both suites gained:

```js
const SERVER_SKEW_MIN = 360;
const DB_NOW = new Date(Date.now() - SERVER_SKEW_MIN * 60 * 1000);
```

360 is the measured `DATEDIFF(mi, GETUTCDATE(), GETDATE())` on the deployed SQL host, 2026-07-27.

**Every `lastErrorAt` fixture now derives from `DB_NOW`, never from `Date.now()`.** This is hazard H-2 and it is the reason Task 1 alone proved nothing: no fixture in this repo set `dbNow` before this phase, so after the controller change all four eligibility cases fell straight through to the process clock and stayed green. Measured — the suites passed unchanged after Task 1, before any fixture moved.

The deferral fixtures are now the skew proof: 5 minutes old on the server clock, 365 on the process clock, against a 30-minute (payment) and 240-minute (PO) interval.

Verified by executing the helper against both clocks for the same row:

| `now` | eligible | consequence for the suite |
|---|---|---|
| `dbNow` | `false` | `deferred=1` holds — test passes |
| `new Date()` | `true` | `deferred=1` fails — test catches the reversion |

The assertions were already in the file. Deriving the fixture from `DB_NOW` is what made them discriminating.

## H-4 / D-ITEM-03 — the developer's decision

`PortalOC_Creator.js` joins the error-stats `OUTER APPLY` at L177 and **never projects** `ef.errorCount` or `ef.lastErrorAt`. Re-verified before recording:

```
$ grep -c '\bef\b' src/controller/PortalOC_Creator.js
1          # and the single hit is a COMMENT at L211, asserting the opposite
$ grep -n 'ef\.' src/controller/PortalPaymentController.js
60,61      # the payment controller does project both
```

So `row.lastErrorAt` is `undefined` on every live PO row, the helper reads that as "never failed → eligible now" (RETRY-C4, deliberately), and **every PO has always been ruled eligible**. The per-row deferral log has never been able to fire for POs. It survived two phases of review because the cron-where suite's mocked recordset supplies `lastErrorAt` — a row shape the real query cannot produce.

**Decision 2026-07-27: DEFER.** `fesaOCFocaltec.lastUpdate` is typed `date`, not `datetime`. Projecting `MAX(lastUpdate)` today would anchor every PO's `lastErrorAt` at 00:00 of the error date; against a 240-minute interval that defers POs only between 00:00 and 04:00 local and is inert the other twenty hours — worse than no deferral and impossible to explain to an operator.

D-ITEM-03 states the resolution path: it must land **together** with CR-04's `ALTER TABLE`, because either alone delivers nothing (projection-only gives the degenerate 4-hours-a-day deferral; column-widening alone widens something nothing reads).

**Consequence for this phase:** RETRY-S2 lands in full (payments). The PO half of RETRY-S4 is structurally correct but behaviourally inert until CR-04.

## D-04 restated for the deploy notes

> A `[RETRY-DEFER]` line printing `nextEligibleAt=2026-07-28T14:30:00.000Z` means **14:30 Mexico time**, not 08:30.

Both operands live in "server-local wall clock labelled UTC" space, so `.toISOString()` renders server-local time carrying a `Z` suffix. Anyone converting from the `Z` lands six hours off in the wrong direction. Documented rather than corrected on purpose — the `[RETRY*]` label field order is anchored by `^...$` regexes in these suites, so the log line itself must not change.

Post-deploy, the observable success signal is: `[RETRY-DEFER]` lines actually appear for payments inside the 30-minute interval, and **no** `[RETRY-CLOCK]` warn is present.
