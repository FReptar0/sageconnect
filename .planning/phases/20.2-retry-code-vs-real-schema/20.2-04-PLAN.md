<objective>
Complete the single-clock migration across the three operator tools: `retry-month-pos.js`,
`retry-month-payments.js` and `po-cron-diagnostic.js`. Each builds its own query, so each needs its own
`GETDATE() AS dbNow` source (CONTEXT: "Each needs its own `dbNow` source because each builds its own
query").

Purpose: these tools exist to tell an operator what the cron will do. Phase 20.1 D-01 put the
eligibility rule in one shared helper precisely so the diagnostic's verdict cannot diverge from the
cron's behaviour. If the controllers move to the server clock (plan 20.2-03) and the scripts stay on the
Node clock, that divergence returns through the back door — with a 360-minute offset the diagnostic would
report "lista para reintentar" for a PO the cron defers.

Output: three operator tools consistent with the cron's clock basis, plus SQL-shape coverage in the two
script suites.

Decisions implemented (CONTEXT traceability) — D-01: `now` comes from `GETDATE() AS dbNow` in the same
SELECT · D-05: `GETDATE()` is a per-statement runtime constant, so one `dbNow` per run and no intra-batch
drift · D-08: the diagnostic's `buildErrorStatsApply` call was already updated in plan 20.2-01; the
`dbNow` edit here lands in a **different block** of the same file.

**The trap this plan exists to avoid** (PATTERNS Q6): in `po-cron-diagnostic.js` the D-06 edit and the
D-01 edit are in different places. Block r4 (L165-188) calls `buildErrorStatsApply` but selects only
`COUNT(*) AS RowsCronWouldSee` and never references `ef.*`. Block r6 (L228-240) is a hand-written
error-stats query and is what actually supplies `lastErrorAt` to `computeRetryEligibility` at L248-252.
Anyone adding `dbNow` by walking `buildErrorStatsApply` call sites patches r4 — the wrong query — and
leaves the diagnostic on the Node clock while reporting itself fixed.
</objective>
