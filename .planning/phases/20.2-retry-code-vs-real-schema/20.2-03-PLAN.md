<objective>
Put both cron controllers on a single clock: add `GETDATE()` as a `dbNow` column to the same SELECT that
produces `lastErrorAt`, resolve it once per batch, and pass it as `now` to `computeRetryEligibility`.
With plan 20.2-01's fragment fix already in place, this also makes the payment cron query executable end
to end, so RETRY-S2 lands here.

Purpose: `lastErrorAt` is written server-local via `GETDATE()` but read back as UTC —
`tedious@18.6.1` defaults `useUTC: true` and `SQLServerConnection.js:14` overrides only
`trustServerCertificate`. Measured on `ZCL-SQL-01`: `DATEDIFF(mi, GETUTCDATE(), GETDATE())` = **-360**.
Since 360 minutes exceeds both configured intervals (240 PO, 30 payment), every candidate always looks
eligible and `[RETRY-DEFER]` can never fire. Taking `now` from the same statement makes any driver-level
timezone reinterpretation apply identically to both operands so it cancels out of the subtraction.

Output: two controllers whose retry verdict is skew-proof, plus integration tests whose fixtures derive
from `dbNow` (per hazard H-2, fixtures that do not set `dbNow` prove nothing) and a `[RETRY-CLOCK]`
observability line for the one failure mode the helper cannot detect.

Decisions implemented (CONTEXT traceability) — D-01: `now` comes from `GETDATE() AS dbNow` in the same
SELECT · D-03: SQL-side `DATEDIFF` was considered and rejected; do not reintroduce it · D-05: `GETDATE()`
is a per-statement runtime constant, so one `dbNow` per tick and no intra-batch drift · D-12 #1: the
SQL-shape test is the only thing that catches removal of the `dbNow` column.
</objective>

  <context>
    **The finding (hazard H-4, discovered during planning, present in neither SPEC, CONTEXT nor PATTERNS).**
    `PortalOC_Creator.js` joins the error-stats `OUTER APPLY` at L177 but never selects `ef.errorCount` or
    `ef.lastErrorAt` into its projection. The filter at L215-226 therefore reads `row.lastErrorAt === undefined`
    on every row. `computeRetryEligibility` fails open on a falsy `lastErrorAt`, so **every PO has always been
    ruled eligible**: `[RETRY-DEFER]` has never been able to fire for POs, and `attempts=` would always read 0.
    The OUTER APPLY runs and its result is discarded. `PortalPaymentController.js:60-61` does project both
    columns, so the payment side is unaffected.

    **Why it went unnoticed.** The `PortalOC_Creator.cron-where` suite passes because its mocked recordset
    supplies `lastErrorAt` directly (L100-104) — a row shape the real query cannot produce.

    **Decision taken by the developer on 2026-07-27: DEFER.** Do NOT project the columns in this phase.
    Rationale: `fesaOCFocaltec.lastUpdate` is typed `date`, so `MAX(lastUpdate)` carries no time of day.
    Projecting it today would anchor every PO's `lastErrorAt` at 00:00 of the error date, making a 240-minute
