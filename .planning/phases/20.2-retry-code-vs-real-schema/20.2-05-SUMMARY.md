## The payments EOM query, as shipped

The `OUTER APPLY` after the deletion — it now selects **only** a count:

```sql
        OUTER APPLY (
            SELECT
                COUNT(*) AS errorCount
            FROM fesa.dbo.fesaPagosFocaltec
            WHERE NoPagoSage = P.DOCNBR
              AND idCia = 'COPDAT'
              AND status NOT IN ('PAID', 'PARTIAL')
        ) AS ef
```

**What was deleted (two references, both to columns that do not exist):**

```sql
                COUNT(*) AS errorCount,
                (SELECT TOP 1 responseAPI FROM fesa.dbo.fesaPagosFocaltec     -- column absent
                 WHERE NoPagoSage = P.DOCNBR AND idCia = '${tenantDb}'
                 ORDER BY lastUpdate DESC) AS lastError                        -- column absent
```

plus the outer SELECT-list item `ef.lastError AS lastError` and the trailing comma on `COALESCE(ef.errorCount, 0) AS attempts`.

**Full payments SELECT list as emitted today** — four items, all schema-valid:

```sql
        SELECT
            '${tenantDb}' AS tenant,
            RTRIM(P.DOCNBR) AS idOrPo,
            P.AUDTDATE AS fechaAuth,
            COALESCE(ef.errorCount, 0) AS attempts
```

**Everything else survived verbatim:** the `FROM APBTA B` / `JOIN BKACCT` / `JOIN APTCR` chain, the `status NOT IN ('PAID', 'PARTIAL')` predicate, the outer `WHERE` (`PAYMTYPE = 'PY'`, `BATCHSTAT = 3`, `ERRENTRY = 0`, `RMITTYPE = 1`), the `buildScopeWhere({ scope: 'current_month' })` call, and the `P.DOCNBR NOT IN (SELECT NoPagoSage ...)` dedupe.

The only columns this query now reads from `fesa.dbo.fesaPagosFocaltec` are **`NoPagoSage`, `idCia` and `status`** — three of the four that exist. `idFocaltec` is not needed here.

## The footnote, exactly as adopted

```html
<p><em>Nota: el sistema de control todavía no registra el detalle del error de cada pago, por lo que esta tabla no incluye una columna de descripción de error.</em></p>
```

One sentence, Spanish, hardcoded, zero interpolation — so it needs no `escapeHtml` and adds no injection surface.

**It renders in BOTH payments cases — populated and "Sin pendientes" — by deliberate placement outside the empty/populated `if/else`.** The reasoning is the whole point of the plan: the empty case is exactly the case an operator misreads. A month-end email that says "Sin pendientes" with no further comment invites the conclusion "nothing failed"; the same email with the footnote invites the correct conclusion, "nothing is *listed*, and here is one thing this report structurally cannot tell you". It never renders for POs.

**Wording deviation from the plan's suggestion** — see Deviations below. The plan proposed ending the sentence with `...no incluye la columna "Último error".` That quotes the very header the same task removes, and the plan's own acceptance criterion requires the payments output **not** to match `/Último error/`. Adopted wording carries the identical meaning without the literal, so `not.toMatch(/Último error/)` remains a real proof that the column is gone rather than an artefact of phrasing.

## CR-03 remains deferred

Nothing writes `status='ERROR'` for payments, and `fesa.dbo.fesaPagosFocaltec` has no column that could hold an error message or an error time. Recording payment failures needs a **design decision**, not a fix — and it is complicated by the payment dedupe (`P.DOCNBR NOT IN (SELECT NoPagoSage ...)`) having no status filter, so inserting an ERROR row would exclude that payment permanently. That is why it sits in the SPEC's out-of-scope list.

**The footnote is the visible pressure D-10 asked for.** It appears in every month-end payments email until CR-03 lands.

**When CR-03 does land, restoring the column is a two-line change in these same two files:**

1. `src/background.js` — re-add the error-description sub-select to the payments `OUTER APPLY` (naming whatever column CR-03 creates) and re-add the matching `ef.lastError AS lastError` SELECT item.
2. `src/utils/EomNotification.js` — delete the `if (isPos)` / `else` split on the header and row template, and delete the `if (!isPos)` footnote push.

The tests then invert symmetrically: the payments negative assertions become positive, and the column-count expectations go from 5/10 to 6/12.
