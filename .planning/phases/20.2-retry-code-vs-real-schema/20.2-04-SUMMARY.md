## Why this plan exists

These tools exist to tell an operator what the cron will do. Phase 20.1 D-01 put the eligibility rule in one shared helper precisely so a preview cannot diverge from the cron's behaviour. Plan 20.2-03 moved the controllers to the server clock; leaving the scripts on the Node clock would have reintroduced that divergence through the back door — at 360 minutes of skew, `retry-month-pos.js` would print "lista para reintentar" for a PO the cron defers.

## The projections

All three use the same form (all three files are 4-space, unbracketed aliases):

```sql
GETDATE() AS dbNow
```

- `retry-month-pos.js` — after `ef.lastErrorAt` in the sweep SELECT
- `retry-month-payments.js` — same position
- `po-cron-diagnostic.js` — block **r6**, immediately after `MAX(lastUpdate) AS lastErrorAt`

Batch resolution is identical in both sweeps:

```js
const dbNow = recordset.length > 0 ? recordset[0].dbNow : null;
if (recordset.length > 0 && !dbNow) {
    logGenerator(LOG_FILE, 'warn', `[RETRY-CLOCK] tenant=${tenantDb} dbNow=missing fallback=node-clock`);
}
```

One line per sweep per tenant, never per row.

## The `GROUP BY` trap

`retry-month-pos.js` is the only one of the three with a `GROUP BY`. `dbNow` is deliberately **not** in it:

```sql
        -- La columna dbNow queda deliberadamente FUERA del agrupamiento de abajo.
        -- SQL Server trata GETDATE() como constante de runtime, no como referencia a columna,
        -- así que es legal en el SELECT de una consulta agrupada sin listarla. No lo "arregles".
        GROUP BY A.PONUMBER, ef.errorCount, ef.lastErrorAt
```

Adding it would turn a runtime constant into a grouping key and change the result cardinality. The SELECT reads as though the column belongs in the clause, so this is guarded twice: the comment above, and `expect(sqlPassed).not.toMatch(/GROUP BY[^\n]*dbNow/)` in the suite.

## r6, not r4 — the diagnostic trap

`po-cron-diagnostic.js` has two queries against `fesaOCFocaltec`:

| Block | Lines | What it selects | Feeds eligibility? |
|---|---|---|---|
| r4 | 164-192 | `COUNT(*) AS RowsCronWouldSee` — calls `buildErrorStatsApply` but reads no `ef.*` | **No** |
| r6 | 224-263 | hand-written `COUNT(*)` + `MAX(lastUpdate) AS lastErrorAt` | **Yes** |

Block r4 is the one that *looks* like the error-stats query, because it calls the shared builder. Patching it would have passed a casual review and changed nothing. Confirmed r4 does not appear in the diff at all — it also still carries the old `status = 'POSTED'` dedupe recorded as D-ITEM-01 in phase 20.1, which stays out of scope.

`MAX(lastUpdate)` is untouched: `fesaOCFocaltec` genuinely has that column. Only `fesaPagosFocaltec` does not.

Section 6's `console.table` gained `dbNow` as a fifth column, rendered as an ISO string, with the D-04 warning in a comment beside it.

## The skew fixtures

Both suites gained `SERVER_SKEW_MIN = 360` and `DB_NOW = Date.now() - skew`. Every `lastErrorAt` derives from `DB_NOW`; the only remaining `Date.now() - ` in either file is the `DB_NOW` definition itself (verified: `grep -c` returns exactly 1 per file, and it is that line).

`retry-month-pos.js`'s existing `totalDeferred: 1` assertion became the skew proof without being edited. Verified by executing the helper against both clocks for the in-interval row, 240-minute interval:

## Deviations from Plan

**[Rule 1 — proxy criterion] Two acceptance-criterion greps tripped on my own comments; both comments were reworded.**

Found during: Task 1 and Task 2 verification.

1. Task 1's criterion `grep -n 'GROUP BY' src/scripts/retry-month-pos.js | grep -c dbNow` must return `0`. It returned `1` — the explanatory comment I placed above the clause read "dbNow NO va en el GROUP BY", putting both tokens on one line. The clause itself was already clean.
   Fix: reworded so `dbNow` and `GROUP BY` never share a line ("La columna dbNow queda deliberadamente FUERA del agrupamiento de abajo."). Re-run returns `0`.

2. Task 2's criterion `grep -A1 'MAX(lastUpdate) AS lastErrorAt' … | grep -c 'GETDATE() AS dbNow'` must return `1`. It returned `0` — I had written a three-line block comment between the two SELECT items, breaking the adjacency the criterion checks. The plan had asked for a *one-line* comment.
   Fix: collapsed to a trailing one-line comment on the `GETDATE()` line itself, restoring adjacency and matching what the plan specified. Re-run returns `1`.

Both are the same class as the `[RETRY-DEFER]` rewording in plan 20.2-03: a grep-based proxy cannot tell a comment from the construct it guards. In every case rewording was preferred over documenting an exception, so the proxy keeps its value for the next reader.

Verification: `SWEEPS_OK` and `DIAG_R6_OK` both emitted after the rewordings.

**Total deviations:** 2 auto-fixed, both comment rewordings. **Impact:** none on shipped behaviour.
