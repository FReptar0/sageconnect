The original defect lived in `src/background.js`, which hand-writes its own `OUTER APPLY` and is unreachable by following `buildErrorStatsApply` call sites. ## Why statement-scoped rather than file-level

A naive "file contains both tokens" check is permanently red on exactly two files:

| File | Why it contains both | Verdict |
|---|---|---|
| `src/background.js` | POs branch selects `responseAPI` and orders by `lastUpdate` — against `fesaOCFocaltec`, which genuinely has both (D-11) | legitimate |
| `src/utils/RetryPolicy.js` | payments-table mentions are JSDoc prose; `MAX(lastUpdate)` is real OC-branch code | legitimate |

Two mechanisms separate signal from noise, and each handles one file:

1. **Block-comment stripping** removes `RetryPolicy.js`'s payments-table mentions entirely, so the file cannot violate regardless of its code lines. Comments are blanked with spaces rather than deleted so line numbers survive.
2. **A 12-line proximity window** around each payments-table reference separates `background.js`'s two branches.

The window is justified by measurement: `background.js`'s nearest legitimate `lastUpdate` (L472, POs branch) sits **37 lines** from its nearest payments-table reference in code (L509) — ~25 lines of margin at `WINDOW = 12`.

`ALLOWED_FILES` therefore ships **empty**. That is the design goal: an exemption list with entries invites the next person to add one rather than fix the query. It is documented as a hook so a genuinely legitimate future case has an obvious home, instead of tempting someone to widen `IMPOSSIBLE_COLUMNS` or shrink `WINDOW` — either of which disarms the guard everywhere at once.
