<decisions>
## Implementation Decisions

### Single-clock source

- **D-01:** The "now" used for retry eligibility comes from **a `GETDATE() AS dbNow` column added to the same SELECT** that produces `lastErrorAt`, passed into `computeRetryEligibility` as `now`. Both operands then originate from the same server, so any driver-level timezone reinterpretation applies identically to both and cancels out of the subtraction.
- **D-02:** `computeRetryEligibility`'s contract is **unchanged** — it keeps taking `{ lastErrorAt, intervalMinutes, now }` and returning `{ eligible, nextEligibleAt }`. This preserves D-01 from Phase 20.1 (eligibility lives in exactly one place) and keeps `nextEligibleAt` derivable for the `[RETRY-DEFER]` operator log without new SQL interpolation.
- **D-03:** The rejected alternative was having SQL compute `DATEDIFF(mi, ef.lastErrorAt, GETDATE())` and letting the helper compare integers. It is more robust (immune to DST and to future driver changes) but reconstructing `nextEligibleAt` would require either interpolating the interval into the SQL string or recomputing it in JS — added surface area in a fix whose purpose is to *reduce* risk. Revisit if CR-04's `ALTER TABLE` ever lands.
- **D-04:** **Known consequence to document in the code and the SUMMARY:** because both operands live in "server-local wall clock labelled UTC" space, the `nextEligibleAt` printed by `[RETRY-DEFER]` via `.toISOString()` renders server-local time with a `Z` suffix. Operators must read it as Mexico time, not UTC. Accepted deliberately over a more convoluted calculation.
- **D-05:** `GETDATE()` in a SELECT list is a runtime constant — evaluated **once per statement**, not per row — so every row in a tick shares an identical `dbNow`. No intra-batch drift.

### buildErrorStatsApply signature

- **D-06:** The timestamp-column selector is a **required parameter that throws when absent**, not an optional parameter with a default. `CLAUDE.md` §6 pitfall #2 records that PR #16 changed a shared util's implicit default and silently broke 7 callers, which PR #19 had to repair. An optional `timestampColumn: 'lastUpdate'` default would recreate exactly that pattern — correct for OCs, silently invalid for payments.
- **D-07:** Throwing on a missing/unknown argument mirrors the posture `getRetryIntervalMinutes` already established in Phase 20.1 (it throws on an unknown `docType`). Keep the two helpers behaviourally consistent.
- **D-08:** All **5 call sites** must be updated to state their table shape explicitly: `PortalPaymentController.js` and `retry-month-payments.js` (payments — no timestamp column), `PortalOC_Creator.js`, `po-cron-diagnostic.js` and `retry-month-pos.js` (OCs — `lastUpdate`). This forced audit is the point of the required parameter.
- **D-09:** **`background.js` does NOT call the helper** — it hand-writes its own `OUTER APPLY` at L492-502 with the same defect, plus a `responseAPI` sub-select and an `ORDER BY lastUpdate` at L495-497. It is a **sixth** emission site and must be fixed separately; a planner that only follows `buildErrorStatsApply` call sites will miss it.

### EOM payments email

- **D-10:** The error-description column is **removed from the payments table**, not filled with a placeholder. A column that always reads "no registrado" trains the operator to ignore it and normalises the gap; a single footnote stating that payment error detail is not recorded yet tells the truth once and keeps visible pressure to resolve CR-03.
- **D-11:** The POs table is **unchanged** — `responseAPI` genuinely exists on `fesaOCFocaltec` and carries real data. The two tables are deliberately asymmetric.

### Test strategy

- **D-12:** Three complementary tests, because each catches a regression the others cannot:
  1. **SQL-shape test** — catches removal of `GETDATE() AS dbNow` from the SELECT (the data stops being provided).
  2. **Helper test with an injected `now`** — catches a revert to `new Date()` (the data is provided but ignored). Must use values that a 360-minute skew would wrongly rule eligible.
  3. **Schema-guard test** — repo-wide assertion that nothing under `src/` selects `lastUpdate` or `responseAPI` from `fesa.dbo.fesaPagosFocaltec`. This is the long-lived net: it covers files this phase never touches.
- **D-13:** All verification is structural — there is no local Sage DB. Live behaviour stays a post-deploy observation.

### Claude's Discretion

- Exact parameter name and shape for the timestamp-column selector on `buildErrorStatsApply` (D-06 fixes the *semantics*: required, throws when absent).
- Exact wording of the EOM footnote (D-10 fixes the *intent*: state the gap once, honestly).
- Which existing test file hosts each of the three tests in D-12.
- Whether the schema-guard test reads files directly or asserts on the generated fragments.

<specifics>
## Specific Ideas

- The measured evidence is the anchor: `DATEDIFF(mi, GETUTCDATE(), GETDATE())` on `ZCL-SQL-01` returned **-360** (server local `12:48:32`, UTC `18:48:32`). Any fix must be provably correct at that offset, and the D-12 helper test must use fixture values that a 360-minute skew would wrongly rule eligible.
- Real production status distributions, for anyone reasoning about blast radius: `fesaOCFocaltec` = `CLOSED 4498 / ERROR 3313 / POSTED 1198 / CANCELLED 18 / OPEN 5`; `fesaPagosFocaltec` = `PAID 2678 / PARTIAL 27 / SYNCED 3 / REVERTED 2`, **zero `ERROR`**.
- `SYNCED` and `REVERTED` appear nowhere in `src/` — provenance unknown (manual edits or an older tool). Only 5 rows, but worth knowing that the EOM query's `status NOT IN ('PAID','PARTIAL')` predicate currently matches exactly those 5 non-error rows.

</specifics>

## Deferred Ideas

- **CR-04 — restore the 240-minute PO interval.** Requires an `ALTER TABLE` (both `lastUpdate` and `createdAt` are `date`). Deliberately deferred until it is measured whether RETRY-C7 alone stops the portal hammering — a production schema change is not justified on a hypothesis. Blocked in practice by SQL access pending an IT request to Alan and Jorge.
- **CR-03 — record payment failures.** Needs a design decision, not a fix: where the failure is recorded and how, given that the payment dedupe (`P.DOCNBR NOT IN (SELECT NoPagoSage …)`) has no status filter, so a naive `ERROR` row would exclude that payment permanently.
- **The 23 uncovered control rows** — `CANCELLED` (18) and `OPEN` (5) match neither side of the RETRY-C7 dedupe. `CANCELLED` is a pre-existing gap (identical before and after RETRY-C7). **`OPEN` semantics are unknown and must be asked, not guessed.**
