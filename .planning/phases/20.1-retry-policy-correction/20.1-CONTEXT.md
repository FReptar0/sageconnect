<decisions>
## Implementation Decisions

### Retry eligibility (helper shape)
- **D-01:** A **single shared eligibility helper** in `src/utils/RetryPolicy.js` encapsulates the whole retry-eligibility rule — first attempt (no `lastErrorAt`) → eligible immediately; row with `lastErrorAt` → eligible when `now − lastErrorAt ≥ intervalMinutes` (`≥` inclusive). Both controllers **and** `po-cron-diagnostic.js` call it, so the first-attempt rule (RETRY-C4, highest blast radius) cannot diverge between call sites. Replaces `computeBackoffWaitMinutes`. Suggested shape (final naming left to the plan): `getRetryIntervalMinutes(intervalConfig, docType)` → `number`, plus `computeRetryEligibility({ lastErrorAt, intervalMinutes, now })` → `{ eligible: boolean, nextEligibleAt: Date|null }` (returns `{ eligible: true, nextEligibleAt: null }` when `lastErrorAt` is null). Honors Phase 20 D-01/D-05 (JS post-filter + pure `RetryPolicy.js` helpers as single source of truth).

### Config namespace
- **D-02:** **Nested** `config.retry.interval.{payment, po}` — mirrors the `config.retry.backoff.{initialMin,multiplier,maxMin}` it replaces and keeps symmetry with the other `config.retry.*` sub-namespaces. Env vars `RETRY_INTERVAL_PAYMENT_MIN` (default 30, guard [10,60]) and `RETRY_INTERVAL_PO_MIN` (default 240, guard [30,1440]); guards placed adjacent to their `parseInt` lines, same pattern as the timeout guards at `src/config.js:186-208`. The `config.retry.backoff` namespace is removed.

### Obsolete env var handling
- **D-03:** `[CONFIG WARN]` via `console.warn` at config load, driven by a list of removed names (`RETRY_BACKOFF_INITIAL_MIN`, `RETRY_BACKOFF_MULTIPLIER`, `RETRY_BACKOFF_MAX_MIN`) — one warn per detected var, the message names it and points to `RETRY_INTERVAL_PAYMENT_MIN` / `RETRY_INTERVAL_PO_MIN`. Non-fatal (inert). `console.warn` matches the `[CONFIG ERROR]` `console.error` convention (winston is not available at config-load time). Implements SPEC RETRY-C3's uptime-preserving behavior.

### Inherited from Phase 20 (honored for consistency)
- **D-04:** Retry eligibility stays in the **JS post-filter**, not the SQL WHERE (Phase 20 D-01). The cron query keeps `buildScopeWhere` (scope) + POSTED `NOT EXISTS` dedupe + `buildErrorStatsApply` OUTER APPLY (errorCount + lastErrorAt). `errorCount` is now used **only** for operator logging (`attempts=`), never for interval math.
- **D-05:** Log labels rename `[BACKOFF-DEFER]` → `[RETRY-DEFER]` and `[BACKOFF]` → `[RETRY]`, keeping the exact field shape (per-row `[RETRY-DEFER] PO ${id} tenant=${db} attempts=${n} nextEligibleAt=${ts}`; summary `[RETRY] tenant=${db} candidates=${X} deferred=${Y} processing=${Z}`) so operators keep the same grep ergonomics (Phase 20 D-13).
- **D-06:** `po-cron-diagnostic.js` Section 6 verdict-priority adapted from Phase 20's order, dropping backoff language: (1) POSTED → "ya está procesada"; (2) ERROR + within interval → "esperando reintento hasta ${nextEligibleAt}"; (3) ERROR + past interval → "lista para reintentar en el próximo tick"; (4) zero fesa rows → "nunca intentada, entra en el próximo tick"; (5) outside `RETRY_SCOPE` → "fuera de scope, ignorada".
- **D-07:** Q1 is a **default flip only** — `buildScopeWhere` is not restructured (it already supports `last_n_days`). Default `RETRY_SCOPE` → `last_n_days`, applied uniformly to POs (`dateField='Fecha'`) and payments (`dateField='P.AUDTDATE'`); `current_month` stays env-selectable.
- **D-08:** Tests keep Phase 20's two-layer shape (D-12): unit tests in `tests/utils/RetryPolicy.test.js` (fixed-interval helper + scope fragment + eligibility) and integration tests in `tests/controller/*.cron-where.test.js` (`jest.mock` `runQuery`, four cases per controller: POSTED skip, ERROR-in-interval skip, ERROR-past-interval include, **first-attempt include**). All geometric-curve assertions deleted.
- **D-09:** The EOM dispatch path (Phase 20 D-09) hardcodes `current_month` independently of `config.retry.scope`, so flipping the default to `last_n_days` does not affect it. EOM/Q3 is out of scope for this phase regardless.

### Claude's Discretion
- **D-01 and D-02 were delegated to Claude** — the user stated they lack the background to choose ("no tengo conocimiento, el senior se fue"). Claude picked the shared-helper option (D-01) for safety (RETRY-C4 blast radius) and the nested namespace (D-02) for codebase symmetry; both rationales recorded above so the planner and any future maintainer understand the "why".
- Exact helper/function names and file-internal structure — planner/executor finalize.
- Whether `errorCount` continues to surface as `attempts=` in logs — recommended **yes** (operator visibility), even though it no longer drives timing.
- `.env.example` ordering and comment wording.

## Specific Ideas

- Payments fixed at **30 min** (client, 20-May); POs **240 min** default (team, 11-Jun) — both env-tunable without redeploy, differentiated by document type.
- **First-attempt (no prior ERROR) MUST stay immediately eligible** — this is the highest-blast-radius regression to guard against (a wrong interval check would defer *normal* uploads and stall the whole cron). It is the reason D-01 centralizes eligibility in one helper.
