**Both cron controllers now decide retry eligibility through the shared fixed-interval helper — POs at 240 min, payments at 30 min — with the first-attempt rule removed from the call sites so it exists in exactly one place, and the OC dedupe widened to exclude CLOSED as well as POSTED.**

## Accomplishments

- The "a first upload is not a retry" rule (RETRY-C4, the phase's highest blast radius) now lives only inside `computeRetryEligibility`. Neither controller re-implements it, so a never-failed PO or payment cannot be wrongly deferred by a call site drifting from the helper.
- PO eligibility is evaluated against `config.retry.interval.po` (240 min) and payment eligibility against `config.retry.interval.payment` (30 min) — the differentiation the 2026-06-11 team session asked for, replacing a single shared geometric curve.
- **RETRY-C7 shipped:** the OC `NOT EXISTS` dedupe reads `status IN ('CLOSED', 'POSTED')`. Combined with the rolling 30-day scope from plan 01, this is what stops closed OCs being re-selected into a 409 → ERROR loop.
- `[BACKOFF-DEFER]` / `[BACKOFF]` are gone from both controllers; `[RETRY-DEFER]` / `[RETRY]` carry the identical field order so operator greps keep working.
- Both integration suites went from 3 cases asserting the rejected geometric behavior to 4 cases asserting the four eligibility outcomes, with the first-attempt case covered for the first time.

## Exact post-filter shape adopted

### `src/controller/PortalOC_Creator.js`

```js
const candidatesCount = recordset.length;
const now = new Date();
const intervalMin = getRetryIntervalMinutes(config.retry.interval, 'po');
const deferred = [];
recordset = recordset.filter((row) => {
    const { eligible, nextEligibleAt } = computeRetryEligibility({
        lastErrorAt: row.lastErrorAt,
        intervalMinutes: intervalMin,
        now,
    });
    if (!eligible) {
        deferred.push({ id: row.EXTERNAL_ID, attempts: row.errorCount || 0, nextEligibleAt });
        return false;
    }
    return true;
});
```

### `src/controller/PortalPaymentController.js`

Identical structure; the only differences are the doc type, the id field, and the underscore-prefixed local names that already existed in this controller:

```js
const _intervalMin = getRetryIntervalMinutes(config.retry.interval, 'payment');
...
```

Both imports became `const { buildScopeWhere, buildErrorStatsApply, getRetryIntervalMinutes, computeRetryEligibility } = require('../utils/RetryPolicy');`.

`getRetryIntervalMinutes` is hoisted **out** of the filter callback in both controllers — it is a constant for the whole tick, and calling it per row would only add a throw site inside a hot loop.

## Final `[RETRY*]` label strings

Byte-for-byte, as emitted:

```
[RETRY-DEFER] PO ${d.id} tenant=${databases[index]} attempts=${d.attempts} nextEligibleAt=${d.nextEligibleAt.toISOString()}
[RETRY] tenant=${databases[index]} candidates=${candidatesCount} deferred=${deferred.length} processing=${recordset.length}

[RETRY-DEFER] Pago ${d.id} tenant=${database[index]} attempts=${d.attempts} nextEligibleAt=${d.nextEligibleAt.toISOString()}
[RETRY] tenant=${database[index]} candidates=${_candidatesCount} deferred=${_deferred.length} processing=${payments.recordset.length}
```

Rendered example an operator will see on the server:

```
[RETRY-DEFER] PO PO0083449 tenant=COPDAT attempts=1 nextEligibleAt=2026-07-27T20:55:29.000Z
[RETRY] tenant=COPDAT candidates=1 deferred=1 processing=0
```

Field order and separators are unchanged from the `[BACKOFF*]` pair — only the label token differs, so an existing `grep 'tenant=COPDAT candidates='` keeps matching (D-05).

`nextEligibleAt.toISOString()` is safe without a null guard: `computeRetryEligibility` returns `nextEligibleAt: null` **only** together with `eligible: true`, and the deferral branch is reached only when `eligible` is false. Verified against the plan-01 contract and the helper source, not assumed.

## Fixture windows chosen

| Suite | Case | Fixture | Why |
|---|---|---|---|
| PO | ERROR inside interval | `lastErrorAt` = 5 min ago | Well inside 240 min; also mirrors the old suite so the deferral case is a clean like-for-like |
| PO | ERROR past interval | `lastErrorAt` = **250 min ago** (`PO_INTERVAL_MIN + 10`) | Must exceed 240 min. The old 20-min fixture only cleared the removed 15-min geometric first step and would now *defer* |
| Payment | ERROR inside interval | `lastErrorAt` = 5 min ago | Well inside 30 min |
| Payment | ERROR past interval | `lastErrorAt` = **40 min ago** (`PAYMENT_INTERVAL_MIN + 10`) | Must exceed 30 min; the old 20-min fixture would now defer |
| Both | First attempt | `errorCount: 0`, `lastErrorAt: null` | RETRY-C4 — never-failed document must lift on this tick |

Both suites derive the past-interval fixture from a named constant (`PO_INTERVAL_MIN` / `PAYMENT_INTERVAL_MIN`) that mirrors the config mock, so the `+10 min` margin stays correct if the interval default is ever retuned.

## Decisions Made

- **Deleted the `errorCount <= 0` short-circuit rather than keeping it as a fast path.** It is behaviorally equivalent to the helper's first-attempt branch *today*, which is exactly why leaving it is dangerous: two copies of a rule that agree now are two copies that can disagree after the next edit. D-01 exists to make that impossible. The cost is one extra function call per row on a recordset that is already bounded by the 30-day scope.
- **`attempts: row.errorCount || 0`** instead of `row.errorCount`. Previously the deferral branch was only reachable when `errorCount >= 1`, so the raw value was always a number. Now a row can be deferred with `errorCount` absent (an ERROR row exists but the OUTER APPLY column came back null/undefined), which would have rendered `attempts=undefined` in the operator log. `|| 0` keeps the field numeric.
- **`getRetryIntervalMinutes` hoisted out of the filter callback.** It throws on an unknown `docType`; inside the callback that throw would fire per row and inside a `.filter()`, which is a worse failure shape than once per tick.
- **Kept `scope: 'current_month'` in both config mocks.** The suites assert `DATEFROMPARTS|DATEADD(month` SQL shape; flipping the mock to `last_n_days` would have silently voided those assertions. The default flip itself is proven in `tests/utils/RetryPolicy.test.js` (plan 01), which is the right layer for it.
- **Named interval constants in the test files** (`PO_INTERVAL_MIN`, `PAYMENT_INTERVAL_MIN`) with fixtures computed as `interval + 10`, rather than bare `250`/`40` literals — so the "must exceed the interval" intent survives a future retune of the defaults.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Cross-test stub leakage in both cron-where suites**

- **Found during:** Task 2, RED gate.
- **Issue:** Both suites used only `jest.clearAllMocks()` in `beforeEach`. `clearAllMocks()` clears call records but does **not** drain queued `mockResolvedValueOnce` / `mockResolvedValue` implementations. A test whose stubs the controller does not fully consume leaks the remainder into the next test. **This was not theoretical — the RED run proved it:** the payment past-interval case aborted early (the removed symbol threw inside `uploadPayments`'s outer `try`), left two `{ recordset: [] }` stubs queued, and the first-attempt case then asserted against a leaked empty recordset, reporting `candidates=0` instead of the row it defines. A test that silently grades the wrong input is worse than a failing one, and the first-attempt case is precisely the one the SPEC calls highest-blast-radius.
- **Fix:** added `mockRunQuery.mockReset()` + `mockPortalPost.mockReset()` to `beforeEach` in **both** suites, with a comment recording why `clearAllMocks` is insufficient.
- **Files modified:** `tests/controller/PortalPaymentController.cron-where.test.js`, `tests/controller/PortalOC_Creator.cron-where.test.js`
- **Verification:** PO suite re-run after the change — still 4/4 green (proving the isolation does not depend on leakage); payment suite still 4/4 red at that point, i.e. the RED gate stayed honest.
- **Committed in:** `1df6259` (Task 2 RED commit). This touched a Task-1 file during Task 2; both files are inside the plan's four-file boundary, and splitting one two-line symmetrical fix across two commits would have left one suite knowingly broken in between.
