## Sweep-loop shape adopted (both scripts)

```js
const now = new Date();
const intervalMin = getRetryIntervalMinutes(config.retry.interval, 'po'); // 'payment' in the payments sweep
const eligible = [];
const deferred = [];
for (const row of recordset) {
    const errorCount = row.errorCount || 0;
    const { eligible: isEligible, nextEligibleAt } = computeRetryEligibility({
        lastErrorAt: row.lastErrorAt,
        intervalMinutes: intervalMin,
        now,
    });
    ...
    if (!row.lastErrorAt)      { entry.verdict = 'never-tried';    eligible.push(entry); }
    else if (!isEligible)      { entry.verdict = 'in-interval';    deferred.push(entry); }
    else                       { entry.verdict = 'ready-to-retry'; eligible.push(entry); }
}
```

Two details worth recording:

- **`eligible: isEligible` alias.** Both files already own `const eligible = []` as the accumulator. Destructuring the helper's boolean as `eligible` would have shadowed the array inside the loop body and silently mis-sorted every row (the plan flagged this; the alias is the guard). A comment in each file records why.
- **`getRetryIntervalMinutes` hoisted out of the loop.** It is constant for the whole sweep and it *throws* on an unknown `docType`; per-row invocation would put a throw site inside a hot loop. Same call the controllers make (plan 02).
- **First-attempt branch keyed on `lastErrorAt`, not `errorCount`.** `errorCount === 0` and "no `lastErrorAt`" agree today (both derive from the same `OUTER APPLY` over ERROR rows), but the helper's rule is the `lastErrorAt` one, and D-04 says `errorCount` must not drive timing. `errorCount` survives only as `entry.errorCount` / `attempts=` operator context.

## Decisions Made

- **The two Jest suites were migrated in the same commit as their source, not a separate `test:` commit.** With the new source and the old mock, `config.retry.interval` is `undefined` → `getRetryIntervalMinutes` returns `undefined` → `computeRetryEligibility` fails open → every row is eligible and the deferral assertions fail. A split commit would have knowingly left `master`-bound history with two red suites for one commit. There is no RED gate to preserve here (this plan is a migration, not TDD).
- **Fixtures expressed via named constants** (`PO_INTERVAL_MIN = 240`, `PAYMENT_INTERVAL_MIN = 30`, past-interval = `interval + 10` min) rather than bare `250` / `40` literals — mirrors exactly what plan 20.1-02 established in the cron-where suites, so a future retune of the defaults keeps the "must exceed the interval" intent visible.
- **The `NOT EXISTS` assertion in the pos suite was tightened, not replaced.** `expect(sqlPassed).toMatch(/NOT EXISTS/)` stays; two assertions were added — a positive `status IN ('CLOSED', 'POSTED')` and a negative `not.toMatch(/AND status = 'POSTED'/)` — mirroring how plan 02 asserted the same shape in the controller suite. The generic match alone would have passed either way, so RETRY-C7's preview half now has real coverage.
- **Verdict priorities 2/3 in the diagnostic keep their own `new Date(nextEligibleAt) > new Date()` comparison** rather than storing the helper's `eligible` boolean on the verdict. The two are exactly equivalent (the helper's boundary is `>=`-inclusive, so `!eligible ⇔ nextEligibleAt > now`), the plan scoped the change to wording, and the smaller diff is the safer one for a production operator tool. Recorded here so a future maintainer knows it was considered, not overlooked.
- **`safeRun('backoff state')` → `safeRun('retry-interval state')`.** The plan only named the heading, but that label is interpolated into the `[!] … -> ERROR:` console line and the winston entry, so leaving it would have surfaced the word "backoff" to an operator at exactly the moment something failed.
