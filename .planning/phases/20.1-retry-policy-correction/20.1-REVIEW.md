# Phase 20.1: Code Review Report

**Reviewed:** 2026-07-27T17:29:36Z
**Depth:** standard
**Files Reviewed:** 13
**Status:** issues_found

## Summary

The refactor itself is clean: `computeRetryEligibility` is well-factored, the first-attempt rule
(`!lastErrorAt → eligible`) is correct at every one of the five call sites, the `>=` boundary is
inclusive as documented, the `eligible`/`isEligible` shadowing hazard in both retry-month scripts
was handled correctly, and `nextEligibleAt.toISOString()` in the two deferred-logging branches is
genuinely unreachable-null (every early return that yields `nextEligibleAt: null` also yields
`eligible: true`). The full suite runs at the documented baseline — 7 failing tests across 6
suites, all pre-existing (`PaymentReconciliation`, `TransformTime`, `no-process-exit`,
`enforcement-wiring`, plus `config.test.js` / `operation-manager.test.js` which both die inside
`validate()` on license env vars this phase never touched). No new SQL interpolation, no new
secrets, no `runQuery` default-DB violations.

The problems are all in whether the shipped policy can actually *execute* in production:

1. **The interval never fires.** `lastErrorAt` comes back from `mssql` interpreted as UTC while
   `GETDATE()` wrote server-local time; on a UTC-6 host every ERROR row reads ~6 h older than it
   is. Both new intervals (240 min / 30 min) are smaller than that offset, so
   `now - lastErrorAt >= intervalMinutes` is always true and `[RETRY-DEFER]` can never be emitted.
   Phase 20's geometric curve still deferred at its upper steps (480/960/1440 min); flattening it
   to 240/30 is what makes the feature fully inert.
2. **RETRY-C7 is half a fix.** The dedupe now excludes `CLOSED` and `POSTED` but not `CANCELLED`,
   which `PortalOC_Canceller.js` writes over the `POSTED` row. A PO cancelled in Sage stays
   `Autorizada = 1` and inside the 30-day scope, so the cron re-uploads it.
3. **The payment half of the policy has no input.** Nothing in the codebase ever writes
   `status = 'ERROR'` to `fesaPagosFocaltec`, and the payment cron's own dedupe would permanently
   exclude such a row anyway. `ef.lastErrorAt` is structurally always `NULL`, so
   `RETRY_INTERVAL_PAYMENT_MIN`, its fail-fast `[10, 60]` guard, the `[RETRY-DEFER] Pago` log line
   and four of the payment tests all describe a state production cannot reach.

Findings 1 and 2 compound: a cancelled PO 409s, writes an ERROR row, and — because the interval
never defers — is retried on the *next* 15-min tick rather than 4 h later, for up to 30 days.

## Critical Issues

### CR-01: Retry interval never defers — `lastErrorAt` and `now` are on different clock bases

**File:** `src/utils/RetryPolicy.js:72-87` (comparison), with all five call sites affected:
`src/controller/PortalOC_Creator.js:212-226`, `src/controller/PortalPaymentController.js:120-134`,
`src/scripts/retry-month-pos.js:114-128`, `src/scripts/retry-month-payments.js:128-142`,
`src/scripts/po-cron-diagnostic.js:247-256`

**Issue:**
`lastErrorAt` is `MAX(lastUpdate)` from `fesaOCFocaltec`, and `lastUpdate` is written with
`GETDATE()` (`PortalOC_Creator.js:280, 350`) — SQL Server **local** wall-clock time.
`src/utils/SQLServerConnection.js:13-15` sets `options: { trustServerCertificate: true }` and never
sets `useUTC`; the tedious default is `useUTC: true`
(`node_modules/tedious/lib/connection.js:485`), and `readDateTime` builds the JS Date via
`Date.UTC(...)` (`node_modules/tedious/lib/value-parser.js:683-700`). So a row written at 10:00
Mexico time (16:00 UTC) is handed to Node as `2026-07-27T10:00:00.000Z`, while
`now = new Date()` on the same box is `16:00Z`.

The measured age is therefore inflated by the server's UTC offset — 6 h for `America/Mexico_City`
(`.env.example:57`, `TIMEZONE=America/Mexico_City`; the payment query's own
`DATEADD(mi, DATEDIFF(mi, GETUTCDATE(), GETDATE()), ...)` at
`PortalPaymentController.js:47-59` only exists because that offset is non-zero). Both new intervals
are below 360 min:

| docType | interval | apparent age at t=0 | deferred? |
|---|---|---|---|
| po | 240 min | ≈ 360 min | never |
| payment | 30 min | ≈ 360 min | never |

Consequence: `eligible` is `true` for every row on every tick, `deferred.length` is always 0,
`[RETRY-DEFER]` is never written, and a permanently-failing PO is re-POSTed every 15 min instead of
every 4 h. This is a **regression introduced by this phase**: Phase 20's curve reached 480/960/1440
min, which still exceeded the offset, so deferral worked for attempts ≥ 6. Flattening to a fixed
240/30 removed the only steps that survived the skew. The `RetryPolicy.js:57-59` docstring frames
this as "skew between the two hosts… out of scope for 20.1", but it is not host skew — it is a
systematic driver-level timezone reinterpretation on a single host.

**Fix:** make both timestamps traverse the identical driver conversion by taking `now` from SQL
Server instead of the Node clock. Minimal, surgical, provably offset-free:

```javascript
// PortalOC_Creator.js — add to the SELECT list (same for the payment query and both sweeps)
  GETDATE()                                    as [SQL_NOW],
```

```javascript
// PortalOC_Creator.js:212-226
const now = recordset.length ? new Date(recordset[0].SQL_NOW) : new Date();
```

Alternative (preferred long-term): move the comparison into SQL so no JS clock is involved —
`AND (ef.lastErrorAt IS NULL OR ef.lastErrorAt <= DATEADD(minute, -${intervalMin}, GETDATE()))` —
and keep `computeRetryEligibility` only for the diagnostic's `nextEligibleAt` display.
Do **not** "fix" this by setting `useUTC: false` on the pool: `SQLServerConnection.js` is shared by
every query in the service and that flips date semantics repo-wide.

**Verification before/after:** run `SELECT GETDATE(), GETUTCDATE();` on the production instance —
a non-zero difference confirms the bug. After the fix, `[RETRY-DEFER]` lines must appear in
`PortalOC_Creator` logs for any PO with a recent ERROR row.

### CR-02: RETRY-C7 dedupe omits `CANCELLED` — the cron re-uploads Sage-cancelled POs

**File:** `src/controller/PortalOC_Creator.js:182-187` and `src/scripts/retry-month-pos.js:105-110`

**Issue:**
The new dedupe is:

```sql
AND NOT EXISTS (
  SELECT 1 FROM fesa.dbo.fesaOCFocaltec
  WHERE ocSage = A.PONUMBER
    AND idDatabase = '${databases[index]}'
    AND status IN ('CLOSED', 'POSTED')
)
```

`fesaOCFocaltec.status` takes exactly four persisted values: `POSTED`, `ERROR`, `CLOSED`
(`PortalOC_Closer.js:125`) and `CANCELLED` (`PortalOC_Canceller.js:100-105`). The canceller does
`UPDATE … SET status = 'CANCELLED' … WHERE status = 'POSTED'` — it **replaces** the POSTED row, so
after a cancellation no `POSTED` and no `CLOSED` row remains and `NOT EXISTS` is TRUE.

The cancelled PO is still selectable by every other clause:
- `X.Autorizada = 1` still holds — `PortalOC_Canceller.js:26-33` keys off
  `POPORL.OQCANCELED / POPORH1.ISCOMPLETE`, never `Autorizaciones_electronicas.dbo.Autoriza_OC`.
- `MAX(Fecha)` in `Autoriza_OC_detalle` is unchanged, so the PO stays inside the 30-day
  `last_n_days` window for a month.

So the cron re-POSTs a purchase order that was cancelled in Sage and cancelled in the portal, on
every eligible tick for up to 30 days. This is byte-for-byte the failure mode RETRY-C7 was written
to eliminate ("a closed OC has no POSTED row left… so a POSTED-only dedupe re-selects it and the
portal answers 409" — `tests/controller/PortalOC_Creator.cron-where.test.js:16-18`); the audit
enumerated one of the two lifecycle end-states. Best case the portal 409s and the loop only burns
ERROR rows; worst case it accepts the payload and resurrects a cancelled OC as `STATUS: 'OPEN'`
(`PortalOC_Creator.js:133`) for the supplier.

Note this is **not** covered by D-ITEM-01, which is scoped to the `po-cron-diagnostic.js` section-4
replica and discusses `CLOSED` only.

**Fix:** extend the set in both places (and in the section-4 replica when D-ITEM-01 is closed):

```sql
    AND status IN ('CANCELLED', 'CLOSED', 'POSTED')
```

and update the matching assertions:

```javascript
// tests/controller/PortalOC_Creator.cron-where.test.js:88
expect(sqlPassed).toMatch(/status IN \('CANCELLED', ?'CLOSED', ?'POSTED'\)/);
// tests/scripts/retry-month-pos.test.js:65 — same
```

Add a regression test proving a PO whose only control row is `CANCELLED` is excluded.

### CR-03: The payment retry interval is structurally unreachable — no producer of `status='ERROR'`

**File:** `src/controller/PortalPaymentController.js:112-142` (post-filter),
`src/controller/PortalPaymentController.js:389-397` (failure branch),
`src/controller/PortalPaymentController.js:72-77` (dedupe),
`src/config.js:207` + `src/config.js:258-263` (value and its fail-fast guard)

**Issue:** two independent structural blocks, either of which alone kills the feature.

1. **Nothing ever writes an ERROR row for payments.** Every writer of
   `fesa.dbo.fesaPagosFocaltec` inserts `PAID`/`PARTIAL` and nothing else —
   `PortalPaymentController.js:363`, `upload-single-payment.js:244`,
   `payment-uuid-repair.js:1134`, `portal-payments-generator.js:218`,
   `payment-reconciliation.js:464`. The controller's own failure branch
   (`PortalPaymentController.js:389-397`) logs and moves on; unlike the PO controller
   (`PortalOC_Creator.js:343-356`) it inserts nothing. So
   `buildErrorStatsApply(... status = 'ERROR')` always yields `errorCount = 0, lastErrorAt = NULL`,
   `computeRetryEligibility` always takes the `!lastErrorAt` early return, `_deferred` is always
   empty, and `[RETRY-DEFER] Pago …` can never be written.

2. **Even if an ERROR row existed, the payment could never be retried.** The cron dedupe is
   status-blind:

   ```sql
   AND P.DOCNBR NOT IN (
       SELECT NoPagoSage FROM fesa.dbo.fesaPagosFocaltec
       WHERE idCia = P.AUDTORG AND NoPagoSage = P.DOCNBR
   )
   ```

   Any control row — including a hypothetical ERROR row — excludes the payment *permanently*.
   This makes the obvious fix for (1) actively dangerous: adding an ERROR insert without also
   adding a status filter here would convert every transient payment failure into a permanent one.

Net effect: `RETRY_INTERVAL_PAYMENT_MIN = 30` (the 2026-05-20 client agreement), its fail-fast
`[10, 60]` range guard, the `.env.example` documentation, and the controller comment at
`PortalPaymentController.js:113-118` all describe behavior that cannot occur. The real payment
retry cadence is "every 15-min tick, forever" — because a failed payment leaves no control row and
is simply re-selected next tick. Two of the four tests in
`tests/controller/PortalPaymentController.cron-where.test.js` (lines 127-140, 142-168) assert
against a `lastErrorAt` value the production query can never produce, which is why this went
unnoticed.

**Fix:** pick one and make the code, the config and the tests agree.

*Option A — make payments behave like POs (matches the stated policy):*

```javascript
// PortalPaymentController.js, in the resp.status !== 200 branch (~line 389)
const respAPI = `${resp.status}: ${typeof resp.data === 'string' ? resp.data : JSON.stringify(resp.data)}`;
await runQuery(`
    INSERT INTO fesa.dbo.fesaPagosFocaltec (idCia, NoPagoSage, status, idFocaltec, lastUpdate)
    VALUES ('${database[index]}', '${hdr.external_id}', 'ERROR', NULL, GETDATE())
`, 'FESA');
```

```sql
-- and make BOTH dedupes status-aware so an ERROR row does not permanently exclude the payment
AND P.DOCNBR NOT IN (
    SELECT NoPagoSage FROM fesa.dbo.fesaPagosFocaltec
    WHERE idCia = P.AUDTORG AND NoPagoSage = P.DOCNBR
      AND status IN ('PAID', 'PARTIAL')
)
```

This also requires confirming `fesaPagosFocaltec` actually has a `lastUpdate` column (the current
INSERTs only ever write `idCia, NoPagoSage, status, idFocaltec`) — `buildErrorStatsApply` already
assumes one via `MAX(lastUpdate)`.

*Option B — delete the fiction:* drop `config.retry.interval.payment` and its guard
(`src/config.js:207, 258-263`), drop the payment post-filter (`PortalPaymentController.js:112-142`)
or reduce it to the `[RETRY]`/`[CRON]` summary lines, remove the `RETRY_INTERVAL_PAYMENT_MIN` block
from `.env.example`, and delete the two tests that assert deferral.

Option A is the one that honors the client agreement; either way this must not ship as-is.

### WR-01: `po-cron-diagnostic.js` throws away the authoritative `eligible` flag and re-derives it inline

**File:** `src/scripts/po-cron-diagnostic.js:248-252, 272, 276`

**Issue:** The whole justification for `computeRetryEligibility` (D-01, restated in the comment at
lines 244-246: "asi el veredicto del diagnostico no puede divergir de lo que el cron realmente
hace") is that one function owns the rule. The diagnostic then destructures only `nextEligibleAt`
and re-implements the comparison twice by hand:

```javascript
else if (verdict.errorCount > 0 && verdict.nextEligibleAt && new Date(verdict.nextEligibleAt) > new Date())
else if (verdict.errorCount > 0 && verdict.nextEligibleAt && new Date(verdict.nextEligibleAt) <= new Date())
```

Today the boundary happens to match the helper's `>=`, so there is no behavioral divergence — but
this is three separate `new Date()` instants (line 251, 272, 276) versus the single pinned `now`
the controllers use, and it is precisely the copy that will drift the next time the rule changes.
It also means the diagnostic cannot benefit from any fix to CR-01 applied inside the helper's
callers.

**Fix:**

```javascript
const { eligible, nextEligibleAt } = computeRetryEligibility({
    lastErrorAt, intervalMinutes: retryIntervalMin, now: new Date(),
});
verdict.eligibleNow = eligible;
// …
else if (verdict.errorCount > 0 && verdict.eligibleNow === false) { /* waiting */ }
else if (verdict.errorCount > 0 && verdict.eligibleNow === true)  { /* ready */ }
```

### WR-02: `[RETRY]` summary counts do not mean what the label implies (PO lines, pre-dedupe payments)

**File:** `src/controller/PortalOC_Creator.js:211-234`, `src/controller/PortalPaymentController.js:119-142`

**Issue:** Two distinct instances of the same operator-facing defect:

- **POs:** the recordset is one row **per PO line** — the query left-joins `POPORL B` and emits
  `LINES_*` columns with `ROW_NUMBER() OVER (PARTITION BY A.PONUMBER …)`
  (`PortalOC_Creator.js:105, 154-155`). The filter runs before `groupOrdersByNumber`
  (line 243), so `candidates=` / `deferred=` / `processing=` are line counts, and a deferred
  12-line PO emits **12 identical `[RETRY-DEFER] PO …` lines** per tick. The sibling preview
  `retry-month-pos.js:111` uses `GROUP BY A.PONUMBER`, i.e. one row per PO — so the preview and
  the cron report the same situation with numbers that differ by an order of magnitude and can
  never be reconciled by an operator.
- **Payments:** the `[RETRY]` line is emitted at line 141-142, *before* the PROVIDERID filter
  (lines 174-184) and the `queryPagosRegistrados` control-table dedupe (lines 199-202).
  `processing=N` therefore overstates what is actually uploaded, sometimes to zero.

**Fix:** for POs, count distinct `EXTERNAL_ID` for the log line and de-duplicate the
`[RETRY-DEFER]` emissions:

```javascript
const deferredPOs = new Map();     // EXTERNAL_ID -> {attempts, nextEligibleAt}
// …in the filter: if (!eligible) { deferredPOs.set(row.EXTERNAL_ID, {...}); return false; }
const candidatePOs = new Set(recordsetBefore.map(r => r.EXTERNAL_ID)).size;
const processingPOs = new Set(recordset.map(r => r.EXTERNAL_ID)).size;
logGenerator(logFileName, 'info',
  `[RETRY] tenant=${databases[index]} candidates=${candidatePOs} deferred=${deferredPOs.size} processing=${processingPOs}`);
```

For payments, move the `[RETRY]` emission below line 202 or add a second
`[RETRY] … uploading=<n>` line after the dedupes.

### WR-03: `computeRetryEligibility` fails **closed** on an unusable `now`, contradicting its own contract

**File:** `src/utils/RetryPolicy.js:82-86`

**Issue:** The docstring (lines 53-55) promises "Fails OPEN, never throws… a stuck row is invisible
and unbounded", and the guards for `lastErrorAt` and `intervalMinutes` honor that. `now` does not:

```javascript
const nowMs = (now instanceof Date ? now : new Date(now)).getTime();
return { eligible: nowMs >= nextEligibleAt.getTime(), nextEligibleAt };
```

- `now: null` → `new Date(null)` → epoch 0 → `0 >= anything` is false → **every row with a
  `lastErrorAt` is deferred forever**, and `nextEligibleAt` is a valid Date so nothing looks wrong
  in the logs.
- `now: 'garbage'` or an Invalid Date → `NaN >= x` is false → same permanent deferral.

The default parameter only fires for `undefined`, so `null` slips straight through. No current
call site passes either value, but this is an exported shared helper whose entire stated purpose is
that a row can never get stuck — and it is the exact "permanent deferral" failure this phase set
out to prevent.

**Fix:**

```javascript
const nowMs = (now instanceof Date ? now : new Date(now)).getTime();
if (!Number.isFinite(nowMs)) {
    // Same fail-open posture as an unparseable lastErrorAt: never strand a row on a bad clock.
    return { eligible: true, nextEligibleAt };
}
```

Add the matching case to `tests/utils/RetryPolicy.test.js:143-152`:
`[null, 'garbage', new Date('x')].forEach(bad => expect(computeRetryEligibility({lastErrorAt, intervalMinutes: 240, now: bad}).eligible).toBe(true));`

### WR-04: `getRetryIntervalMinutes` returns `undefined` for a malformed config, silently disabling deferral

**File:** `src/utils/RetryPolicy.js:27-39`

**Issue:** The function throws loudly for an unknown `docType` ("a programmer error worth surfacing
loudly", line 18-20) but returns `cfg.payment` / `cfg.po` unvalidated. `getRetryIntervalMinutes({}, 'po')`
and `getRetryIntervalMinutes(undefined, 'po')` both return `undefined`, which
`computeRetryEligibility` then coerces to `interval = 0` (line 77-79) — so every row becomes
eligible immediately and `nextEligibleAt` is logged as the ERROR timestamp itself. A typo in the
config key, a stale test mock, or a future `config.retry` reshape disables the whole retry policy
with **zero** signal: no throw, no log, no changed log shape. Given the codebase's history with
implicit defaults (CLAUDE.md §6 #2), the asymmetry is the wrong way round.

**Fix:**

```javascript
function getRetryIntervalMinutes(intervalConfig, docType) {
    const cfg = intervalConfig || {};
    if (docType !== 'payment' && docType !== 'po') {
        throw new Error('getRetryIntervalMinutes: invalid docType ' + docType);
    }
    const value = cfg[docType];
    if (!Number.isInteger(value) || value <= 0) {
        // config.retry.interval.* is range-guarded at boot, so this is a programmer error.
        throw new Error(`getRetryIntervalMinutes: invalid interval for ${docType}: ${value}`);
    }
    return value;
}
```
