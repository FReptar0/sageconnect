# Phase 20.1: Retry policy correction — Specification

**Created:** 2026-07-20
**Ambiguity score:** 0.15 (gate: ≤ 0.20)
**Requirements:** 6 locked
**Scope of this SPEC:** Q1 + Q2 only (Q3 alerts + cross-system retry-detection query deferred to a later amendment — see Boundaries)

## Goal

Change Phase 20's retry policy from (a) a `current_month`-default scope to a rolling 30-day window default, and (b) a geometric backoff (`15→30→60→…→1440` min) to a **fixed, document-type-differentiated retry interval** (payments 30 min, POs 240 min, both env-adjustable) — so the still-undeployed behavior matches the 2026-05-20 client agreement as refined by the team on 2026-06-11, before any deploy.

## Background

Phase 20 was built 13–15 May from the 15-May email interpretation and verified PASS-WITH-NOTES, but was **never deployed** (`master` is ~45 commits ahead of `origin/master`). The 2026-05-20 client meeting and 2026-06-11 team session closed **different** criteria on Q1 and Q2. This phase is the surgical correction. Grounded current state (verified 2026-07-20 against `master`):

- **Q1 (scope):** `src/utils/RetryPolicy.js:buildScopeWhere` **already** supports `last_n_days` (line 83-85), and `src/config.js` already reads `RETRY_LOOKBACK_DAYS` (default 30, guarded to [1,365]) and accepts `RETRY_SCOPE ∈ {current_month, last_n_days}`. The only gap is the **default**: `config.retry.scope` defaults to `'current_month'` (config.js:198, commented "customer-locked 2026-05-15"). Both controllers consume the same `config.retry.scope`, so flipping the default is uniform across POs and payments.
- **Q2 (frequency):** `src/utils/RetryPolicy.js:computeBackoffWaitMinutes(errorCount, backoffConfig)` (line 28) computes the geometric curve from `config.retry.backoff.{initialMin,multiplier,maxMin}` (config.js:203-207, three range guards at 257-270). Both controllers' JS post-filter defer an ERROR row until its geometric window elapses. This is the behavior the meetings rejected — they want a **fixed** interval, **differentiated** by document type.
- **Unchanged/correct (Q4 + dedupe):** `buildErrorStatsApply` OUTER APPLY (errorCount + lastErrorAt), the `POSTED` NOT-EXISTS dedupe in the WHERE, and "retry everything" (Q4) are correct and stay.

## Requirements

1. **RETRY-C1 — Rolling 30-day scope default (amends RETRY-03)**: The default retry scope becomes a rolling 30-day window, uniform across POs and payments.
   - Current: `config.retry.scope` defaults to `'current_month'` (config.js:198); `last_n_days` + `RETRY_LOOKBACK_DAYS=30` already exist but are non-default.
   - Target: default `RETRY_SCOPE` → `'last_n_days'` (keep `RETRY_LOOKBACK_DAYS` default 30). `current_month` remains a valid, env-selectable value (only the default changes; `buildScopeWhere` is not restructured). The stale "customer-locked 2026-05-15" comment is corrected to reference the 2026-06-11 team decision. Applies identically to POs (`dateField='Fecha'`) and payments (`dateField='P.AUDTDATE'`).
   - Acceptance: with no env overrides, `config.retry.scope === 'last_n_days'` and `config.retry.lookbackDays === 30`; `buildScopeWhere(config.retry, {dateField})` returns a `>= DATEADD(day, -30, CAST(GETDATE() AS DATE))` fragment for both date fields; `RETRY_SCOPE=current_month` still returns the month-bounds fragment. Verified by `RetryPolicy.test.js` + a config-load assertion.

2. **RETRY-C2 — Fixed differentiated interval helper (supersedes RETRY-04)**: The geometric backoff helper is replaced by a fixed-interval helper that ignores prior error count and differs by document type.
   - Current: `computeBackoffWaitMinutes(errorCount, backoffConfig)` returns `initialMin × multiplier^(errorCount-1)` capped at `maxMin`.
   - Target: a helper (working name `getRetryIntervalMinutes(config, docType)`; final name settled in plan) returns `config.retry.intervalPaymentMin` for `docType='payment'` and `config.retry.intervalPoMin` for `docType='po'`, with no dependence on any error-count argument. `computeBackoffWaitMinutes` is removed from `module.exports`.
   - Acceptance: `getRetryIntervalMinutes(config,'payment') === config.retry.intervalPaymentMin` (30 by default) and `(config,'po') === config.retry.intervalPoMin` (240 by default), and the return value is identical regardless of any attempt-count input; `computeBackoffWaitMinutes` is not exported. Verified by the rewritten `RetryPolicy.test.js`.

3. **RETRY-C3 — Interval env vars + guards; backoff env vars removed & inert (supersedes RETRY-05)**: Two new range-guarded interval env vars replace the three backoff env vars; a stale backoff var never blocks boot.
   - Current: `RETRY_BACKOFF_INITIAL_MIN` (15), `RETRY_BACKOFF_MULTIPLIER` (2), `RETRY_BACKOFF_MAX_MIN` (1440) → `config.retry.backoff.*` with three range guards.
   - Target: `RETRY_INTERVAL_PAYMENT_MIN` (default 30, range [10,60]) and `RETRY_INTERVAL_PO_MIN` (default 240, range [30,1440]) → `config.retry.intervalPaymentMin` / `config.retry.intervalPoMin`. The `config.retry.backoff` namespace, its three env reads, and its three guards are removed. If any `RETRY_BACKOFF_*` var is still present in the environment it is **inert** (unread) and the loader emits **one `[CONFIG WARN]` per detected obsolete var** (never fatal — this is an always-on service; a removed-optional cannot cause wrong behavior, so fail-fast is reserved for invalid REQUIRED config).
   - Acceptance: config loads with `intervalPaymentMin=30`, `intervalPoMin=240`, and `config.retry.backoff === undefined`; startup exits 1 with `[CONFIG ERROR]` when `RETRY_INTERVAL_PAYMENT_MIN ∉ [10,60]` or `RETRY_INTERVAL_PO_MIN ∉ [30,1440]`; setting `RETRY_BACKOFF_INITIAL_MIN=5` does **not** prevent boot and produces exactly one `[CONFIG WARN]` line naming that var.

4. **RETRY-C4 — Per-type eligibility in both controllers; first-attempt stays immediately eligible**: Each controller's retry-eligibility post-filter uses its own document type's fixed interval, and a never-failed document is never deferred.
   - Current: both controllers defer an ERROR row using `computeBackoffWaitMinutes(ef.errorCount, config.retry.backoff)`.
   - Target: `PortalOC_Creator.js` uses `intervalPoMin`; `PortalPaymentController.js` uses `intervalPaymentMin`. Eligibility rule: a row with **no prior ERROR row** (no `lastErrorAt`) is eligible **immediately** (a first upload is not a retry); a row **with** `lastErrorAt` becomes eligible when `(now − lastErrorAt) ≥ intervalMin` (`≥` inclusive). `[BACKOFF-DEFER]` / `[BACKOFF]` log labels are renamed `[RETRY-DEFER]` / `[RETRY]`.
   - Acceptance: rewritten `PortalOC_Creator.cron-where.test.js` and `PortalPaymentController.cron-where.test.js` each prove four outcomes — (a) `POSTED` row → excluded; (b) ERROR row with `lastErrorAt` inside the interval → deferred; (c) ERROR row with `lastErrorAt` at/older than the interval → included; (d) no ERROR row (first attempt) → included immediately — evaluated against `intervalPoMin` (PO suite) / `intervalPaymentMin` (payment suite), with zero geometric-curve assertions.

5. **RETRY-C5 — Diagnostic section 6 relabel (amends RETRY-07)**: The `po-cron-diagnostic.js` retry section reports fixed-interval fields, not backoff.
   - Current: section 6 "Estado de backoff" reports `backoffWaitMin` from the geometric curve.
   - Target: section 6 renamed to retry-interval and reports `lastErrorAt`, `retryIntervalMin` (the config value for the document type), and `nextEligibleAt = lastErrorAt + retryIntervalMin`; `backoffWaitMin` and any geometric-curve language removed. A deferred PO's verdict reads "deferred — next eligible at <timestamp>".
   - Acceptance: the script source contains no `backoffWaitMin` / geometric-curve wording and does emit `retryIntervalMin` + `nextEligibleAt` (verified structurally without a Sage DB; live output confirmed post-deploy).

6. **RETRY-C6 — Obsolete tests deleted; baseline preserved**: Tests that assert the geometric curve or backoff env vars are removed/rewritten, and no new failures are introduced.
   - Current: `RetryPolicy.test.js` asserts the canonical curve (`15,30,60,…,1440`); both `*.cron-where.test.js` suites assert geometric deferral. These pass but validate the rejected behavior.
   - Target: geometric-curve assertions deleted; `RetryPolicy.test.js` rewritten for the fixed-interval helper + scope default; both cron-where suites rewritten per RETRY-C4. `.env.example` updated (add the two interval vars + `RETRY_SCOPE=last_n_days` default; remove `RETRY_BACKOFF_*`).
   - Acceptance: `npm test` shows the same ~7 pre-existing failures (`PaymentReconciliation`, `TransformTime`, `no-process-exit`, `enforcement-wiring` per CLAUDE.md §6) and **zero new** failures; no test in the suite asserts a geometric backoff curve.

## Boundaries

**In scope:**
- Q1: flip default `RETRY_SCOPE` → `last_n_days` (30-day rolling), uniform for POs and payments; retain `current_month` as an env option.
- Q2: fixed differentiated retry interval — `RETRY_INTERVAL_PAYMENT_MIN` (30, [10,60]) and `RETRY_INTERVAL_PO_MIN` (240, [30,1440]); remove the geometric helper, the `RETRY_BACKOFF_*` env vars, and their guards; emit `[CONFIG WARN]` on obsolete vars.
- Both controllers' retry-eligibility post-filter updated per type; first-attempt (never-failed) documents remain immediately eligible.
- `po-cron-diagnostic.js` section 6 relabel; `[BACKOFF*]` → `[RETRY*]` log labels.
- Rewrite `RetryPolicy.test.js` + both `*.cron-where.test.js`; update `.env.example`.

**Out of scope:**
- **Q3 differentiated alerts** (immediate PO alert + biweekly payment report, `EomNotification.js` → `PendingNotifications.js`, `dispatchEomIfDue` rewrite) — deferred to a later amendment of this SPEC after the Santiago session; keeps this correction shippable independently.
- **Cross-system (Sage + portal) retry-detection query** — the mechanism that surfaces OCs authorized-but-absent-from-portal; pending the Santiago working session (he identified the risk and knows which docs fall out today = real test cases).
- **Manual sync button (bastión)** — separate work stream; needs client-IT coordination (Jorge/Alan).
- **Clock-basis alignment** between the Node process `now` and SQL Server `lastUpdate` — pre-existing since Phase 20, not introduced here; documented as an assumption (see Constraints), not fixed in 20.1.
- **Per-type Q1 window differentiation** — no signal in the meetings; would add config surface. The window is uniform; only the Q2 *interval* differs by type.
- **Schema changes to `fesa.dbo.fesaOCFocaltec` / `fesaPagosFocaltec`** — v2.4 constraint; everything derives from existing rows.
- **Cron cadence change** — stays 15 min (CLAUDE.md §3/§9 defense-in-depth tier).
- **Backfill script for pre-change orphan docs** — the first post-deploy tick lifts everything in the 30-day scope (implicit backfill); a dedicated script is v2.5 if ever needed.

## Constraints

- **Always-on (CLAUDE.md §3):** this change introduces **no** new `setInterval`/`setTimeout`/EventEmitter listener/module-scope `Map|Set`/`child_process` — it is pure-function + config + post-filter logic. No new retained-state lifetime to bound. (This is the key always-on check for the phase, and it passes by construction.)
- **No local Sage DB (STATE blocker):** SQL-touching behavior is validated **structurally** and via **Jest with mocked query results**; real cron-lift behavior is a **post-deploy** observation via the `[CRON] retry-scope=…` log line and `fesa.*` row inspection.
- **Obsolete-var handling is uptime-preserving:** removed `RETRY_BACKOFF_*` vars are inert + `[CONFIG WARN]`, never fail-fast — a boot failure on this always-on payment-data service is the exact failure that hurt the customer at the 28–29 April month-end close.
- **Defense-in-depth invariant unchanged:** `axios (30s) < step (5m) < child (10m) < lock (14m)` is untouched — this change never touches a timeout tier.
- **SQL-injection discipline (CLAUDE.md §6#1):** the interval values are range-guarded numbers used in JS timing math, never interpolated into SQL; `buildScopeWhere` interpolates only the already-range-guarded `lookbackDays`. No new SQL string-interpolation site is added.
- **Hook bypass at execute time:** editing `src/config.js` trips `pre-edit-critical.sh`; execution runs with `SAGECONNECT_HOOKS_BYPASS=1` (authorized per session, execute-phase only). The SPEC/discuss/plan steps touch only `.planning/` and need no bypass.
- **Conventions:** CommonJS, 4-space indent, `logGenerator(LOG_FILE, level, msg)` for anything that must survive a restart.

## Acceptance Criteria

- [ ] With no env overrides, `config.retry.scope === 'last_n_days'` and `config.retry.lookbackDays === 30`; `RETRY_SCOPE=current_month` is still selectable.
- [ ] `buildScopeWhere` emits the rolling-30-day fragment for both `Fecha` (POs) and `P.AUDTDATE` (payments).
- [ ] `getRetryIntervalMinutes(config,'payment') === 30` and `(config,'po') === 240` by default, independent of any error-count input.
- [ ] `computeBackoffWaitMinutes` and `config.retry.backoff` no longer exist.
- [ ] Startup exits 1 with `[CONFIG ERROR]` for `RETRY_INTERVAL_PAYMENT_MIN ∉ [10,60]` or `RETRY_INTERVAL_PO_MIN ∉ [30,1440]`.
- [ ] A stale `RETRY_BACKOFF_*` env var does NOT block boot and emits exactly one `[CONFIG WARN]` naming it.
- [ ] A document with no prior ERROR row (first attempt) is eligible immediately, in both controllers.
- [ ] A document with `lastErrorAt` is deferred until `(now − lastErrorAt) ≥` its type's interval (`≥` inclusive): `intervalPoMin` for POs, `intervalPaymentMin` for payments.
- [ ] A `POSTED` row is never re-selected (dedupe unchanged).
- [ ] `po-cron-diagnostic.js` section 6 reports `lastErrorAt` / `retryIntervalMin` / `nextEligibleAt`, and never `backoffWaitMin`.
- [ ] `[BACKOFF*]` log labels are renamed to `[RETRY*]`.
- [ ] `.env.example` documents `RETRY_INTERVAL_PAYMENT_MIN` / `RETRY_INTERVAL_PO_MIN` and the `RETRY_SCOPE=last_n_days` default, and drops `RETRY_BACKOFF_*`.
- [ ] `npm test` shows no NEW failures beyond the ~7-failure baseline; no test asserts a geometric backoff curve.
