# Phase 20.4: Bound the portal existence probe per tick - Context

**Gathered:** 2026-09-08
**Status:** Ready for planning

<domain>
## Phase Boundary

A dual bound — elapsed-time budget **and** probe count cap, whichever is reached first — on the `4.1)` portal existence probe inside `createPurchaseOrders()`, so the probe cannot consume the 5-minute `createPurchaseOrders` step budget. An OC that arrives after either bound is reached is deferred fail-closed to the next tick, and the resulting backlog is reported on the existing `[PORTAL-CHECK-SUMMARY]` line.

This phase adds **a stop condition to an existing loop**. It does not change what the probe asks, how its answer is dispatched, what the cron query selects, the retry timing, or the schema. Closes **WR-05**, open since `20.3-REVIEW.md`.

</domain>

<decisions>
## Implementation Decisions

The user delegated all gray areas (2026-09-08): *"haz lo que se tenga que hacer, de la mejor manera, que sea lo mejor y lo más óptimo."* This repeats the 20.3 delegation and its three standing criteria, which remain the vara here: **satisfy the locked SPEC**, **minimum diff**, **do not knock existing structures out of alignment**. Rationale is recorded for every decision so the planner can tell a deliberate choice from an arbitrary one.

### Where the clock starts and what it measures

- **D-01: The elapsed-time origin is captured as the FIRST statement of `createPurchaseOrders()`** — `const tickStart = Date.now();` at `PortalOC_Creator.js:34`, before `getCurrentDateString()`, not immediately before the `for` loop at L296.

  *Why:* the SPEC's stated goal is that the probe "cannot consume the whole 5-minute `createPurchaseOrders` **step** budget". The ceiling being protected belongs to the **step**, not to the probe. If the origin sits just before the loop, the 120 s budget is spent *on top of* whatever the SELECT already consumed — and that SELECT is an `OUTER APPLY` over a 9,032-row control table, so the step can still blow through 300 s with the bound fully in place. Measuring from function entry makes the budget a **slice of the step**, which is precisely the arithmetic the relational guard assumes: 120 s of probing + 180 s of remaining POST work = 300 s. That sum only closes if both sides are measured from the same origin.

  *Accepted cost:* an unusually slow SELECT can leave zero probes in that tick. That is fail-closed and correct — if the step is already late, probing makes it worse — and D-04 below is what makes the case visible instead of silent.

  *Always-on (CLAUDE.md §3):* `tickStart` is a function-scoped `const`, unreachable the moment `createPurchaseOrders()` returns. It is not a cache, does not grow across ticks, and there is nothing to release. A module-scope origin would make tick N's budget depend on tick N−1 — the exact class of retained state §3 forbids.

- **D-02: `Date.now()`, not `process.hrtime.bigint()`.**

  *Why:* a monotonic clock would be more correct in theory — immune to an NTP step on a Windows Server mid-tick — but there is no `hrtime` precedent anywhere in this codebase, it is materially harder to pin deterministically in Jest, and an NTP correction landing inside a single 5-minute window on a domain-synced server is theoretical. `Date.now()` wins on minimum diff and testability. **Record the reasoning in a comment** so a future reader does not "upgrade" it without knowing the trade was deliberate.

- **D-03 (clock doctrine, load-bearing): this is NOT the Phase 20.2 `dbNow` case, and must be commented as such.**

  *Why:* Phase 20.2 established that retry eligibility reads the SQL Server clock (`GETDATE()` projected as `dbNow`) because it compares against timestamps **SQL Server itself wrote** — mixing clocks there produced the -360 min skew that made `[RETRY-DEFER]` unable to fire. This phase measures a **local duration against its own origin**: both endpoints come from the same process clock, so no cross-clock comparison exists and `dbNow` is inapplicable. Without an explicit comment, a future reader following 20.2's doctrine would "fix" this into a bug — a round-trip to SQL per loop iteration purely to measure elapsed time.

### Shape of the cut in the loop

- **D-04: The bound is a NESTED early `continue` inside `if (priorErrors > 0)` — NOT an extended `&&` on the gate.**

  ```js
  if (priorErrors > 0) {
    if (probed >= config.portal.probeMaxPerTick
        || (Date.now() - tickStart) >= config.portal.probeBudgetMs) {
      probeDeferred++;
      continue;                       // RETRY-E3: no GET, no POST, no INSERT, no Joi
    }
    // ... existing 4.1 probe block, unchanged ...
  }
  ```

  *Why this is called out explicitly:* RETRY-E1's own wording — *"the gate additionally requires both budget-remaining and count-remaining to be true"* — reads naturally as `if (priorErrors > 0 && budgetLeft && countLeft)`. **That form is a bug.** When the gate goes false today, control falls through to the POST. A deferred OC would therefore be POSTed, which is the exact opposite of RETRY-E3 and would re-manufacture the duplicate-POST / 409 that Phase 20.3 exists to eliminate. The nested form is the only one that satisfies both requirements at once. This is a documented reading hazard, not a preference.

- **D-05: Count is checked before budget.** Purely readability — the count comparison is free, the clock read is not, and short-circuit `||` skips the second when the first is true. No behavioral difference.

- **D-06: The deferred path emits NO per-row log line — the summary only.**

  *Why:* Phase 20.3's D-06 established per-row lines for the probe's *outcomes* (found / cancelled / rejected), where volume is bounded by what was actually probed. The deferred set is bounded only by the size of `ordersToSend`, which is exactly the case this phase exists for — a per-row line would emit thousands of lines on the worst tick, which is the tick the operator most needs to be able to read. The count belongs in the aggregate.

### Operator visibility

- **D-07: The summary is emitted when `probed > 0 || probeDeferred > 0`** — `PortalOC_Creator.js:562` changes from `if (probed > 0)`.

  *Why:* with D-01's origin at function entry, `probed === 0 && probeDeferred > 0` is reachable — a SELECT that overruns the budget defers the first probe-eligible OC without ever probing. Under the current condition that tick prints nothing, so the single worst scenario is the one that stays silent, and RETRY-E4 ("the backlog becomes visible") is unmet exactly where it matters. This does not contradict 20.3's D-06 rationale for the omission (*"el tick silencioso es el abrumadoramente común"*): a tick with `deferred > 0` is not a silent tick. The counter invariant is untouched — `probeDeferred` is counted outside `probed`.

- **D-08: `deferred=` stays inside the existing `info`-level summary line; no separate WARN line.**

  *Why:* the SPEC locks the field ("The summary line gains a trailing `deferred=` field") and its out-of-scope list is long and deliberate. More to the point, the SPEC's accepted-residual-risk section already fixes the escalation criterion: *"the `deferred=` field makes a persistent backlog visible to the operator, which is the signal that would justify building fairness"*, and *"if `deferred=` stays non-zero across consecutive ticks... this becomes a real finding and needs its own phase."* Adding a WARN now would pre-empt that criterion with a different one. Recorded as a deferred idea instead.

- **D-09: The five existing fields keep their names, order and spelling; `deferred=` is appended last.** The 20.3 log-anchoring assertions parse this line and must continue to pass unchanged (SPEC acceptance criterion).

### Counter placement

- **D-10: `let probeDeferred = 0;` joins the five existing counters at `PortalOC_Creator.js:286-291`, function-scoped, and is incremented ONLY on the fail-closed path — outside and before the probe's `try` block.**

  *Why:* incrementing inside the `try` is how WR-02 originally broke the invariant. The deferred path never enters the `try` at all, which is what keeps `probed === found + absent + skipped + unknown` true byte-for-byte. Verifying that invariant against real portal responses is still item 2 of the pending 20.3 human UAT, so it must not be perturbed.

### Config surface

- **D-11: `config.portal.probeBudgetMs` and `config.portal.probeMaxPerTick`, declared next to `httpTimeoutMs` (`src/config.js:137`), parsed through the existing `parseEnvNumber(raw, parser, def)` helper (`src/config.js:94`).** Defaults 120000 and 50. **OPTIONAL, never REQUIRED** — the October server boots from a fresh `.env` and a missing REQUIRED var would fail-fast the service (decision 20.1-01).

  `parseEnvNumber` is load-bearing here for the reason its own JSDoc gives: it applies the default only when the var is absent/empty, and passes an explicitly-set `'0'` or `'abc'` through verbatim so the range guard can reject it. The `parseInt(...) || default` idiom would silently swallow `'0'` and bypass the floor.

- **D-12: Both range guards go INSIDE the existing guard block (`src/config.js:221-244`), placed AFTER the `STEP_TIMEOUT_MS` guard**, in the established `console.error('[CONFIG ERROR] ...'); process.exit(1);` shape.

  *Why after, not anywhere in the block:* the relational guard compares against `config.schedule.stepTimeoutMs`. Placing it before that value's own floor guard would let it compare against a value already known to be invalid, producing a misleading error naming the wrong var. Order is a correctness constraint, not style.

  Three guards total: floor `probeBudgetMs >= 10000`; floor `probeMaxPerTick >= 1`; relational `probeBudgetMs <= stepTimeoutMs * 0.5`, whose message **names both values** so the operator can see which one to change.

- **D-13: `.env.example` documents both vars with default and range, and its defense-in-depth comment (line 79) is extended to name the new innermost tier:** `PORTAL_HTTP_TIMEOUT_MS (30s) < PORTAL_PROBE_BUDGET_MS (2m) < STEP_TIMEOUT_MS (5m) < CHILD_PROCESS_TIMEOUT_MS (10m) < LOCK_TIMEOUT_MS (14m)`.

### Test strategy

- **D-14: Drive the clock with `jest.spyOn(Date, 'now')` and a controlled sequence — NOT `jest.useFakeTimers()`.**

  *Why:* the 20.3 suite (43 tests across 3 `describe` blocks) uses no fake timers anywhere — pure `jest.mock` plus `beforeEach(jest.clearAllMocks)`. Installing fake timers changes the environment for every test in whatever file they land in, and the existing tests are `async` with `await` over mocked promises. Modern fake timers and microtasks do coexist, but that is risk surface bought for nothing: the only time source the new code reads is `Date.now()`, so a spy over `Date.now` is deterministic, surgical, and leaves the event loop alone.

  *On the letter of the SPEC:* RETRY-E1's acceptance says "proven with fake timers". A `Date.now` spy **is** a fake clock; what the criterion actually demands is determinism and that both bounds be independently reachable. Recorded here explicitly so `/gsd-verify-work` reads this as a documented implementation choice, not a deviation.

- **D-15: New test file `tests/controller/PortalOC_Creator.probe-budget.test.js` — do NOT extend `PortalOC_Creator.portal-check.test.js`.**

  *Why:* a `Date.now` spy in a shared `beforeEach` would reach the 43 existing tests, and the SPEC requires the 20.3 assertions to keep passing unchanged. A separate file makes that true by construction. Same reasoning the Phase 23 D-16 decision used (own file rather than editing `schedule-routes.test.js`).

- **D-16: Both bounds must be proven independently reachable** — the stalling-stub test must stop on the budget with the count cap far from reached, and the immediate-resolve test must stop on the count cap with the budget far from exhausted. A test that passes because the *other* bound fired first proves nothing; this is an explicit SPEC acceptance criterion.

The three standing criteria (SPEC, minimum diff, no misalignment) were the tiebreaker in each case; where "lo más óptimo" and "minimum diff" pulled apart, the record says which won and why — D-01 (correctness of the bound over a marginally simpler origin), D-07 (a one-token condition change that closes a real blind spot), and D-08 (the SPEC's own escalation criterion over extra log volume) are the three that mattered.

## Deferred Ideas

- **A WARN-level line when `deferred > 0`** (rejected as D-08). The `info` summary is what the SPEC locks, and its residual-risk section already fixes the escalation criterion. If `deferred=` proves easy to miss in practice on `zcl-rds-test`, this becomes a one-line follow-up.
- **Fair scheduling of deferred OCs** — the SPEC's own accepted residual risk. The loop iterates `ordersToSend` in stable SQL order, so with a probeable set larger than the bound, the tail can starve indefinitely. Harmless because starvation is fail-closed, and visible via `deferred=`. Fixing it likely means rotating the starting offset, which needs state that survives a tick and therefore its own §3 lifetime argument — a separate phase, justified only if `deferred=` stays non-zero across consecutive ticks.
- **`process.hrtime.bigint()` for a monotonic origin** (rejected as D-02). Revisit only if an NTP step is ever observed corrupting a tick.
