# Phase 20.4: Bound the portal existence probe per tick — Specification

**Created:** 2026-09-03
**Ambiguity score:** 0.107 (gate: ≤ 0.20)
**Requirements:** 4 locked
**Milestone:** v2.4 — Retry policies · **Branch:** `feat/reintentos`
**Closes:** WR-05, open since `20.3-REVIEW.md`

## Goal

Bound the Phase 20.3 portal existence probe so it cannot consume the whole 5-minute `createPurchaseOrders` step budget: stop probing when either a configurable elapsed-time budget or a configurable probe count is reached, whichever comes first, defer the remaining OCs to the next tick fail-closed, and report the backlog on the existing summary line.

## Background

**The hole.** Phase 20.3 added the `4.1)` probe block to `src/controller/PortalOC_Creator.js`. Its gate is `if (priorErrors > 0)` (L308) and nothing else — one serial portal `GET` per OC with a prior failure, with **no cap on count and no cap on elapsed time**. The step that contains it is bounded from the outside by `withStepTimeout(createPurchaseOrders(i), config.schedule.stepTimeoutMs, …)` (`src/background.js:237`), default 300 s.

**Why the outer bound is not enough.** The probe reuses the `PortalClient` singleton, so each `GET` can take up to the 30 s axios ceiling before it gives up. A degraded portal — one that answers slowly rather than failing fast — is therefore the expensive case, not the outage case: roughly **10 probed OCs exhaust the full 300 s**. When the step timeout fires, `background.js:246` re-throws and the tenant's remaining steps (`processOrderChanges`, `closePurchaseOrders`, …) are skipped for that tick. But the original promise is **not cancelled** — this is the phantom continuation accepted as D-10 and documented at `background.js:88-90`. The abandoned `createPurchaseOrders` keeps iterating: still probing, still POSTing, still INSERTing rows, while the rest of the tick advances and potentially into the following tick, with no operator-visible signal that two copies of the step are live.

**The backlog that makes it likely.** Production, measured 2026-07-27 on `ZCL-SQL-01`: `fesaOCFocaltec` holds 9,032 rows, of which **3,313 are `ERROR`**. Every failed attempt INSERTs a new row, so those 3,313 rows are accumulated retry history, not 3,313 distinct OCs — but the distinct-OC count behind them has never been measured, and the probe gate opens once per distinct OC per tick. Two open findings make that set grow rather than shrink: WR-04/CR-02 (a portal-`CANCELLED` or unrecognised-status OC is re-selected and re-probed every tick, forever) and CR-02's own deferral. The first tick after the phase reaches a server is the worst one, and it is the one nobody has watched.

**Why this cannot wait for production data.** Sizing the risk is item 3 of the Phase 20.3 human UAT, and it is unresolvable before deploy: it depends on real portal latency and the real distinct-OC cardinality. The 20.3 verification routed it to human verification precisely because no code mitigation existed. Phase 20.4 replaces that open bet with a bound, so the first tick on the new server is safe regardless of what the cardinality turns out to be.

**What the existing config guards do and do not do.** `src/config.js:222-242` holds four range guards (`LOCK_TIMEOUT_MS`, `PORTAL_HTTP_TIMEOUT_MS`, `CHILD_PROCESS_TIMEOUT_MS`, `STEP_TIMEOUT_MS`). Every one of them checks a **floor in isolation** — `>= 60000`, `>= 1000`, `>= 30000`. **None checks the relationship between tiers.** `STEP_TIMEOUT_MS=30000` alongside `PORTAL_HTTP_TIMEOUT_MS=30000` passes all four and violates the `axios < step` invariant that CLAUDE.md §9 declares load-bearing. That invariant is documented, not enforced. A floor-only guard on the new budget would inherit the same hole and would let a mistaken `.env` on the October server silently restore the exact failure this phase removes.

**Deployment context.** This work lands on `feat/reintentos`, which does **not** merge to `master` until the execution button is in production. The retry work travels with the October server migration, and the new server boots from a **fresh `.env`**. A REQUIRED env var missing there would fail-fast the service on first boot — the shape of the April month-end outage, and the reason decision 20.1-01 fixed the rule that removed OPTIONAL vars warn and never exit.

## Requirements

1. **RETRY-E1 — Dual bound on the probe loop**: probing stops when the elapsed-time budget is exhausted **or** the probe count cap is reached, whichever occurs first.
   - Current: `PortalOC_Creator.js:308` gates only on `priorErrors > 0`. No count cap, no elapsed-time reading, no upper bound of any kind on how many serial `GET`s one tick issues.
   - Target: the gate additionally requires both budget-remaining and count-remaining to be true. The elapsed reading is taken from a timestamp captured **inside** `createPurchaseOrders` (function-scoped, per CLAUDE.md §3 — no module-scope state that survives a tick), measured against `config.portal.probeBudgetMs`; the count is the existing `probed` counter measured against `config.portal.probeMaxPerTick`.
   - Acceptance: with a probe stub that stalls 30 s per call and a budget of 120 000 ms, the loop issues at most 4 probes and then stops, proven with fake timers against a fixture of ≥ 20 probe-eligible OCs. With a probe stub that resolves immediately, the same fixture stops at the count cap, not the budget — proving both bounds are live and independently reachable.

2. **RETRY-E2 — Both parameters are OPTIONAL env vars with a relational guard**: `PORTAL_PROBE_BUDGET_MS` and `PORTAL_PROBE_MAX_PER_TICK`, defaults 120 000 ms and 50.
   - Current: neither var exists. `src/config.js` has no `portal.probeBudgetMs` / `portal.probeMaxPerTick`; `.env.example:80` documents the four-tier invariant with no probe tier in it.
   - Target: both parsed through the existing `parseEnvNumber(raw, parser, def)` helper (`src/config.js:94`) so that unset, empty or whitespace-only falls back to the default and the service boots. Range guards follow the four existing ones in placement and message shape, with one addition: the budget guard is **relational** — it fails startup when the budget exceeds 50 % of `config.schedule.stepTimeoutMs`, naming both values in the error so the operator can see which one to change.
   - Acceptance: with neither var set, `node -e "require('./src/config')"` exits 0 and `config.portal.probeBudgetMs === 120000` / `config.portal.probeMaxPerTick === 50`. With `PORTAL_PROBE_BUDGET_MS=200000` and `STEP_TIMEOUT_MS=300000` (200 s > 150 s = 50 %), startup exits 1 with a `[CONFIG ERROR]` naming both values. With `PORTAL_PROBE_BUDGET_MS=5000` (below the 10 000 ms floor), startup exits 1. With `PORTAL_PROBE_BUDGET_MS=""`, startup exits 0 at the default.

3. **RETRY-E3 — Reaching either bound is fail-closed**: a deferred OC produces no portal write and no local write.
   - Current: every probe-eligible OC either reaches the probe or, absent the probe, reaches the POST. There is no third path.
   - Target: an OC that is probe-eligible but arrives after a bound is reached takes an early `continue` — no `GET` is issued, the POST is **not** reached, no `INSERT` of any status is emitted, and no Joi validation runs (which matters: the Joi failure path is itself an `ERROR`-row emitter, and Phase 20.3 deliberately placed the probe block ahead of it for that reason). The OC is simply re-evaluated on the next tick.
   - Acceptance: with the budget exhausted after probe 4 of a 20-OC fixture, the remaining 16 OCs produce zero `portalClient.post` calls, zero `runQuery` INSERT emissions, and zero `validatePO` calls — asserted on the mocks directly, not inferred from log text.

4. **RETRY-E4 — The counter invariant survives and the backlog becomes visible**: `deferred` is counted outside `probed`, and `[PORTAL-CHECK-SUMMARY]` reports it.
   - Current: `PortalOC_Creator.js:559-563` emits `probed= found= absent= skipped= unknown=` under the documented invariant `probed === found + absent + skipped + unknown`, verified under Jest but never against real portal responses — that is item 2 of the still-pending 20.3 human UAT.
   - Target: a `probeDeferred` counter, function-scoped like the existing five, incremented **only** on the fail-closed path of RETRY-E3 and never inside the probe's own try block. The summary line gains a trailing `deferred=` field. Because a deferred OC is never probed, `probed` does not move and the invariant holds unchanged.
   - Acceptance: across every scenario in the suite — bound reached, bound not reached, probe failure mid-write, mixed outcomes — `probed === found + absent + skipped + unknown` holds exactly, asserted as an explicit equality on the parsed summary line rather than on individual counters. The `deferred=` field appears last and the pre-existing five fields keep their current names, order and spelling, so the 20.3 log-anchoring assertions continue to pass unchanged.

## Boundaries

**In scope:**
- The dual bound (elapsed-time budget + count cap) in the `4.1)` block of `src/controller/PortalOC_Creator.js`
- `config.portal.probeBudgetMs` and `config.portal.probeMaxPerTick` in `src/config.js`, with floor guards and the relational budget-vs-step guard
- Both vars documented in `.env.example`, and its line 80 defense-in-depth comment extended with the new innermost tier
- The `probeDeferred` counter and the `deferred=` field on `[PORTAL-CHECK-SUMMARY]`
- Jest coverage for both bounds, the fail-closed path, the counter invariant, and all four config-guard outcomes

**Out of scope:**
- `src/utils/GetPurchaseOrders.js` — the bound belongs to the caller that owns the loop, not to a single-request helper. Modifying it would put per-call state in a pure function and break the 20.3 guard that asserts its options object carries `headers` only.
- **WR-03** (the tautological pass-through mocks of `groupOrdersByNumber` / `parseExternPurchaseOrders`) — a test-integrity fix with its own risk surface; bundling it would make this diff unreviewable.
- **WR-04 / CR-02** (adding `CANCELLED` to the `NOT EXISTS` dedupe IN-list) — this is what makes the probeable set grow without bound, so it is the natural follow-up, but it is a one-line SQL change to a dedupe that 14 other sites mirror and it needs its own caller audit (CLAUDE.md §6 #2).
- **WR-06**, **IN-02**, **IN-03**, **IN-04** — unrelated open findings from the same review.
- Cancelling the phantom continuation itself — D-10 is an accepted architectural decision recorded at `background.js:88-90`, not a defect. This phase makes the continuation far less likely to trigger; it does not change what happens if it does.
- Any probe, bound or counter for **payments** — payments have no `ERROR` rows at all (CR-03, deferred), so there is nothing to bound.
- Any schema change, and any change to the RYASA exclusion, the 30-day scope, or the RETRY-C7 `status IN ('CLOSED','POSTED')` dedupe.

## Constraints

- **Always-on (CLAUDE.md §3):** the elapsed-time origin must be captured inside `createPurchaseOrders` and die with it. A module-scope timestamp would make tick N's budget depend on tick N−1 and would never be reclaimed — the exact class of retained state §3 exists to forbid.
- **Extends the defense-in-depth invariant with a new innermost tier:** `axios 30 s < probe budget < step 5 m < child 10 m < lock 14 m`. The budget is bounded above at 50 % of `STEP_TIMEOUT_MS` by the relational guard, which leaves the remaining half of the step for the POST work on genuinely-absent OCs — work that predates Phase 20.3 and still has to fit.
- **No new SQL string interpolation** (CLAUDE.md §6 #1). This phase adds no SQL.
- **`runQuery`'s signature is untouched** (CLAUDE.md §6 #2).
- **OPTIONAL, never REQUIRED**, for both vars — the October server boots from a fresh `.env` and a missing REQUIRED var would fail-fast the service (decision 20.1-01).
- **No local Sage DB and no staging** (HANDOFF §6): verification is structural + Jest with fake timers. Live confirmation happens on `zcl-rds-test` before the October migration begins, never during it.
- **Test baseline:** the CLAUDE.md §6 failing set (`PaymentReconciliation`, `TransformTime`, `no-process-exit`, `enforcement-wiring`, plus the `config` / `operation-manager` worker crashes). Last measured on this branch at the close of 20.3: 6 failed suites / 7 failed tests / 565 passed / 573 total.

## Acceptance Criteria

- [ ] With a 30 s-per-call probe stub and the default 120 000 ms budget, a ≥ 20-OC fixture issues at most 4 probes, then stops
- [ ] With an immediately-resolving probe stub, the same fixture stops at 50 probes (the count cap), not at the budget
- [ ] Both bounds are independently reachable — neither test above passes by accident of the other bound firing first
- [ ] An OC deferred by either bound issues no `GET`, no `POST`, no `INSERT`, and no Joi validation
- [ ] `probed === found + absent + skipped + unknown` holds in every suite scenario, asserted on the parsed summary line
- [ ] `[PORTAL-CHECK-SUMMARY]` ends with a `deferred=` field; the five existing fields keep their names, order and spelling
- [ ] With neither env var set, `node -e "require('./src/config')"` exits 0 with `probeBudgetMs === 120000` and `probeMaxPerTick === 50`
- [ ] `PORTAL_PROBE_BUDGET_MS=200000` with `STEP_TIMEOUT_MS=300000` exits 1 with a `[CONFIG ERROR]` naming both values
- [ ] `PORTAL_PROBE_BUDGET_MS=5000` exits 1 (below the 10 000 ms floor)
- [ ] `PORTAL_PROBE_MAX_PER_TICK=0` exits 1 (below the floor of 1)
- [ ] `.env.example` documents both vars with defaults and ranges, and its defense-in-depth comment names the probe tier
- [ ] No module-scope mutable state is introduced — `grep` confirms the elapsed-time origin is declared inside `createPurchaseOrders`
- [ ] `src/utils/GetPurchaseOrders.js` is byte-identical to its pre-phase content
- [ ] `npm test` holds at the CLAUDE.md §6 baseline with no NEW failing suites or tests

## Accepted residual risk

**Deferred OCs are not scheduled fairly.** The loop iterates `ordersToSend` in the order the SQL returned it, and that order is stable across ticks. With a probeable set larger than the per-tick bound, the same leading OCs are probed every tick and the tail can starve indefinitely. This is accepted for now on three grounds: the count cap of 50 exceeds any plausible distinct-OC cardinality behind the current backlog once WR-04/CR-02 stops re-feeding it; starvation is fail-closed and therefore harmless (a starved OC is simply not created that tick, exactly as today); and the `deferred=` field makes a persistent backlog visible to the operator, which is the signal that would justify building fairness. **If `deferred=` stays non-zero across consecutive ticks on `zcl-rds-test` or after the migration, this becomes a real finding and needs its own phase** — likely rotation of the starting offset, which is cheap but needs state that survives a tick and therefore an §3 lifetime argument.
